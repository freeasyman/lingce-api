# 随访提示词数据库写入规范

**适用业务：** 随访任务生成  
**提示词代码：** `followup_task_generation`  
**编写人：** Codex  
**编写时间：** 2026-09-13  
**适用项目：** `lingce-api`

## 1. 先看哪里

开始修改前，先查看以下内容：

1. 后台提示词管理页面：`http://localhost:3001/recordings/prompts`
2. API 提示词读取实现：`internal/followup/service.go`
3. 提示词表读写实现：`internal/recording/store.go`
4. 数据库迁移目录：`internal/store/migrations/`
5. 随访提示词迁移：`internal/store/migrations/20260913_003_seed_followup_task_prompt.sql`
6. 随访备份文本（仅供对照，不作为运行时来源）：
   - `apps/followup/data/followup-system-prompt.txt.bak.txt`
   - `apps/followup/data/followup-user-prompt.txt.bak.txt`

运行时不得从 `data` 目录读取提示词。唯一运行时来源是数据库。

## 2. 写入哪张表

全局业务提示词写入：

```text
recording_analysis_prompts
```

随访使用固定业务代码：

```text
followup_task_generation
```

同一个 `code` 表示同一个业务提示词。不能用页面显示名称“任务脚本生成”代替该代码。

## 3. 字段怎么填

| 字段 | 随访填写方式 |
|---|---|
| `code` | 固定为 `followup_task_generation` |
| `name` | `随访任务生成` |
| `description` | 说明根据完整清洗后转写生成可执行随访任务 |
| `category` | `analysis` |
| `system_prompt` | 完整角色、业务价值、生成原则、时间规则、证据规则、禁止事项和输出要求 |
| `user_prompt_template` | 客观 ID、医生和客户信息、录音时间、`cleaned_transcript` 模板 |
| `output_schema` | JSONB 格式的任务输出结构 |
| `version` | 当前为 `v1` |
| `is_active` | 正式使用时为 `true` |
| `usage_count` | 新建时必须为 `0`，不能写 `NULL` |
| `created_by` / `updated_by` | 系统迁移使用 `0`；后台人工操作使用实际用户 ID |
| `created_at` / `updated_at` | 使用 `NOW()` |

### 3.1 system_prompt

`system_prompt` 保存稳定规则，包括：

- AI 的角色；
- 随访对患者和医院的价值；
- 只能依据明确事实和原话；
- 任务数量、优先级和时间规则；
- evidence、script、contact_method 规则；
- 允许修改和不允许修改的边界；
- 禁止事项；
- 只输出 JSON 的要求。

完整正式内容以迁移文件中的 `$followup_system$` 内容为准。修改规则时必须同步更新迁移文件，不能只在开发库后台修改。

### 3.2 user_prompt_template

`user_prompt_template` 保存每次调用都会变化的输入模板。可用变量由 API 的 `renderUserPrompt` 定义：

```text
{{tenant_id}}
{{recording_id}}
{{encounter_id}}
{{employee_id}}
{{doctor_name}}
{{customer_id}}
{{customer_name}}
{{recorded_at}}
{{cleaned_transcript}}
```

随访模板必须包含：

```text
本次输入的客观信息：
tenant_id: {{tenant_id}}
recording_id: {{recording_id}}
encounter_id: {{encounter_id}}
employee_id: {{employee_id}}
doctor_name: {{doctor_name}}
customer_id: {{customer_id}}
customer_name: {{customer_name}}
recorded_at: {{recorded_at}}

以下是一次 Encounter 的完整清洗后转写：
{{cleaned_transcript}}
```

`cleaned_transcript` 必须是 Worker 清洗后的完整转写，不得替换成原始转写、摘要或截断文本。

### 3.3 output_schema

`output_schema` 是 JSONB，保存期望的输出结构，便于后台查看、版本管理和测试。它不是一次请求的业务结果，也不是用户提示词。

随访输出顶层结构：

```json
{
  "type": "object",
  "required": ["tasks"],
  "properties": {
    "tasks": {
      "type": "array",
      "items": {
        "type": "object",
        "required": [
          "title",
          "contact_time",
          "purpose",
          "background",
          "script",
          "evidence",
          "contact_method",
          "executor",
          "editable_fields"
        ]
      }
    }
  }
}
```

API 仍必须在 Go 代码中进行实际 JSON 解析和业务校验，不能只依赖 `output_schema`。

## 4. 租户覆盖怎么处理

租户覆盖写入现有表：

```text
recording_analysis_tenant_configs
```

运行时先读取全局 `recording_analysis_prompts`，再读取当前租户中 `prompt_code = 'followup_task_generation'` 且启用的配置：

- `custom_system_prompt` 非空：替换全局 `system_prompt`；
- `custom_user_prompt_template` 非空：替换全局 `user_prompt_template`；
- `custom_output_schema` 非空：保存并供管理展示；当前随访解析仍执行固定任务结构校验；
- `additional_instructions` 非空：追加到系统提示词末尾。

没有租户配置时使用全局提示词。全局提示词不存在或未启用时必须报错，不得回退到代码或文本文件中的旧提示词。

## 5. 如何幂等写入

正式迁移必须放在：

```text
internal/store/migrations/
```

文件名使用递增版本，例如：

```text
20260913_003_seed_followup_task_prompt.sql
```

迁移必须满足：

1. 用稳定 `code` 查找记录；
2. 已存在时 `UPDATE` 完整刷新正式内容；
3. 不存在时 `INSERT`；
4. `usage_count` 显式写 `0`；
5. 不删除已有提示词；
6. 不生成重复的 `code`；
7. 不在迁移文件中手动写 `BEGIN` / `COMMIT`；API 的 schema migration runner 会为每个迁移自动开启事务；
8. 由 API 的 schema migration runner 自动执行。

本项目采用：

```sql
BEGIN;
UPDATE ... WHERE code = 'followup_task_generation';
INSERT ... SELECT ... WHERE NOT EXISTS (...);
COMMIT;
```

这样既能修复已存在但内容过期的记录，也能初始化全新环境。

## 6. 修改提示词的流程

1. 先在需求文档中确认规则变更；
2. 修改迁移 SQL 中的完整 `system_prompt`、`user_prompt_template` 或 `output_schema`；
3. 保持 `code = 'followup_task_generation'` 不变；
4. 递增 `version`，例如从 `v1` 改为 `v2`；
5. 在开发库执行或启动 API 应用迁移；
6. 用查询 SQL 检查数据库实际内容；
7. 用真实录音重新分析，检查 `followup_generation_runs.prompt_code` 和 `prompt_version`；
8. 确认日志中的 system prompt、user prompt 与数据库版本一致。

不要只修改后台当前记录后就结束。否则新环境无法复现，迁移也无法解释线上提示词来源。

## 7. 检查 SQL

### 7.1 检查全局提示词

```sql
SELECT
  id,
  code,
  name,
  category,
  version,
  is_active,
  usage_count,
  length(COALESCE(system_prompt, '')) AS system_prompt_length,
  length(COALESCE(user_prompt_template, '')) AS user_prompt_length,
  output_schema,
  created_at,
  updated_at
FROM recording_analysis_prompts
WHERE code = 'followup_task_generation';
```

### 7.2 检查模板变量

```sql
SELECT
  code,
  version,
  user_prompt_template LIKE '%{{cleaned_transcript}}%' AS has_cleaned_transcript,
  user_prompt_template LIKE '%{{encounter_id}}%' AS has_encounter_id,
  user_prompt_template LIKE '%{{customer_id}}%' AS has_customer_id
FROM recording_analysis_prompts
WHERE code = 'followup_task_generation';
```

### 7.3 检查租户覆盖

```sql
SELECT
  tenant_id,
  prompt_code,
  is_enabled,
  priority,
  length(COALESCE(custom_system_prompt, '')) AS custom_system_prompt_length,
  length(COALESCE(custom_user_prompt_template, '')) AS custom_user_prompt_length,
  length(COALESCE(custom_output_schema, '')) AS custom_output_schema_length,
  length(COALESCE(additional_instructions, '')) AS additional_instructions_length
FROM recording_analysis_tenant_configs
WHERE prompt_code = 'followup_task_generation'
ORDER BY tenant_id, priority DESC, id DESC;
```

## 8. 运行时读取位置

随访 API 的读取和拼接位置：

```text
internal/followup/service.go
```

主要函数：

- `loadPrompt`：读取全局提示词和租户覆盖；
- `renderUserPrompt`：替换模板变量；
- `loadModelConfig`：读取 `llm_model_configs`；
- `callLLM`：调用内部 LLM 网关；
- `writeLLMLog`：记录实际提示词、模型配置和返回结果。

不要在 Handler 中写提示词，不要在 Worker 中读取随访提示词。

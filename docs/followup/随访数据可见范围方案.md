# 随访数据可见范围方案

**文档状态：** 已确认方案
**适用范围：** 随访中心任务及相关患者数据的查看权限
**确认日期：** 2026-09-11

## 一、目标与边界

本方案只解决“谁可以查看哪些员工的数据”，不改变现有员工体系，也不引入部门层级或复杂 ACL。

需要明确区分三种关系：

1. **功能权限**：员工是否可以使用随访中心及其功能；
2. **数据可见范围**：员工登录后可以查看哪些员工归属的数据；
3. **任务执行人**：某条任务由谁负责处理。

数据可见范围大于任务执行范围。`recording_tasks.assigned_to` 只表示任务执行人，不能作为查看权限判断依据。

## 二、现有 RBAC 调查结论

现有 RBAC 可以继续负责功能权限，主要结构包括：

```text
institution_employee_roles
→ institution_roles
→ institution_role_permissions
→ institution_permissions
```

现有 RBAC 没有发现能够直接表达以下关系的数据结构：

```text
viewer_employee_id
target_employee_id
```

也没有发现随访产品专用的员工数据可见范围表。

以下表不能直接代替本方案：

- `employee_partnerships`：表达“录音归属员工 → 任务执行员工”，用于任务分配；
- `emr_permission_assignments`：表达电子病历的 `self / department / tenant` 范围，不是员工之间的直接查看关系。

因此，本方案复用现有 RBAC 的功能权限判断，新增独立的随访数据可见范围关系。

## 三、最小数据结构

建议新增表：`followup_data_scopes`

字段：

| 字段 | 类型 | 约束 | 含义 |
|---|---|---|---|
| `id` | `bigserial` | 主键 | 关系记录 ID |
| `tenant_id` | `integer` | 非空 | 租户 ID |
| `viewer_employee_id` | `integer` | 非空 | 可以查看数据的员工 |
| `target_employee_id` | `integer` | 非空 | 被查看数据的归属员工 |
| `created_by` | `integer` | 可空 | 创建或修改关系的员工 |
| `created_at` | `timestamp` | 非空，默认当前时间 | 创建时间 |
| `updated_at` | `timestamp` | 非空，默认当前时间 | 更新时间 |

唯一约束：

```text
(tenant_id, viewer_employee_id, target_employee_id)
```

该约束保证同一个租户内，同一查看人和同一目标员工之间不会产生重复关系。

建议索引：

```text
(tenant_id, viewer_employee_id)
(tenant_id, target_employee_id)
```

所有员工 ID 必须校验属于同一 `tenant_id`，避免跨租户授权。

## 四、关系含义

表中每一行表示：

```text
viewer_employee_id 可以查看 target_employee_id 归属的数据
```

示例：

```text
tenant_id = 5
viewer_employee_id = A
target_employee_id = A
tenant_id = 5
viewer_employee_id = A
target_employee_id = B
tenant_id = 5
viewer_employee_id = A
target_employee_id = C
tenant_id = 5
viewer_employee_id = B
target_employee_id = B
```

含义是：

- 员工 A 可以查看 A、B、C 的数据；
- 员工 B 只能查看 B 的数据。

是否允许查看自己的数据，建议通过显式关系配置，不在代码中隐含推断。初始化时可为每名随访员工写入一条“查看自己”的关系。

## 五、查询规则

### 1. 任务列表

登录员工为 `viewer_employee_id` 时，只返回其可见范围内的数据：

```sql
SELECT rt.*
FROM recording_tasks rt
JOIN recordings r
  ON r.id = rt.recording_id
 AND r.tenant_id = rt.tenant_id
JOIN followup_data_scopes fds
  ON fds.tenant_id = rt.tenant_id
 AND fds.target_employee_id = r.employee_id
WHERE rt.tenant_id = $1
  AND fds.viewer_employee_id = $2;
```

这里使用 `recordings.employee_id` 作为录音归属员工/医生员工。不能使用 `recording_tasks.assigned_to` 代替，因为 `assigned_to` 表示任务执行人，不表示数据归属人。

### 2. 详情、统计及导出

任务详情、批量统计、导出接口必须复用同一可见范围过滤条件，不能只在前端隐藏数据。

### 3. 越权访问

员工请求不在可见范围内的任务 ID 时，后端统一返回无数据或无权限错误，不返回任务内容。

## 六、配置方式

随访中心提供“数据查看范围”配置页面，配置内容只包含：

- 查看员工；
- 可查看的员工列表；
- 保存、删除关系。

不配置部门、不配置组织树、不改变员工基础资料。

管理操作必须记录创建人和时间；删除关系采用物理删除即可，后续如需审计再增加操作日志，不在 MVP 引入复杂历史版本。

## 七、与任务执行分配的关系

两套关系独立存在：

```text
employee_partnerships
录音归属员工 → 任务执行员工

followup_data_scopes
查看员工 → 可查看数据归属员工
```

任务生成时仍按 `employee_partnerships` 写入：

```text
recording_tasks.assigned_to
recording_tasks.assigned_by = 'partnership'
```

任务列表和详情权限按 `followup_data_scopes` 判断。即使某员工不是任务执行人，只要其在可见范围内，仍然可以查看该任务；反之，任务执行人不自动获得其他员工数据的查看权。

## 八、MVP 实施顺序

1. 新增 `followup_data_scopes` 表及唯一约束、索引；
2. 后端抽取统一的“当前员工可见目标员工”查询；
3. 将该过滤接入随访任务列表、详情、统计和导出接口；
4. 新增随访中心“数据查看范围”配置页面；
5. 配置接口校验租户和员工归属；
6. 用员工 A、B、C 的最小数据验证：
   - A 可查看 A、B、C；
   - B 只能查看 B；
   - B 无法通过详情接口访问 A 的任务。

## 九、明确不做的内容

- 不修改现有机构端 RBAC 表结构；
- 不复用 `employee_partnerships` 作为查看权限；
- 不引入部门、岗位、组织树继承；
- 不增加角色嵌套、通配符、条件表达式；
- 不把任务执行人自动视为数据查看人；
- 不在前端单独实现权限过滤。

## 十、最终结论

现有 RBAC 继续判断“能否使用随访功能”；新增 `followup_data_scopes` 专门判断“能查看哪些员工的数据”。两者职责清晰、数据结构最小，并且保留了未来扩展其他随访数据类型的空间。

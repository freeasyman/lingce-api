## 3. 代码审计结论

以下结论分为两部分：

1. 2026-08-16 审计时发现的历史问题；
2. 截至当前这轮重构已经完成的清理结果。

### 3.1 `store.go` 中确认存在的兼容逻辑

审计时原先确认存在如下兼容点：

1. `GetLatestSuiteTicket(...)`
   - 先按 `(mode, provider_app)` 查；
   - 旧代码曾存在按旧 `suite_id=providerApp` fallback。

2. `UpsertCorpInstall(...)`
   - 先按新唯一键 `(mode, provider_app, corp_id)` upsert；
   - 旧代码曾存在按旧 `corp_id` 主键语义 update fallback。

3. `GetCorpInstallByCorpID(...)`
   - 先按 `(mode, provider_app, corp_id)` 查；
   - 旧代码曾存在查不到再按旧 `corp_id` 查。

4. `UpsertUserBinding(...)`
   - 旧代码曾存在按旧 `(corp_id, wecom_user_id)` 兼容更新。

结论：

- 上述旧 fallback 在本轮重构中已经完成大部分删除；
- 当前 `GetLatestSuiteTicket(...)`、`UpsertCorpInstall(...)`、`GetCorpInstallByCorpID(...)` 已经收口为新结构写法；
- `GetAnyUserBinding(...)` 已删除；
- 当前还需要继续确认和收口的重点已经缩小到 `UpsertUserBinding(...)` 及其调用面。

### 3.2 `partner_service.go` 中确认存在的兼容逻辑

审计时原先确认存在如下兼容点：

1. `loginWithTemplateOAuth(...)`
   - 旧代码曾先查新绑定；
   - 查不到时调用 `GetAnyUserBinding(...)` 找旧绑定；
   - 找到后再写入一条 `Source=legacy_promoted` 的新绑定。

2. `resolveTemplateOAuthContext(...)`
   - 旧代码曾在缺少明确实例上下文时，遍历 `ListActiveCorpInstallsByMode(...)` 的全部 install 逐个试 code。

结论：

- 这两处旧兼容和猜测式识别逻辑已经在本轮重构中删除；
- 当前 `partner_standard_service.go` 与 `partner_template_service.go` 已分别持有各自的 OAuth、安装回调、企业回调实现；
- `partner_service.go` 仍作为共享基础层存在，但已不再承担旧数据提升或跨模式猜测式识别职责。

### 3.3 `partner_handler.go` / `handler.go` 审计结论

当前现状：

- 自建应用走老的 `/api/v1/wecom/*` 链路；
- 第三方模式走 `PartnerHandler`；
- `PartnerHandler` 内通过 `service.routePrefix` 区分不同第三方路由前缀。

结论：

- 路由层和服务层的拆分已经比审计时更进一步；
- 标准应用与代开发应用已经拆成两套独立 service；
- 另外，自建应用链路里曾混入的旧 `/api/v1/wecom/partner-enterprise/callback` 入口已删除，不再让自建模块承接第三方企业回调。

### 3.4 当前尚未完成的代码清理项

截至当前，仍需继续核查和处理的重点：

1. `UpsertUserBinding(...)` 是否还保留旧主键兼容写法；
2. 自建应用 `service.go` 中是否还残留不必要的第三方辅助能力；
3. 三模式回归验证尚未开始，当前只是完成了运行态清理与服务拆分，不代表链路已验收通过。

## 4. 运行态表审计结论

结合代码依赖，本次确认如下表的定位：

### 4.1 保留

- `tenant_wecom_apps`

原因：

- 自建应用基础配置表；
- 承载客户企业特有配置；
- 不属于临时运行态。

### 4.2 建议清空

- `wecom_user_bindings`
- `wecom_corp_installs`
- `wecom_suite_tickets`
- `wecom_directory_members`

原因：

1. `wecom_user_bindings`
   - 直接影响登录、绑定、消息发送；
   - 当前已混有旧结构。

2. `wecom_corp_installs`
   - 直接影响标准应用和代开发实例识别；
   - 当前已有 `tenant_id=0` 这类未闭环数据。

3. `wecom_suite_tickets`
   - 当前是历史混杂最严重的表；
   - 直接驱动第三方应用 token 获取。

4. `wecom_directory_members`
   - 只是通讯录同步缓存；
   - 可以在重测时重新同步生成；
   - 如果不清，可能继续误导绑定状态和匹配结果。

### 4.3 默认保留

- `wecom_event_logs`
- `wecom_message_logs`

原因：

- 它们更偏向审计与历史诊断；
- 不作为当前企业实例识别的主输入；
- 默认不纳入本次运行态清空。

补充：

- 如后续需要把企业微信测试环境做成完全无历史痕迹，也可以单独做日志归档或清理；
- 但这不属于本次基础 reset 范围。

## 5. 本次 SQL 脚本设计

本次新增 SQL 目录：

### 5.1 备份脚本

`01-wecom-runtime-backup.sql` 的作用：

- 在数据库内创建专用备份 schema：
  - `wecom_reset_backup_20260816`
- 将以下表完整备份到该 schema：
  - `wecom_user_bindings`
  - `wecom_corp_installs`
  - `wecom_suite_tickets`
  - `wecom_directory_members`
  - `wecom_event_logs`
  - `wecom_message_logs`
  - `tenant_wecom_apps`

说明：

- 即便本次不清理日志表，也一并备份，方便回看。

### 5.2 清理脚本

`02-wecom-runtime-reset.sql` 的作用：

- 仅清空以下运行态表：
  - `wecom_user_bindings`
  - `wecom_corp_installs`
  - `wecom_suite_tickets`
  - `wecom_directory_members`

明确不会动：

- `tenant_wecom_apps`
- `wecom_event_logs`
- `wecom_message_logs`

### 5.3 清理后检查脚本

`03-wecom-runtime-postcheck.sql` 的作用：

- 检查清空是否成功；
- 再次确认保留表是否还在；
- 输出三种模式重建前的基础计数。

## 7. 风险与约束

### 7.1 当前 `lingce-api` 工作区不是干净状态

当前工作区仍有未提交改动，且不全是本次企业微信三模式重构直接产生的内容。

因此：

- 本次先补文档和 SQL；
- 后续删兼容代码时必须逐文件复核，避免误覆盖现有修改。

### 7.2 本次 SQL 是“重建前置动作”，不是最终修复

清库本身不会自动让三种模式变干净。

它的意义是：

- 让后续删兼容代码时不再被旧运行态拖住；
- 让三种模式都能在零历史状态下验证自身是否真正成立。

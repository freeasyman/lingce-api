## 2. 本次代码审计范围

本次实际审计了以下代码文件：

- `internal/wecom/store.go`
- `internal/wecom/service.go`
- `internal/wecom/partner_service.go`
- `internal/wecom/handler.go`
- `internal/wecom/partner_handler.go`

重点核查内容：

1. 是否仍存在历史兼容读写逻辑；
2. 是否仍存在“猜旧数据”的 fallback；
3. 是否仍存在模式混用；
4. 运行态数据具体依赖哪些表；
5. 清理运行态后，哪些兼容代码可以直接删除。

## 3. 代码审计结论

### 3.1 `store.go` 中确认存在的兼容逻辑

确认存在如下兼容点：

1. `GetLatestSuiteTicket(...)`
   - 先按 `(mode, provider_app)` 查；
   - 查不到再按旧 `suite_id=providerApp` fallback。

2. `UpsertCorpInstall(...)`
   - 先按新唯一键 `(mode, provider_app, corp_id)` upsert；
   - 冲突后再按旧 `corp_id` 主键语义 update fallback。

3. `GetCorpInstallByCorpID(...)`
   - 先按 `(mode, provider_app, corp_id)` 查；
   - 查不到再按旧 `corp_id` 查。

4. `UpsertUserBinding(...)`
   - 先按新键更新；
   - 再按旧 `(corp_id, wecom_user_id)` 更新；
   - 最后再插入。

5. `GetAnyUserBinding(...)`
   - 完全绕开模式和 provider 维度；
   - 直接按 `(corp_id, wecom_user_id)` 取最近一条。

结论：

- 这 5 处都属于明确的“运行时历史兼容”；
- 在运行态清空后，应全部删除或收口为单一新结构写法。

### 3.2 `partner_service.go` 中确认存在的兼容逻辑

确认存在如下兼容点：

1. `loginWithTemplateOAuth(...)`
   - 先查新绑定；
   - 查不到时调用 `GetAnyUserBinding(...)` 找旧绑定；
   - 找到后再写入一条 `Source=legacy_promoted` 的新绑定。

2. `resolveTemplateOAuthContext(...)`
   - 若请求显式传了 `corp_id`，先按指定实例查；
   - 否则遍历 `ListActiveCorpInstallsByMode(...)` 的全部 install，逐个试 code。

结论：

- 这两处是当前代开发模式最典型的“脏兼容”和“猜测式识别”；
- 它们虽然让链路暂时跑通，但本质上破坏了模式边界；
- 在运行态清空后，必须彻底删除。

### 3.3 `partner_handler.go` / `handler.go` 审计结论

当前现状：

- 自建应用走老的 `/api/v1/wecom/*` 链路；
- 第三方模式走 `PartnerHandler`；
- `PartnerHandler` 内通过 `service.routePrefix` 区分不同第三方路由前缀。

结论：

- 路由层已经有模式拆分的雏形；
- 但服务层仍然没有彻底拆开；
- 下一步应继续把标准应用与代开发应用的 service/resolver 拆净，而不是只停留在 routePrefix 层。

## 4. 运行态表审计结论

结合代码依赖，本次确认如下表的定位：

### 4.1 保留

- `tenant_wecom_apps`

原因：

- 自建应用基础配置表；
- 承载客户企业特有配置；
- 不属于临时运行态。

### 4.2 建议清空

- `wecom_user_bindings`
- `wecom_corp_installs`
- `wecom_suite_tickets`
- `wecom_directory_members`

原因：

1. `wecom_user_bindings`
   - 直接影响登录、绑定、消息发送；
   - 当前已混有旧结构。

2. `wecom_corp_installs`
   - 直接影响标准应用和代开发实例识别；
   - 当前已有 `tenant_id=0` 这类未闭环数据。

3. `wecom_suite_tickets`
   - 当前是历史混杂最严重的表；
   - 直接驱动第三方应用 token 获取。

4. `wecom_directory_members`
   - 只是通讯录同步缓存；
   - 可以在重测时重新同步生成；
   - 如果不清，可能继续误导绑定状态和匹配结果。

### 4.3 默认保留

- `wecom_event_logs`
- `wecom_message_logs`

原因：

- 它们更偏向审计与历史诊断；
- 不作为当前企业实例识别的主输入；
- 默认不纳入本次运行态清空。

补充：

- 如后续需要把企业微信测试环境做成完全无历史痕迹，也可以单独做日志归档或清理；
- 但这不属于本次基础 reset 范围。

## 5. 本次 SQL 脚本设计

本次新增 SQL 目录：

- `scripts/sql/wecom_mode_reset/`

包含以下文件：

1. `README.md`
2. `01-wecom-runtime-backup.sql`
3. `02-wecom-runtime-reset.sql`
4. `03-wecom-runtime-postcheck.sql`

### 5.1 备份脚本

`01-wecom-runtime-backup.sql` 的作用：

- 在数据库内创建专用备份 schema：
  - `wecom_reset_backup_20260816`
- 将以下表完整备份到该 schema：
  - `wecom_user_bindings`
  - `wecom_corp_installs`
  - `wecom_suite_tickets`
  - `wecom_directory_members`
  - `wecom_event_logs`
  - `wecom_message_logs`
  - `tenant_wecom_apps`

说明：

- 即便本次不清理日志表，也一并备份，方便回看。

### 5.2 清理脚本

`02-wecom-runtime-reset.sql` 的作用：

- 仅清空以下运行态表：
  - `wecom_user_bindings`
  - `wecom_corp_installs`
  - `wecom_suite_tickets`
  - `wecom_directory_members`

明确不会动：

- `tenant_wecom_apps`
- `wecom_event_logs`
- `wecom_message_logs`

### 5.3 清理后检查脚本

`03-wecom-runtime-postcheck.sql` 的作用：

- 检查清空是否成功；
- 再次确认保留表是否还在；
- 输出三种模式重建前的基础计数。

## 6. 运行态清理后的直接开发动作

清理完成后，代码层应立即推进以下动作：

1. 删除 `GetAnyUserBinding(...)`
2. 删除 `legacy_promoted`
3. 删除 suite ticket fallback
4. 删除 corp install fallback
5. 删除 user binding 兼容式 upsert
6. 删除代开发 install 穷举试 code
7. 将第三方 service 继续向标准应用 / 代开发两条链路拆开

## 7. 风险与约束

### 7.1 当前 `lingce-api` 工作区不是干净状态

当前工作区仍有未提交改动，且不全是本次企业微信三模式重构直接产生的内容。

因此：

- 本次先补文档和 SQL；
- 后续删兼容代码时必须逐文件复核，避免误覆盖现有修改。

### 7.2 本次 SQL 是“重建前置动作”，不是最终修复

清库本身不会自动让三种模式变干净。

它的意义是：

- 让后续删兼容代码时不再被旧运行态拖住；
- 让三种模式都能在零历史状态下验证自身是否真正成立。

## 8. 本文结论

代码审计已经证明：

1. 当前兼容逻辑真实存在，而且集中在 `store.go` 与 `partner_service.go`；
2. 当前运行态表中，至少有 4 张表应作为本次 reset 的直接对象；
3. 本次最佳策略仍然是：
   - 保留 `tenant_wecom_apps`
   - 备份运行态
   - 清空运行态
   - 再删兼容代码
   - 然后三模式从零重测

# 企业微信三模式彻底重构方案

更新日期：2026-08-16

## 0. 本次方案的最终前提

本方案以最新决策为准，替代此前“迁移旧运行态数据并继续兼容运行”的方向。

本次已确认的前提如下：

1. 目前没有正式客户依赖现有企业微信链路。
2. 当前仅有测试企业在使用，允许从零重测三种模式。
3. 用户已同意：
   - 保留基础配置数据；
   - 清空企业微信运行态数据；
   - 删除运行时历史兼容；
   - 自建应用、标准应用、代开发应用三种模式全部重新验证。

因此，本次重构的正式策略不是“带着旧运行态继续修补”，而是：

- 保留基础配置；
- 清空运行态；
- 重建三种模式的干净链路；
- 让运行时代码只处理新结构。

## 1. 重构总目标

本次重构的目标是形成一套长期可维护、模式边界清晰、数据结构干净的正式方案：

1. 自建应用 `self_built`、标准应用 `partner_standard`、代开发应用 `partner_template` 三条链路彻底分开。
2. 删除所有运行时历史兼容和猜测式识别逻辑。
3. 清空旧的企业微信运行态数据，不再做旧运行态“边跑边迁”。
4. 登录、绑定、消息发送、许可检查，都围绕“企业微信应用实例”建模。
5. 三种模式的企业上下文来源必须清晰、稳定、可解释。
6. 后续新增客户时，不允许再依赖调试期补洞逻辑。

## 2. 三种模式的正式定义

### 2.1 自建应用 `self_built`

定义：

- 客户在自己的企业微信后台创建自建应用。
- 灵策后台保存该客户企业自己的：
  - `corp_id`
  - `agent_id`
  - `secret`

正式结论：

- 这是该模式的天然输入，不属于历史兼容。
- 本次要消除的是“客户手工拼入口 URL”这类低质量交互，不是否定这些参数本身。

### 2.2 标准应用 `partner_standard`

定义：

- 客户安装企业微信第三方标准应用。
- 企业实例由安装授权关系和服务商侧授权数据确定。

正式结论：

- 目标是不再要求客户手工提供企业参数。
- 但前提是实例识别、许可状态、员工绑定全部闭环。

### 2.3 代开发应用 `partner_template`

定义：

- 客户扫码安装代开发模板，生成该客户企业自己的应用实例。
- 运行时仍然需要企业实例上下文。

正式结论：

- 不能把“完全不需要任何企业实例上下文”写成当前既定目标。
- 但客户企业微信管理员不应被要求理解 `corp_id`、`agent_id`、回调拼接规则。
- 企业上下文的获取和归属应尽可能由服务端承接，而不是让客户管理员介入。

## 3. 当前系统的核心问题

### 3.1 三种模式虽然已有路由区分，但服务层仍有混用

问题：

- 第三方两种模式仍然存在共享 service 内通过 `mode` 分支切换的逻辑。
- 调试一个模式时，容易把补丁带进另一个模式。

### 3.2 运行时仍残留历史兼容逻辑

当前问题包括：

- 历史绑定提升为当前绑定；
- suite ticket 历史 fallback；
- corp install 历史 fallback；
- 用户绑定兼容写入；
- 代开发 code 穷举 install。

这些逻辑的存在说明：

- 现网运行仍在“猜旧数据”；
- 这与“彻底干净清晰的链路”目标冲突。

### 3.3 运行态数据已经严重混杂

生产审计结果已经证明：

- `wecom_user_bindings` 仍同时存在新旧结构；
- `wecom_suite_tickets` 大量记录仍为空 `mode/provider_app`；
- `wecom_corp_installs` 已出现实例归属不闭环的问题；
- 当前兼容代码不是多余，而是在兜这批脏运行态数据。

因此：

- 如果继续保留旧运行态并直接删兼容，风险高；
- 既然当前没有正式客户负担，最佳方案就是直接清空运行态并从零重建。

### 3.4 许可状态尚未成为实例级交付门禁

当前问题：

- 接口调用许可链路已经具备一部分能力；
- 但许可是否 ready，并没有作为“实例能否交付”的前置状态进行治理。

这会导致：

- 登录时才暴露许可问题；
- 测试时才发现库存、激活、续期问题；
- 运维无法一眼判断实例是否真正可用。

## 4. 本次重构后的正式目标状态

重构完成后，系统应满足：

1. 三种模式各自拥有独立 handler、service、resolver。
2. 企业微信运行态表只保存新结构数据，不再保留混用语义。
3. 每个企业微信实例都具有明确的：
   - 模式；
   - 企业归属；
   - 应用实例归属；
   - 许可状态；
   - 最近登录与绑定状态。
4. 运行时代码不再查询旧结构，不再做 fallback，不再“尝试一下旧链路”。
5. 三种模式都能从零完成：
   - 安装；
   - 登录；
   - 首次绑定；
   - 再次登录；
   - 消息发送；
   - 许可检查。

## 5. 数据策略

### 5.1 保留的数据

本次保留：

- `tenant_wecom_apps`

保留原因：

- 这是自建应用的基础配置表；
- 它承载客户企业特有配置，不属于运行态临时数据；
- 当前审计表明该表数据本身相对完整。

### 5.2 清空并重建的数据

本次原则上清空并重建以下企业微信运行态数据：

- `wecom_user_bindings`
- `wecom_corp_installs`
- `wecom_suite_tickets`

如代码中还有其他纯运行态企业微信表，也应纳入同一策略评估：

- 仅保留审计与业务必要日志；
- 清空会影响运行识别、绑定、授权、ticket 的旧状态。

### 5.3 不清理的数据

明确不动：

- 业务主数据；
- 员工主数据；
- 客户主数据；
- 跟进、提醒、录音、订单等业务数据。

## 6. 必删的运行时兼容逻辑

在运行态清空后，以下兼容逻辑应被正式删除：

1. `GetAnyUserBinding(...)`
2. `legacy_promoted`
3. `GetLatestSuiteTicket(...)` 中的历史 fallback
4. `GetCorpInstallByCorpID(...)` 中按旧结构查询 fallback
5. `UpsertCorpInstall(...)` 中按旧结构更新 fallback
6. `UpsertUserBinding(...)` 的兼容 update-then-insert
7. `resolveTemplateOAuthContext(...)` 中遍历所有 install 试 code

## 7. 三种模式的最终干净链路

### 7.1 自建应用

1. OPS 保存客户企业自己的 `corp_id`、`agent_id`、`secret`。
2. 员工从固定自建入口访问。
3. 后端按租户解析出唯一自建实例。
4. 发起 OAuth。
5. 拉取企业微信身份。
6. 完成首次绑定或直接登录。

### 7.2 标准应用

1. 客户安装标准应用。
2. 回调写入标准应用实例。
3. 员工从固定标准应用入口访问。
4. 后端按标准应用实例解析企业上下文。
5. 拉取企业微信身份。
6. 完成首次绑定或直接登录。

### 7.3 代开发应用

1. 客户扫码安装代开发模板并完成企业应用创建。
2. 企业实例写入代开发 install 记录。
3. 员工从固定代开发入口访问。
4. 后端按代开发实例解析企业上下文。
5. 拉取企业微信身份。
6. 完成首次绑定或直接登录。

特别要求：

- 不得再让客户企业微信管理员提供系统内部识别所需的技术参数；
- 代开发上下文的最终识别必须由服务端链路承接；
- 即使暂时仍需某些企业实例参数，也必须由服务端保存和解析，不得依赖客户理解技术字段。

## 8. 关于接口调用许可的正式结论

对最初第 2 个问题，正式结论如下：

1. 当前许可链路不是偶然打通。
2. 但它也还不是“完全成熟、零人工、零库存依赖”的最终交付链路。
3. 本次重构后，许可状态必须成为实例级状态，而不是登录期临时报错。

建议实例许可状态：

- `unknown`
- `not_required`
- `needs_activate`
- `ready`
- `inventory_missing`
- `activation_failed`

交付规则：

- 只有 `license_status=ready` 的实例，才允许进入客户测试或正式交付阶段。

## 9. 关于客户企业管理员动作的正式结论

对代开发模式，必须严格收敛客户企业管理员动作。

正式目标：

- 客户企业管理员只做企业微信侧必要动作；
- 不承担灵策内部技术参数识别责任；
- 不需要理解后台数据模型；
- 不需要手工查找系统内部使用的企业上下文。

理想最小动作应收敛为：

1. 扫码安装应用；
2. 配置可见范围；
3. 如企业微信平台确有要求，再填写服务商提供的固定开发信息。

而不是：

- 去理解 `corp_id`、`agent_id`、`provider_app`；
- 去判断该填哪条回调 URL；
- 去替我们完成企业归属匹配。

## 10. 上线原则

本次重构必须遵守以下顺序：

1. 先更新方案与执行文档；
2. 先做代码审计；
3. 再清空运行态；
4. 再删兼容逻辑；
5. 再按三种模式逐个从零重测；
6. 验证通过后，再考虑开放给正式客户。

## 11. 本文结论

本次重构的本质不是“继续补丁”，而是：

- 承认三种模式各自真实存在；
- 保留必要基础配置；
- 彻底丢弃脏运行态；
- 删除历史兼容；
- 把三种模式都重建为可解释、可测试、可维护的正式链路。

对最初三个问题，本文最终回答如下：

1. 是否仍残留调试期兼容代码：
   - 是，而且当前生产运行态数据真实依赖它们。
   - 正确处理方式不是继续容忍，而是清空运行态后删除它们。
2. 接口调用许可是否只是偶然打通：
   - 不是偶然。
   - 但还必须前置为实例状态，才算成熟。
3. 新客户是否必须提供 `corp_id` / `agent_id`：
   - 自建应用基础配置天然需要；
   - 标准应用目标是不需要客户手工提供；
   - 代开发模式的目标也应是客户管理员不承担这件事，服务端自己承接实例识别。

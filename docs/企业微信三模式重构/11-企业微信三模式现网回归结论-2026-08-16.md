# 企业微信三模式现网回归结论

日期：2026-08-16

## 1. 当前结论

截至 2026-08-16 晚间，三模式现网状态已经可以明确分成三类：

1. 自建应用 `self_built`
   - 已真实跑通
   - 真实员工从企业微信进入后可完成自动绑定与二次自动登录

2. 标准应用 `partner_standard`
   - 当前未真正接入现网回调
   - 代码入口已注册，但企业微信没有向 `/api/v1/wecom/partner-standard/callback` 发送真实 POST 回调
   - 因此现网没有 `partner_standard` 的 suite ticket，也没有任何标准应用企业实例

3. 代开发应用 `partner_template`
   - 现网正在持续收到模板侧 `suite_ticket`
   - 但当前没有任何企业实例真正落入 `wecom_corp_installs`
   - 说明模板级回调已通，企业实例级闭环尚未形成

### 2.2 实际页面行为

2. 第二次进入时，页面表现为“闪一下企业微信登录，然后进入首页”

结论：

- `self_built` 已达到“真实可用”
- 当前三模式里，只有自建应用已完成现网闭环

## 3. 标准应用现网验证结果

### 3.1 日志事实

从 2026-08-15 至 2026-08-16 的生产日志看：

1. 没有任何真实的 `POST /api/v1/wecom/partner-standard/callback`
2. 只有人工探测产生的：
   - `GET /api/v1/wecom/partner-standard/callback`
   - 状态 `400`
3. 访问：
   - `GET /api/v1/wecom/partner-standard/install-url`
   - 返回 `500`

### 3.2 数据事实

生产库查询结果：

1. `wecom_suite_tickets`
   - 没有任何 `partner_standard` 记录
2. `wecom_corp_installs`
   - 没有任何 `partner_standard` 实例

### 3.3 结论

标准应用当前的真实阻塞不是代码崩溃，而是：

1. 企业微信标准应用后台并没有把真实 suite 回调打到当前 `partner-standard/callback`
2. 因为没有 suite ticket，`install-url` 无法工作

所以标准应用当前不能继续靠 API 侧打补丁推进，必须先确认企业微信标准应用后台回调配置是否已经切到：

- `https://wecom.khgl.xyz/api/v1/wecom/partner-standard/callback`

## 4. 代开发应用现网验证结果

### 4.1 日志事实

从 2026-08-15 至 2026-08-16 的生产日志看：

1. 持续存在真实的：
   - `POST /api/v1/wecom/partner-template/callback`
   - 状态长期为 `200`
2. 2026-08-16 晚间最近几次仍持续收到该回调

### 4.2 suite ticket 事实

生产库 `wecom_suite_tickets` 当前只有 1 组有效记录：

- `mode=partner_template`
- `provider_app=dka3fffb6a3be8c955`
- `suite_id=dka3fffb6a3be8c955`
- 最近时间：`2026-08-16 17:54:14`

这说明：

- 模板侧回调配置是真实生效的
- 现网模板仍在向灵策 API 稳定推送 `suite_ticket`

### 4.3 event log 事实

最近两天 `wecom_event_logs` 中，绝大多数都是：

- `info_type=suite_ticket`

此外只看到了少量：

- `cancel_auth`
- `enter_agent`

说明：

- 企业实例回调里至少存在一类真实事件不是 `InfoType`，而是 `Event`
- 例如：
  - `MsgType=event`
  - `Event=enter_agent`
- 这一类事件此前会被记成空 `info_type`
- 本轮代码已经补齐为：
  - 优先记录 `InfoType`
  - 没有 `InfoType` 时记录 `Event`

### 4.4 历史授权事实

虽然当前 `wecom_corp_installs` 是空表，但生产日志与历史事件已经证明：

1. 2026-08-15 存在多次真实 `create_auth`
2. 对应日志明确出现过多次：
   - `wecom third-party corp install synced`
3. 当时已经真实写出过企业实例，且 `agent_id` 随发布过程多次变化：
   - `1000043`
   - `1000044`
   - `1000045`
   - `1000046`
   - `1000047`

这说明：

- 代开发模式不是“从未跑通”
- `create_auth -> syncCorpInstall -> wecom_corp_installs` 这条链路历史上已经真实成功过
- 当前空表更接近“运行态清理后，尚未重新形成 active install”，而不是“create_auth 永远打不通”

### 4.5 install 事实

生产库 `wecom_corp_installs` 当前为：

- `0 rows`

结合历史日志，这里的正确解读应当是：

1. 当前时点没有 active install
2. 但不代表 install 同步逻辑从未成功
3. 当前更可能是：
   - 运行态被清理后尚未重建
   - 或最近一次企业状态变化已经取消了旧实例
   - 或还没有新的 `create_auth` 重新写入 active install

### 4.6 `change_auth` 事实

历史日志还证明另一点：

1. `change_auth` 事件大多只带：
   - `AuthCorpId`
2. 并不稳定携带：
   - `AuthCode`

因此：

- `change_auth` 不应被视为“必然可重建 install 的事件”
- 当前代码对无 `auth_code` 的 `change_auth` 跳过同步，是合理行为
- 真正能创建/重建 install 的关键事件仍然是 `create_auth`

### 4.7 结论

代开发模式当前的问题不是：

1. 模板回调没通
2. suite ticket 不存在

而是：

1. 当前时点没有 active install
2. 需要重新形成一次有效的 `create_auth`
3. 企业实例回调事件虽然在进来，但它本身并不能替代 `create_auth` 写出 `permanent_code`
4. 因此员工侧登录仍缺失可用的企业实例上下文

## 5. 代码层已完成的收口

本轮已经完成 1 个必要收口：

1. `partner_template` 不再暴露错误的安装入口语义
   - 代开发模式不应继续走：
     - `/api/v1/wecom/partner-template/install-url`
     - `/api/v1/wecom/partner-template/install`
     - `/api/v1/wecom/partner-template/install/callback`
   - 这些路由已从能力模型上收口为“标准应用专属”

这次收口的目的，是防止后续测试再次被错误的“install-url”链路带偏。

## 6. 下一步动作

### 6.1 标准应用

下一步不是改代码，而是先核对企业微信标准应用后台配置：

- 数据回调 URL 是否已切到：
  - `https://wecom.khgl.xyz/api/v1/wecom/partner-standard/callback`

只有这一步成立，`partner_standard` 才会产生真实 suite ticket。

### 6.2 代开发应用

下一步应继续沿真实模板链路排查：

1. 客户企业完成模板安装/发布时，企业微信到底发了哪些事件
2. 为什么最近只有 `suite_ticket`，没有形成稳定 install
3. 是否需要针对代开发模式补一条“企业实例创建后主动拉取并落库”的服务端同步动作

### 6.3 自建应用

当前无需继续修复，自建模式已经完成现网验证。

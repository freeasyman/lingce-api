# 企业微信三模式生产审计结果

审计日期：2026-08-16  
审计环境：生产数据库 `lingce_prod`  
审计范围：

- `wecom_user_bindings`
- `wecom_corp_installs`
- `wecom_suite_tickets`
- `tenant_wecom_apps`
- 上述表之间的跨表一致性

## 1. 审计结论摘要

本次生产审计的核心结论如下：

1. **第 1 个问题成立**
   - 生产环境中仍然残留明显的历史兼容数据结构
   - 运行时代码中保留 fallback 不是多余担心，而是当前数据真实需要它

2. **第 2 个问题的结论更清晰了**
   - 接口调用许可链路不是“偶然碰巧打通”
   - 但当前生产数据结构里，实例层还没有把许可和租户归属闭环收口
   - 仍然需要把许可状态上升为实例状态来治理

3. **第 3 个问题也更清晰了**
   - 三种模式的企业上下文来源目前确实不统一
   - 代开发模式虽然已经能登录，但实例记录里的 `tenant_id` 仍是 `0`
   - 这说明当前链路虽然“跑通”，但还没有达到“完全干净清晰”

4. **本次审计已经支持新的执行决策**
   - 当前生产运行态数据混杂明显
   - 既然当前没有正式客户负担，继续做旧运行态迁移的收益已经低于直接清理重建
   - 因此，后续动作应切换为：
     - 保留 `tenant_wecom_apps`
     - 清空企业微信运行态
     - 删除兼容代码
     - 三种模式从零重测

## 7. 额外发现：线上真实表结构与代码假设不完全一致

本次审计还发现一个重要事实：

- `wecom_corp_installs` 生产表没有 `id` 列
- 当前唯一索引与主键并存：
  - 新唯一索引：`(mode, provider_app, corp_id)`
  - 旧主键：`corp_id`

这说明：

1. 表结构已经部分迁到新模型
2. 但旧主键语义还没有完全移除

这也是为什么：

- 当前 `UpsertCorpInstall(...)` 仍保留兼容逻辑
- 以及为什么删除 install fallback 前必须先做正式迁移

## 8. 对最初三个问题的正式回答

### 8.1 第 1 个问题：是否还残留调试期兼容代码

审计结论：

- **是，仍然残留，而且生产数据真实需要它们**

最明显证据：

- `wecom_user_bindings` 中 `2/3` 记录仍是空 `mode/provider_app`
- `wecom_suite_tickets` 中 `8296/8598` 记录仍是空 `mode/provider_app`
- `wecom_corp_installs` 仍保留旧 `corp_id` 主键语义

结论：

- 当前不能直接删兼容代码
- 必须先迁数据

### 8.2 第 2 个问题：接口调用许可是否只是偶然打通

审计结论：

- **不是偶然**
- 但当前实例层数据结构还没有把“许可状态 + 实例归属 + 可交付状态”收口为一个正式闭环

最明显证据：

- 唯一代开发实例 `tenant_id=0`
- 自建应用配置 `config_confirmed` 仍全部为 false

结论：

- 接口调用许可不是“碰巧打通”
- 但确实还没有被产品化到实例交付状态里

### 8.3 第 3 个问题：新客户应用主页是否必须带 `corp_id` / `agent_id`

审计结论：

- 从当前生产数据看，三种模式仍然不是同一种上下文模型
- 特别是代开发模式，实例归属还没有正式闭环到租户

这说明：

- 当前不能把“代开发应用完全不需要企业上下文”写成正式结论
- 当前正确方向仍然是：
  - 保留必要企业实例上下文
  - 删除脏兼容
  - 删除猜测式识别

## 9. 当前最重要的阻塞项

按优先级排序：

1. `wecom_suite_tickets` 绝大多数仍是旧结构
2. `wecom_user_bindings` 仍有旧结构绑定
3. `wecom_corp_installs` 的代开发实例 `tenant_id=0`
4. `wecom_corp_installs` 仍保留旧 `corp_id` 主键语义
5. `tenant_wecom_apps.config_confirmed` 还没有形成运营闭环

## 10. 下一步建议

基于本次生产审计，并结合当前“可从零重测”的业务条件，我建议下一步改为以下顺序：

1. 写清理与重建方案
2. 导出运行态备份
3. 清空：
   - `wecom_user_bindings`
   - `wecom_corp_installs`
   - `wecom_suite_tickets`
4. 删除 runtime fallback
5. 三种模式从零重新安装、登录、绑定、发消息
6. 按新链路重新生成干净运行态

## 11. 本文结论

这次生产审计的结论非常明确：

- 现在的系统已经不是“完全没打通”；
- 但当前运行态数据混杂严重；
- 既然没有正式客户负担，最佳路径已经不是迁移旧运行态，而是清理后重建。

所以，下一阶段应进入：

- **运行态清理设计**
- **兼容代码删除**
- **三模式从零验证**
- **许可状态产品化**

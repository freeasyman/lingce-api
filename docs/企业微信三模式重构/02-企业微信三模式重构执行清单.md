# 企业微信三模式重构执行清单

更新日期：2026-08-16

## 0. 执行前提

本清单承接《01-企业微信三模式彻底重构方案》。

执行前提已经明确：

1. 当前没有正式客户依赖现有企业微信运行态。
2. 允许放弃旧运行态数据，不做迁移延续。
3. 保留 `tenant_wecom_apps`。
4. 企业微信三种模式全部从零验证。

因此，本清单不再以“迁移旧运行态并继续兼容”为目标，而是以“清空运行态、删除兼容、重建链路”为目标。

## 1. 数据处理清单

### 1.1 保留表

保留：

- `tenant_wecom_apps`

要求：

- 不删除；
- 不清空；
- 继续作为自建应用基础配置来源。

### 1.2 清空表

首批明确清空：

- `wecom_user_bindings`
- `wecom_corp_installs`
- `wecom_suite_tickets`

要求：

- 清空前先导出备份；
- 仅做运行态清空，不做业务主数据清理；
- 清空动作必须单独形成 SQL 和回滚说明。

### 1.3 待审计后决定是否清空的表

需要继续审查是否属于纯运行态的表或记录：

- 企业微信登录临时状态表
- 企业微信安装事件缓存表
- 仅用于授权/票据/绑定的历史记录表

原则：

- 只要它会影响当前运行识别，就不能带旧值继续跑；
- 只要它只是审计日志，可保留。

## 2. 必删代码清单

### 2.1 绑定兼容

必须删除：

- `internal/wecom/store.go`
  - `GetAnyUserBinding(...)`
- `internal/wecom/partner_service.go`
  - `legacy_promoted`
  - 历史绑定提升逻辑

### 2.2 suite ticket 兼容

必须删除：

- `internal/wecom/store.go`
  - `GetLatestSuiteTicket(...)` 中历史 fallback

### 2.3 corp install 兼容

必须删除：

- `internal/wecom/store.go`
  - `GetCorpInstallByCorpID(...)` 中旧结构 fallback
  - `UpsertCorpInstall(...)` 中旧结构 update fallback

### 2.4 用户绑定写入兼容

必须删除：

- `internal/wecom/store.go`
  - `UpsertUserBinding(...)` 兼容式 update-then-insert

目标写法：

- 只保留单一新结构 upsert。

### 2.5 代开发 code 穷举识别

必须删除：

- `internal/wecom/partner_service.go`
  - `resolveTemplateOAuthContext(...)` 中遍历 install 试 code 的逻辑

### 2.6 第三方模式混合 service

必须拆除：

- `internal/wecom/partner_service.go`
- `internal/wecom/partner_handler.go`

要求：

- 不再允许一个 service 内用 `mode` 分支承接标准应用和代开发应用。

## 3. API 重构清单

### 3.1 拆分 service

新增或收敛为独立 service：

- `self_built_service`
- `partner_standard_service`
- `partner_template_service`

每个 service 独立负责：

1. `PrepareOAuth`
2. `LoginWithOAuth`
3. `BindEmployee`
4. `ResolveEmployeeBinding`
5. `ResolveCorpToken`
6. `BuildEntryContext`

### 3.2 拆分 handler

新增或收敛为独立 handler：

- `self_built_handler`
- `partner_standard_handler`
- `partner_template_handler`

### 3.3 拆分 resolver

新增或收敛为独立 resolver：

- `self_built_resolver`
- `partner_standard_resolver`
- `partner_template_resolver`

要求：

- 每次登录前必须先解析出唯一企业实例；
- 不允许使用“遍历所有 install / 试一下”的识别方式。

### 3.4 `oauth/prepare` 规范化

三种模式都必须具备：

- `POST /api/v1/wecom/{mode}/oauth/prepare`

职责：

- 由后端返回完整 OAuth 地址；
- 前端不再自己拼装企业参数；
- 企业上下文由服务端统一解析。

### 3.5 许可状态前置

必须补齐实例级许可状态能力：

1. `CheckInstanceLicense`
2. `EnsureInstanceLicense`
3. `MarkInstanceLicenseStatus`

要求：

- 许可失败要在实例页和诊断页可见；
- 不允许继续等到客户登录时才暴露。

## 4. H5 重构清单

### 4.1 保留三条登录路由

保留：

- `/login/self-built`
- `/login/partner-standard`
- `/login/partner-template`

说明：

- H5 只区分模式；
- 不再承担脏上下文拼接责任。

### 4.2 前端不再自行作为企业识别主来源

删除前端对下列参数的主依赖：

- `corp_id`
- `agent_id`
- `suite_id`
- `template_id`

说明：

- 不是说这些值永远不出现；
- 而是前端不能再靠它们自己做主识别、主绑定、主推断。

### 4.3 首次绑定只信后端上下文

要求：

- 首次绑定所需的企业上下文、企业微信身份、模式信息，全部由后端返回；
- 前端不得再从 URL 兜底拼装核心身份。

## 5. OPS / 后台清单

### 5.1 新增企业微信实例总览

页面目标：

- 以企业实例为中心查看接入状态。

建议字段：

- 租户
- 模式
- 企业名称
- corp_id
- agent_id
- 许可状态
- 当前绑定状态
- 最近登录结果
- 最近同步结果
- 最近消息投递结果

### 5.2 自建应用配置页

继续仅保留自建应用需要的基础字段：

- `corp_id`
- `agent_id`
- `secret`

### 5.3 标准应用 / 代开发应用改为实例状态页

不要再做成“人工填大量字段”的误导式页面。

展示重点应收敛为：

- 是否安装
- 是否收到回调
- 是否识别实例
- 许可是否 ready
- 可见范围是否确认
- 最近登录是否成功

### 5.4 登录诊断页

必须可按实例查看最近失败原因。

## 6. 实施顺序

必须按以下顺序执行：

1. 完成方案与执行文档
2. 代码审计并列出实际待删函数
3. 产出运行态清空 SQL 与备份方案
4. 清空运行态
5. 拆 service / handler / resolver
6. 删除 runtime fallback
7. 收口 H5 登录链路
8. 补齐 OPS 实例状态页与诊断能力
9. 自建应用从零验证
10. 标准应用从零验证
11. 代开发应用从零验证

## 7. 验收标准

重构完成后，必须同时满足：

1. 代码中不再存在：
   - `legacy_promoted`
   - `GetAnyUserBinding`
   - suite ticket 历史 fallback
   - corp install 历史 fallback
   - 代开发 code 穷举 install
2. 运行态表已由新链路重新写入，不再依赖旧数据。
3. 三种模式各自的 handler、service、resolver 独立。
4. 登录链路不再依赖历史兼容数据。
5. 许可状态成为实例级前置状态。
6. 代开发模式不再要求客户管理员承担技术参数识别责任。
7. 三种模式都能从零完成安装、登录、绑定、消息发送和再次登录。

## 8. 本文结论

本次执行不是“修旧系统”，而是：

- 保基础配置；
- 清运行态；
- 删兼容；
- 重建三种模式正式链路；
- 再从零验收。

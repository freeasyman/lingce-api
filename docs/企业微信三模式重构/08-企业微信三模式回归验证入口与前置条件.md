# 企业微信三模式回归验证入口与前置条件

更新日期：2026-08-16

## 1. 目的

本文用于在代码清理阶段之后，给三模式从零回归验证提供统一入口清单。

目标是避免再次出现：

1. 不清楚该打哪个接口；
2. 不清楚每个模式依赖哪些配置；
3. 不清楚登录、安装、回调、绑定各自落在哪条链路。

## 2. 当前代码状态结论

截至当前：

1. 自建应用链路保留在 `/api/v1/wecom/*`
2. 标准应用链路固定在 `/api/v1/wecom/partner-standard/*`
3. 代开发应用链路固定在 `/api/v1/wecom/partner-template/*`
4. 自建链路中旧的 `partner-enterprise` 回调残留已删除
5. 标准应用与代开发应用已拆为独立 service

这意味着：

- 三种模式已经具备独立的后端入口；
- 下一步重点不再是删 fallback，而是逐条验证入口是否能在零运行态下独立成立。

## 3. 三模式后端入口

### 3.1 自建应用 `self_built`

回调与登录入口：

- `GET /api/v1/wecom/callback`
- `POST /api/v1/wecom/callback`
- `POST /api/v1/wecom/oauth/login`
- `POST /api/v1/wecom/bind`

说明：

- 企业微信自建应用消息回调走 `/api/v1/wecom/callback`
- 员工企业微信 OAuth 登录走 `/api/v1/wecom/oauth/login`
- 首次绑定走 `/api/v1/wecom/bind`

### 3.2 标准应用 `partner_standard`

入口：

- `GET /api/v1/wecom/partner-standard/callback`
- `POST /api/v1/wecom/partner-standard/callback`
- `GET /api/v1/wecom/partner-standard/enterprise-callback`
- `POST /api/v1/wecom/partner-standard/enterprise-callback`
- `GET /api/v1/wecom/partner-standard/install-url`
- `GET /api/v1/wecom/partner-standard/install`
- `GET /api/v1/wecom/partner-standard/install/callback`
- `POST /api/v1/wecom/partner-standard/oauth/login`
- `POST /api/v1/wecom/partner-standard/bind`

说明：

- `callback`：服务商侧 suite 回调
- `enterprise-callback`：企业实例回调
- `install-url/install`：获取或跳转安装链接
- `install/callback`：客户授权安装后的服务端回调
- `oauth/login`：员工从企业微信进入 H5 后的登录接口

### 3.3 代开发应用 `partner_template`

入口：

- `GET /api/v1/wecom/partner-template/callback`
- `POST /api/v1/wecom/partner-template/callback`
- `GET /api/v1/wecom/partner-template/enterprise-callback`
- `POST /api/v1/wecom/partner-template/enterprise-callback`
- `GET /api/v1/wecom/partner-template/install-url`
- `GET /api/v1/wecom/partner-template/install`
- `GET /api/v1/wecom/partner-template/install/callback`
- `POST /api/v1/wecom/partner-template/oauth/login`
- `POST /api/v1/wecom/partner-template/bind`

说明：

- 结构与标准应用一致；
- 但 token 获取、员工信息获取、企业实例语义都属于代开发模式自己的链路。

## 4. 关键请求结构

### 4.1 OAuth 登录请求

接口：

- `POST /api/v1/wecom/oauth/login`
- `POST /api/v1/wecom/partner-standard/oauth/login`
- `POST /api/v1/wecom/partner-template/oauth/login`

请求体：

```json
{
  "code": "企业微信OAuth返回的code",
  "corp_id": "可选；当前部分模式仍会显式传入"
}
```

说明：

- `code` 必填；
- `corp_id` 当前仍保留字段，但长期目标是不让前端承担主识别责任。

### 4.2 首次绑定请求

接口：

- `POST /api/v1/wecom/bind`
- `POST /api/v1/wecom/partner-standard/bind`
- `POST /api/v1/wecom/partner-template/bind`

请求体：

```json
{
  "corp_id": "企业ID",
  "wecom_user_id": "企业微信用户ID"
}
```

说明：

- 该接口依赖当前登录态中的员工身份；
- `employee_id` 不由前端传，而由 JWT 用户上下文决定。

### 4.3 安装链接返回

接口：

- `GET /api/v1/wecom/partner-standard/install-url`
- `GET /api/v1/wecom/partner-template/install-url`

返回结构：

```json
{
  "install_url": "安装链接",
  "redirect_uri": "安装回调地址",
  "state": "状态串",
  "auth_type": 1
}
```

支持查询参数：

- `tenant_id`
- `state`
- `auth_type`

说明：

- 当前已支持把 `tenant_id` 编进 `state`
- 这会影响安装完成后的租户归属

## 5. 配置前置条件

### 5.1 自建应用

依赖：

1. `tenant_wecom_apps` 中已有租户配置
2. 配置内至少包含：
   - `corp_id`
   - `agent_id`
   - `secret`
3. 企业微信后台已完成：
   - 应用主页
   - 可信域名
   - JSAPI 域名
   - 企业可信 IP

### 5.2 标准应用

依赖：

1. secrets 中配置：
   - `wecom.partner_standard.app_id`
   - `wecom.partner_standard.app_secret`
   - `wecom.partner_standard.token`
   - `wecom.partner_standard.encoding_aes_key`
   - `wecom.partner_standard.callback_base_url`
2. 服务商侧标准应用已安装授权
3. 已收到 suite ticket
4. 安装后应生成 `wecom_corp_installs` 实例记录

### 5.3 代开发应用

依赖：

1. secrets 中配置：
   - `wecom.partner_template.app_id`
   - `wecom.partner_template.app_secret`
   - `wecom.partner_template.token`
   - `wecom.partner_template.encoding_aes_key`
   - `wecom.partner_template.callback_base_url`
2. 客户企业已扫码安装代开发模板
3. 服务商侧回调已收到 suite ticket
4. 客户企业实例回调已可达
5. 安装后应生成 `wecom_corp_installs` 实例记录

## 6. 每种模式的最小验证闭环

### 6.1 自建应用

1. 配置存在
2. 回调可验证
3. 员工进入 H5
4. OAuth 登录成功
5. 首次绑定成功
6. 再次进入自动登录成功
7. 发送提醒成功

### 6.2 标准应用

1. `callback` 验证通过
2. `install-url` 可生成安装链接
3. 客户安装完成
4. `install/callback` 成功写入实例
5. `enterprise-callback` 验证通过
6. 员工 OAuth 登录成功
7. 首次绑定成功
8. 再次进入自动登录成功
9. 发送提醒成功

### 6.3 代开发应用

1. `callback` 验证通过
2. 模板安装成功
3. 企业应用创建成功
4. `enterprise-callback` 验证通过
5. 实例写入成功
6. 员工 OAuth 登录成功
7. 首次绑定成功
8. 再次进入自动登录成功
9. 发送提醒成功

## 7. 当前剩余风险

当前还未进入真实回归验证，所以以下问题仍未被证明已经消失：

1. H5 页面是否完全按模式分流
2. 前端是否还残留旧 URL 兜底逻辑
3. 标准应用和代开发应用在真实企业微信环境中的 OAuth 参数是否完全一致
4. 企业实例回调是否在所有模式下都能用当前配置稳定验证

## 8. 下一步执行顺序

建议严格按以下顺序执行：

1. 自建应用从零验证
2. 标准应用从零验证
3. 代开发应用从零验证

原因：

- 自建应用依赖最少；
- 标准应用和代开发应用共享服务商侧概念，但企业实例语义不同；
- 先把最简单链路跑通，能更快区分“基础 OAuth 问题”和“第三方实例问题”。

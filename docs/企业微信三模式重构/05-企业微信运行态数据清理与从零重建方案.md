# 企业微信运行态数据清理与从零重建方案

更新日期：2026-08-16

## 1. 目标

本方案用于明确：

1. 哪些数据保留；
2. 哪些数据清空；
3. 清空后如何重建；
4. 清空后哪些兼容代码可以直接删除；
5. 三种模式如何重新验证。

## 2. 保留范围

明确保留：

- `tenant_wecom_apps`

保留原因：

- 这是自建应用基础配置；
- 不属于临时运行态；
- 后续自建模式从零验证仍需使用。

## 3. 清理范围

明确清理：

- `wecom_user_bindings`
- `wecom_corp_installs`
- `wecom_suite_tickets`

清理原则：

1. 清空前先导出只读备份。
2. 清空后不保留任何旧绑定、旧 install、旧 ticket。
3. 之后所有记录都必须由重构后的正式链路重新产生。

## 4. 为什么不做旧运行态迁移

本次不建议做旧运行态迁移，原因如下：

1. 当前无正式客户负担。
2. 生产审计已证明旧运行态混杂严重。
3. 继续迁移旧运行态，只会把历史歧义继续带入新代码。
4. 从零重建成本更低，验证更可靠。

## 5. 清理后的直接收益

清空运行态后，可以直接消除以下不确定性：

1. 旧绑定误命中新登录；
2. 旧 ticket 被 fallback 命中；
3. 旧 corp install 误导企业归属；
4. 新旧模式共享数据导致的假成功；
5. 调试期“临时兼容”继续污染正式链路。

## 6. 清理后可直接删除的兼容代码

在运行态清空后，以下兼容逻辑不再有保留理由：

1. `GetAnyUserBinding(...)`
2. `legacy_promoted`
3. `GetLatestSuiteTicket(...)` 历史 fallback
4. `GetCorpInstallByCorpID(...)` 历史 fallback
5. `UpsertCorpInstall(...)` 旧结构 update fallback
6. `UpsertUserBinding(...)` 兼容写法
7. `resolveTemplateOAuthContext(...)` install 穷举试 code

## 7. 从零重建顺序

建议按以下顺序重建：

### 7.1 自建应用

1. 使用已保留的 `tenant_wecom_apps`。
2. 重新完成员工首次登录。
3. 重新产生绑定记录。
4. 验证消息发送。

### 7.2 标准应用

1. 重新安装标准应用。
2. 重新接收授权回调。
3. 重新产生 install、ticket、binding。
4. 验证许可状态、登录、发送消息。

### 7.3 代开发应用

1. 重新扫码安装代开发模板。
2. 重新生成企业实例。
3. 重新接收企业回调。
4. 重新产生 install、ticket、binding。
5. 验证登录、绑定、消息发送、再次登录。

## 8. 清理后的验收判断

若清理后任一模式仍需：

- 依赖旧绑定；
- 依赖旧 install；
- 依赖旧 ticket；
- 依赖 fallback；
- 依赖“多试几次某条链路”；

则说明该模式尚未真正重构完成。

## 9. 执行要求

1. 清理 SQL 必须单独保存。
2. 清理前备份必须单独保存。
3. 清理后首轮验证必须按模式逐一记录。
4. 每个模式都要留下“首次安装 / 首次登录 / 首次绑定 / 再次登录 / 发送消息”的验证结论。

## 10. 本文结论

当前最佳策略不是迁移旧运行态，而是：

- 留基础配置；
- 清企业微信运行态；
- 让三种模式全部重新产出干净数据；
- 以此为基础删除所有历史兼容。

# 企业微信三模式清理后验证计划

更新日期：2026-08-16

## 1. 目标

本计划用于约束运行态清理后的验证顺序和验收口径，避免再次进入边调边补的状态。

## 2. 验证总原则

1. 三种模式逐个验证，不并行混测。
2. 每个模式必须完成完整闭环后，才进入下一个模式。
3. 每一步都要记录：
   - 输入条件
   - 操作动作
   - 产生的数据
   - 页面结果
   - 日志结果

## 3. 自建应用验证项

必须验证：

1. OPS 自建配置可读取。
2. 员工首次从企业微信进入。
3. 首次绑定成功。
4. 再次进入直接登录成功。
5. 通讯录同步成功。
6. 提醒消息发送成功。

## 4. 标准应用验证项

必须验证：

1. 客户安装标准应用成功。
2. 授权回调成功落库。
3. 许可状态为 `ready`。
4. 员工首次进入成功。
5. 首次绑定成功。
6. 再次进入直接登录成功。
7. 提醒消息发送成功。

## 5. 代开发应用验证项

必须验证：

1. 客户扫码安装模板成功。
2. 企业应用创建成功。
3. 企业回调成功。
4. 实例归属成功。
5. 员工首次进入成功。
6. 首次绑定成功。
7. 再次进入直接登录成功。
8. 提醒消息发送成功。

特别要求：

- 重点验证客户企业管理员是否只需要做最小动作；
- 不允许把技术识别责任转嫁给客户企业管理员。

## 6. 验收失败判定

若出现以下任一情况，视为该模式未通过：

1. 需要手动修数据库才能继续。
2. 需要依赖旧运行态数据。
3. 需要人工推测实例归属。
4. 需要临时改 URL 参数才能通过。
5. 需要补写调试兼容代码才能通过。

## 7. 产出要求

每个模式验证结束后，都要产出：

1. 验证记录文档
2. 失败点清单
3. 修复清单
4. 最终通过结论

## 8. 本文结论

清理后的验证目标不是“勉强跑通一次”，而是证明：

- 三种模式都能脱离历史运行态独立成立；
- 新客户从零接入时，不再依赖过去的脏数据和临时兼容。

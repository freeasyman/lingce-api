## 1. 生产现状诊断（基于 3621 条真实调用，2026-06-20 ~ 07-18）

### 1.1 架构地基是干净的（好消息）

- **无任何绕过网关的 AI 调用**。`lingce-api` 与 `lingce-worker` 全部经 `llm-gateway`，已核实无直连 dashscope/openai 的代码。→ "所有成本可被记录"在架构上成立。
- 录音的成本大头（转写 ASR、清洗、核心结构化分析）在 **`lingce-worker`** 执行，不在 `lingce-api`。这是原交付文档未点明的关键事实。
- 审计表 `gateway_call_records` 与业务表同在 `lingce_prod`（阿里云 RDS）同库，跨表 JOIN 可行，利于回填与对账。

## 2. 真实成本与定价方案

### 2.1 真实单位成本（修复后测算，按业务场景拆分）

完整成本 = 该录音全部 worker 步骤（转写+清洗+分析各步，含重试）文本成本 + 应记 ASR 成本（`duration秒 × 0.00022`）。

**注意：不能用"每条录音平均成本"单一口径定价**。剔除碎录音（duration ≥ 300s）后按角色拆分，差异巨大：

| 场景 | 有效录音 | 平均时长 | 平均真实成本 | 中位 | P90 | 最大 |
|---|---|---|---|---|---|---|
| 医生 | 395 | ~13 分钟 | **¥0.32** | ¥0.24 | ¥0.43 | ¥3.44 |
| 咨询师 | 301 | ~28 分钟 | **¥0.44** | ¥0.27 | ¥0.77 | ¥3.44 |
| 前台 | 20 | **~160 分钟** | **¥3.03** | ¥3.54 | ¥4.21 | ¥4.27 |

关键洞察：
1. 早前"¥0.27 单一均值"把碎录音/只转写未分析的录音混入拉低了，已废弃。真实值：医生 ¥0.32、咨询师 ¥0.44。
2. **前台场景成本是医生/咨询师的 7~10 倍**（录音超长 + 事件分段逐段分析，一条裂成几十次调用）。→ 对客户"一口价 X 点"会在前台场景巨亏，**证明按客户展示点数必须区分业务场景/动作**。
3. ASR 占成本约 60%，而它当前生产记为 0，等于每条录音成本被低估一多半。
4. 即便最贵的前台 ¥3~4/条，对比 5000/年毛利仍极高。**成本不是定价约束，场景差异才是要防的坑。**

### 2.1.1 内容生成成本：生产数据不足（需确认）

全库扫描内容相关调用，生产几乎无数据：`lingce-api/content/chat` 成功 30 条共 ¥0.09（每条 ~¥0.003）、`doctor_content_gen` 2 条 ¥0.12。

- 文章/小红书/视频脚本/图文功能**在生产上基本未起量**，或调用未带可识别 caller_module（现全归到笼统的 `content/chat`，区分不出动作）。
- 代码侧 content service 有 topic_generation/content_generation/graphic_note_repair 且传了归因，但生产 caller_module 打点太粗，对应不上。
- 影响：内容生成暂无法用真实数据定价，对客户点数先按 token 估算拍保守值，待起量后校准；**内容归因打点需在第 0 层一并修**（见 3.7）。

### 2.2 定价的核心判断：瓶颈是转化，不是成本

- 现价 5000 元/账号/年。按真实成本 ¥0.27/条，需分析 **约 1.8 万条/年** 才触及成本线。
- 生产 28 天实际仅 1539 条、AI 成本约 ¥170。**当前毛利极高，AI 成本几乎可忽略**。
- 结论：**5000 的年费门槛挡住了小客户**。新定价的价值在于降低起步价、让客户"先小额试、用爽了再加购"，从而提升销售转化。

### 2.3 定价模式（已定：平台费 + 点数包含制）

分层结构（具体价格待你确认，以下为建议）：

```
平台费（席位/年） + 赠送点数额度
  ├─ 起步版：低平台费（如 1980/年）+ 含 N 点，够小客户先跑起来
  ├─ 标准版：中平台费（如 4980/年）+ 含更多点，主力档
  └─ 旗舰版：高平台费 + 大额点数 + 高级功能
点数用完 → 加购点数包（阶梯价，量大折扣）
```

- 平台费锚定"产品价值/席位"，点数锚定"用量"，两者解耦。
- 起步版降低门槛提转化；加购点数打开上不封顶的增长空间。

### 2.4 扣费口径：底层真实成本结算 + 客户侧可预估展示（关键设计）

你选了"按真实成本 × 汇率换算"。但真实成本每次调用波动（token/时长不同），若直接换算，客户会看到"同样一条录音这次扣 8 点、下次扣 11 点"，无法预估、难解释，反伤转化。且你已定"客户只看点数、不看人民币"。

解法——**两层口径分离**：

1. **结算层（内部，真实成本×汇率）**：每次调用按 `真实成本 × 汇率` 精确折算为点数，写入 `ai_billing_events`，保证毛利与真实成本挂钩、可对账、可审计。
2. **展示/扣费层（对客户，可预估）**：客户看到的是"一次录音分析约 X 点"这种**按业务动作的可预估口径**（用真实成本分布定档，如 P50/P90 定价），扣费按此口径。客户能预估、能理解。
3. 两层差额（真实成本波动）由灵策承担/吸收，因毛利极高，风险可控。

> 即"内部按真实成本核算保毛利，对客户按业务动作稳定计价"。汇率、动作点数、倍率全部走 `billing_rule_version` 版本化，历史账单永久可解释。

### 2.5 待你确认的定价参数

1. 汇率：1 元真实成本 = 多少点？（建议先定 1 元=100 点，即 1 点=1 分，与现占位口径一致，便于迁移）
2. 各档平台费与赠送点数的具体数字。
3. 各业务动作的对客户展示点数（录音分析 / 内容生成 / 选题 等），我可据成本分布给建议值。
4. 点数是否有效期（年度清零 / 滚存）。
5. 老客户（已付 5000 包干）如何平滑迁移（建议：折算为等值大额点数包 + 标准版席位）。

## 3. 第 0 层 · 修复成本真相（发布前提，1~2 天）

目标：做完后，每一次 LLM/ASR 调用的真实成本都被准确、完整、带归因地记录。

### 3.1 生产库归因 migration（问题①）

- 现状：`gateway_call_records` 生产仅 22 列，归因字段全缺。
- 动作：在 `lingce_prod` 执行归因字段 `ALTER TABLE` + 索引（见 `开发方案.md` 第 5 节 SQL），确认 `llm-gateway` migration 在生产真正跑过。
- 校验：`information_schema.columns` 确认 35 列到位；新调用能写入归因。
- **不可逆操作，执行前逐条与你确认。**

### 3.2 ASR per_second 成本落地（问题②）

- 现状：代码 `calculateAudioCost` 已支持 per_second，但生产 164 条 fun-asr 成本仍全 0。
- 需排查：生产网关是否为修复前的旧版本（未部署）？还是 `duration=0` 导致 `时长×单价=0`？
- 结合问题③，大概率是"时长被清零/多除导致成本≈0"与"旧版本未部署"叠加。
- 动作：确认修复版本已部署；补齐 `fun-asr=0.00022`、`paraformer-v2=0.00008` 等定价加载。

### 3.3 音频时长单位修正（问题③）

- 现状：网关记 3.2s，真实 12541s，差约 1000 倍。`recordings.duration` 单位=秒（已实测确认）。
- 动作：核实 DashScope 返回的 `duration` 原始单位。若上游已是秒，则去掉 `/1000.0`；若为毫秒需按段累计而非取单段。
- 校验：随机抽 10 条转写，`audio_duration_seconds` 与 `recordings.duration` 对齐（误差 <5%），且 `total_cost = duration × 单价 > 0`。

### 3.4 worker 归因补全（覆盖成本大头）

- 现状：`lingce-worker` 走网关但**未传** `recording_id`/`analysis_run_id`/`analysis_step_run_id`/`billing_subject`/`business_domain`，仅靠 `trace_id` 隐含 recording_id。
- 动作：在 `gateway.TextInferenceRequest`/`AudioInferenceRequest` 加 `Billing` 字段，在 transcribe/clean/analysis 各步传递归因；worker 已有 `run_id`/`step_run_id`，透传即可。
- billing_subject 分档：`transcription` / `transcription_cleaning` / `recording_analysis`（分析各步可细分）。

### 3.5 历史数据回填

- 从 `trace_id`（`transcribe_1866_...`）正则解析 `recording_id` 回填归因（`开发方案.md` 第 10 节）。
- ASR 历史成本重算：`UPDATE ... SET total_cost = recordings.duration × 单价`（JOIN recordings），标记修复时间点，报表注明口径切换。
- **批量 UPDATE 生产数据，执行前逐条与你确认，先在小范围 dry-run。**

### 3.6 失败调用口径（问题⑤）

- 失败调用 cost=0 保留（未产生真实计费），但报表/扣费须区分成功/失败；点数只对成功调用扣。

### 3.7 内容生成归因打点细化（新增）

- 现状：内容生成全部归到笼统 `caller_module=content` / `function_type=chat`，无法区分文章/小红书/视频脚本/图文/选题，将来无法按动作计费。
- 动作：在 lingce-api content service 各调用点传细分 `billing_subject`（topic_generation/content_generation/graphic_note_repair/script_generation 等）与 `business_object_type`，caller_module 也按动作细化。
- 待生产起量后重新测算内容生成真实成本，校准对客户点数。

## 4. 第 2 层 · 计费系统架构（4~5 天）

### 4.1 数据模型（新增，建议落在 lingce-api 库）

```text
ai_billing_rules            点数规则版本化（汇率/动作点数/倍率/生效时间）
  id, version, effective_from, exchange_rate,
  action_points(jsonb: {recording_analysis: X, content_generation: Y, ...}),
  multipliers(jsonb), status

ai_billing_events           扣点流水（每次可计费调用一条）
  id, tenant_id, gateway_call_record_id,
  business_domain, business_object_type, business_object_id, billing_subject,
  actual_cost_cny,           -- 真实成本（结算层）
  settle_points,             -- 真实成本×汇率（内部核算）
  charged_points,            -- 对客户实扣（可预估口径）
  billing_rule_version, created_at

ai_credit_accounts          租户点数账户
  tenant_id, balance_points, granted_points, purchased_points,
  frozen_points, updated_at

ai_credit_transactions      账户流水（充值/赠送/扣减/退款/过期）
  id, tenant_id, type(grant|purchase|consume|refund|expire),
  points, balance_after, ref_type, ref_id, remark, created_at
```

### 4.2 扣费流程

```
调用成功落 gateway_call_records（真实成本，已修复）
  → 计费服务读规则版本
  → 计算 settle_points(真实×汇率) 与 charged_points(动作可预估口径)
  → 写 ai_billing_events
  → 扣 ai_credit_accounts.balance_points，写 ai_credit_transactions(consume)
  → 余额不足：告警/软阻断（策略待定）
```

### 4.3 关键设计原则

- 网关只记原始成本与归因，**不做扣点**（扣点在 lingce-api 计费服务）。
- 规则版本化：汇率/点数/倍率变更只新增 version，历史账单按当时 version 解释。
- 幂等：以 `gateway_call_record_id` 唯一约束防重复扣点。
- 异步：扣点走队列/定时批处理，不阻塞 AI 调用主链路。

## 5. 第 1 层 · 运营后台重做 + 第 3 层 · 详情内嵌（前端，lingce-web）

### 5.1 后端生产级聚合接口（替代前端本地聚合）

新增真·后端聚合（SQL 直接 GROUP BY，非拉全量本地算）：

```text
GET /ai-usage/summary        （后端聚合，含趋势）
GET /ai-usage/top-objects    高成本业务对象 Top-N（后端）
GET /ai-usage/anomalies      单次高成本/失败重试（后端）
GET /ai-usage/by-*           租户/域/主题/模型（后端聚合）
```

### 5.2 运营后台（推倒重做 codex 版本）

- 面向运营/财务：真实成本、毛利、租户排行、业务域/主题/模型分布、异常、调用明细。
- 数据来自后端聚合，去掉前端 `buildObjectRows`/`buildAnomalies` 本地计算。
- 保留现路由 `/management-dashboard/attribution`（降低联动风险）。

### 5.3 租户侧 AI 用量中心（新建）

- 面向租户管理员：已用/剩余点数、消耗趋势、业务构成、明细、预算预警（50/80/100%）。
- **只展示点数与业务用量，绝不展示人民币成本**（已定）。

### 5.4 详情页内嵌消耗组件

- 录音详情：本条录音各步骤（转写/清洗/分析）点数、时长、状态时间线。
- 内容详情/生成任务：一次生成任务下多次调用合并视图。复用 by-recording/by-content/by-generation-task。

### 5.5 前端权限口径

- 运营：全租户、真实成本、request_id/trace_id 排障字段。
- 租户管理员：仅本租户、只看点数。
- 普通业务用户：仅有权业务对象的消耗摘要，无跨对象汇总、无成本。

## 7. 硬约束与风险（补充你未想到的）

1. **规则版本化不可省**：汇率/点数一旦发布给客户就需版本化、可追溯，禁止写死在前端或调用方。
2. **扣点幂等**：以 gateway_call_record_id 唯一约束，防重试/重放重复扣点。
3. **修复时间点标记**：ASR 修复后新旧成本口径不一致，报表必须标注切换时间，避免对账争议。
4. **worker 与 api 的 recording_id 一致性**：回填与新数据都要保证同一录音的所有步骤归到同一 recording_id。
5. **余额不足策略**：软阻断（仍执行，转欠费）还是硬阻断（拒绝调用）需产品定，影响客户体验。
6. **并发扣点竞态**：账户余额更新需行锁/乐观锁，防并发超扣。
7. **老客户迁移**：已付 5000 包干客户不能因改制受损，需折算方案与灰度。
8. **生产写操作全部先 dry-run + 逐项确认**（migration、回填、批量 UPDATE）。

## BUG-A（P0）content 上下文 SQL 引用未 JOIN 的 `r.` 别名 → 500

### 现象
- `GET /api/v1/ai-usage/top-objects?type=content` → 500
- `GET /api/v1/ai-usage/contents/{id}`（内容详情）→ 500
- 报错：`missing FROM-clause entry for table "r" (SQLSTATE 42P01)`

### 根因
`usageASRDurationSQL()`（store_aiusage.go:266）内部写死调用 `usageObjectDurationSQL("recording")`，恒定展开成 `COALESCE(r.duration, 0)`：
```go
func usageASRDurationSQL() string {
	return "CASE WHEN COALESCE(" + usageJSONText("billing_subject") + ", NULLIF(g.function_type, '')) = 'transcription' THEN COALESCE(" + usageObjectDurationSQL("recording") + ", " + usageAudioDurationSecondsSQL() + ") ELSE 0 END"
}
```
当查询是 content 上下文时，`usageObjectJoin("content")` JOIN 的是 `content_items ci`（无 `r` 别名），SQL 里却出现 `r.duration` → 报错。

recording 上下文不报错（因为 JOIN 了 recordings r）；所以只有 content 分支崩。

### 修复
给 `usageASRDurationSQL` 加 `objectType` 参数，content 时不引用 `r`（用 usage_metadata 的音频秒数即可，content 本无 ASR，退化为 0 也可接受）：
```go
func usageASRDurationSQL(objectType string) string {
	durationExpr := usageObjectDurationSQL(objectType) // recording→r.duration; content→0::double precision
	return "CASE WHEN COALESCE(" + usageJSONText("billing_subject") + ", NULLIF(g.function_type, '')) = 'transcription' THEN COALESCE(" + durationExpr + ", " + usageAudioDurationSecondsSQL() + ") ELSE 0 END"
}
```
（`usageObjectDurationSQL` 已有 content 分支返回 `0::double precision`，直接复用即可。）

### 同步改全部 6 个调用点，传入正确 objectType
| 行 | 所在函数 | 应传 objectType |
|---|---|---|
| 286 | GetAIUsageSummaryAggregate | `"recording"`（该查询固定 JOIN recordings r，传 recording 保持原逻辑）|
| 334 | GetAIUsageTrendDaily | `"recording"`（同上，固定 JOIN r）|
| 372 | queryAIUsageGroup | `"recording"`（固定 JOIN r）|
| 465 | GetAIUsageTopObjects | 传入该函数的 `objectType` 变量 |
| 812 | ListAIUsageRecordRows | `"recording"`（records 查询 JOIN recordings r）|
| 875 | GetAIUsageObjectAggregate | 传入该函数的 `objectType` 变量 |

要点：**凡是函数体内 `usageObjectJoin(objectType)` 用的是变量 objectType 的（465、875），必须把同一个 objectType 传给 usageASRDurationSQL**；其余固定 JOIN recordings r 的传字面量 `"recording"`。改完确认这些查询里 ASR 时长表达式与 JOIN 的别名一致。

### BUG-A 验收
- `top-objects?type=content`、`contents/{id}` 返回 200。
- `top-objects?type=recording`、录音详情、summary、records 仍 200 且 ASR 时长数值不变（可用 recording 侧对比修复前后 total_audio_seconds 一致）。

## BUG-B（P0）对象在时间范围内无数据时详情接口崩溃

### 现象
- `GET /api/v1/ai-usage/recordings/{id}`（或 contents/{id}）当该对象在筛选时间范围内**没有任何调用**时 → 500
- 报错：`cannot scan NULL into *int64`（col: tenant_id）
- 实测：recordings/1859 在范围外→500；recordings/1796 有数据→200 正常。

### 根因
`GetAIUsageObjectAggregate`（store_aiusage.go:857）用聚合查询 `SELECT MAX(g.tenant_id) ... WHERE recording_id=$3 AND created_at范围`。当无匹配行时，聚合仍返回**一行**，但 `MAX(tenant_id)` 为 NULL，`COUNT(*)`=0；scan `&agg.TenantID`（`int64`）遇 NULL 崩溃。同理 first_call_at/last_call_at（MIN/MAX created_at）也会是 NULL。

### 修复（二选一，推荐方案1）

**方案1（推荐）：无数据时优雅返回 nil（handler 层转 404 或空）**
在 scan 前先判断 total_calls：把查询改为可判空，或用 `COALESCE`。最简单稳妥——SQL 里对可空列加 COALESCE：
```sql
SELECT COALESCE(MAX(g.tenant_id), 0) AS tenant_id,
       COUNT(*) AS total_calls,
       ...
       COALESCE(MIN(g.created_at)::text, '') AS first_call_at,
       COALESCE(MAX(g.created_at)::text, '') AS last_call_at,
       ...
```
然后在 Go 里：scan 完若 `agg.TotalCalls == 0` → `return nil, nil`（service 层已有 `agg == nil` 分支转空/404，参考现有 GetAIUsageByRecording 里 `if err != nil || agg == nil { return nil, err }`）。

**方案2：scan 进 nullable 再转换**
`tenant_id` 用 `pgtype.Int8` 或 `*int64` 扫，first/last_call_at 用 `*string`，无行时字段留零值。

### 注意
- 同一函数 content/recording 两条路径都要覆盖。
- object_name/role/scene 的 MAX(...) 在无行时也可能 NULL，若它们 scan 进 string 也会崩——一并用 `COALESCE(..., '')` 兜底。

### BUG-B 验收
- 范围外的 recordings/{id}、contents/{id} 返回 200 空结果（或 404），不再 500。
- 有数据时详情返回不变（recordings/1796 全年范围仍正常）。

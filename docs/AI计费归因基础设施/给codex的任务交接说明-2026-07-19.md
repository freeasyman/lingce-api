## 1. 一句话目标

让每一次 LLM/ASR 调用的**真实成本**被准确、完整、带业务归因地记录下来。这是后续计费、点数、报表的地基——地基是错的，上面全错。**本层不做扣费、不做点数、不做界面**，只修数据真相。

---

## 2. 为什么做这件事（背景，帮你理解而非照抄）

系统横跨 4 个仓库：`llm-gateway`（AI 调用网关+审计）、`lingce-worker`（录音分析后台，成本大头在这）、`lingce-api`（业务后端+统计查询）、`lingce-web`（前端）。所有 AI 调用都经过 llm-gateway 落审计表 `gateway_call_records`（生产库 `lingce_prod`，阿里云 RDS，与业务表同库）。

问题：之前一轮开发在**代码层**完成了归因字段、ASR 成本修复，`go test` 通过、文档写了"闭环完成"。但用生产 3621 条真实数据核查后发现，**生产层面成本完全不可信**：ASR 成本全是 0、音频时长差 100~3000 倍、归因字段在生产表里根本不存在。"代码通过 ≠ 生产可用"。你要修的就是这个鸿沟。

## 4. ⚠️ 两个「反直觉」的关键约束（最容易做错，务必遵守）

### 约束一：不要去改 ASR 定价配置
`model_pricing.json` 里 `fun-asr=0.00022`、`paraformer-v2=0.00008` **是对的**，`calculateAudioCost` 读 `PerSecond` 的逻辑**也是对的**。ASR 成本为 0 **不是**因为定价缺失。真因是 C（时长）+ 没部署。**不要动定价配置，不要动 calculateAudioCost 的读价逻辑。**

### 约束二：音频时长修复不是「删掉 /1000」
`usage.duration` 这个字段对 fun-asr 本身就不可信（除不除 1000 都错）。正确做法是**换数据源**：代码在 `extractAudioResults`（`dashscope_audio.go:296-309`、`342-355`）已经解析了每个句子的 `EndTime`（秒），取 `max(EndTime)` 才是真实音频时长。`usage.duration/1000` 只能作为 segments 为空时的兜底。**见执行计划 T1 的伪代码。**

---

## 5. 任务分两类，工作方式完全不同

### A 类：纯代码修复（你可直接改 + 写测试 + 跑 `go test`，不碰生产）
- **T1** [llm-gateway] 修音频时长来源（换成 `max(segment.EndTime)`）— 最高优先，见约束二
- **T3** [llm-gateway + worker] worker 归因贯通（加 Billing 字段 + 各调用点传 recording_id/analysis_run_id/step_run_id/billing_subject/business_domain）
- **T4** [lingce-api] 内容打点细化（各动作细分 billing_subject）
- **T2** [llm-gateway] 确认 ASR 定价（不改代码，仅确认，见约束一）
- **T4b** 失败调用口径（不改代码，登记约定：成本/点数只统计 success=true）

### B 类：生产库操作（不可逆，严格纪律，见第 6 节）
- **T5** 生产库归因 migration（部署新 gateway 会自动跑，可能无需手动）
- **T6** 历史回填（recording_id 回填 + ASR 历史成本重算）
- **T7** 部署 llm-gateway / worker / lingce-api 到生产

### 执行顺序
```
先做 A 类全部（改代码+测试，在 dev/staging 验证 T1 时长修复用真实录音核对）
  → 产品负责人确认代码 + 安排部署窗口
  → T7 部署（自动带 T5 migration）
  → 部署后做 T6 历史回填（每条 UPDATE 先 dry-run）
```

---

## 6. 🔒 生产库安全纪律（B 类必须遵守，不可跳过）

生产库是阿里云 RDS 上的 `lingce_prod`，跑着真实客户数据。

1. **任何生产写操作（migration / UPDATE）执行前，先把 SQL + dry-run SELECT 的结果贴给产品负责人，得到明确确认后才执行。** 不要自作主张跑 UPDATE。
2. T6 的每条 UPDATE，先跑对应的 `SELECT count(*)` 和 `LIMIT 20` 样例预览，确认影响范围和结果正确，再执行。
3. UPDATE 建议包在事务里（`BEGIN; ... 验证 ...; COMMIT/ROLLBACK`），或先备份受影响行。
4. 只读连库方式见 `第0层执行计划` 与项目既有记录；连库只用于 SELECT 验证与经确认的 UPDATE，绝不做 DROP/DELETE/TRUNCATE。
5. ASR 历史成本重算要按模型区分单价（生产目前只有 fun-asr=0.00022），并在报表标注"成本修复时间点"，因为修复前后口径不一致。

---

## 7. 完成的定义（第 0 层验收总标准）

1. 新转写记录 `total_cost > 0`，`audio_duration_seconds` 与 `recordings.duration`（单位=秒）误差 < 5%。
2. worker 新调用（转写/清洗/分析）带 recording_id / business_domain / billing_subject，分析步骤带 analysis_run_id / analysis_step_run_id。
3. 生产表含全套 35 列归因字段。
4. 历史 ASR 记录成本已重算，报表标注修复时间点。
5. 任取一条录音，`SELECT sum(total_cost) FROM gateway_call_records WHERE recording_id=X` 能得到该录音真实总成本（ASR + 文本各步）。
6. `llm-gateway` / `lingce-worker` / `lingce-api` 三仓库 `go test ./...` 全部通过。

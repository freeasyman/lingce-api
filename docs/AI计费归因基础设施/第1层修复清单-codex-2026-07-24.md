## P0（必修）成本结构二级映射接错字段，导致"成本结构"tab 名存实亡

### 问题根因
前端 `groupStructureLevelOne/Two`（attribution.tsx）用 `doctor-patient-core`、`frontdesk-event-analyze` 等作映射键——**这些是 `caller_module` 的值**。但数据来自 `by-billing-subject` 接口（`GROUP BY billing_subject`）。

生产真实 `billing_subject` 只有粗值：`recording_analysis`(709条,¥31.74)、`transcription`、`transcription_cleaning`、`content_generation`、少量 `P_FRONTDESK_*`。细分维度全在 **`caller_module`**：
```
frontdesk-event-analyze / frontdesk-event-segment / doctor-patient-supporting-details
/ consultant-conversion-analysis / doctor-patient-core / frontdesk-required-actions / frontdesk-summary
```

**后果**：成本结构第二级(按角色分析环节)几乎全空；第一级"分析"桶漏掉 `recording_analysis` 大头。

### 修复方案：新增 by-caller-module 聚合接口，前端方案A改用它

**后端 1 — store_aiusage.go**：新增一个方法（复用现成的 `queryAIUsageGroup`）：
```go
func (s *Store) GetAIUsageByCallerModuleAggregates(ctx context.Context, filter AIUsageFilter) ([]AIUsageGroupItem, error) {
	return s.queryAIUsageGroup(ctx, filter, "COALESCE(NULLIF(g.caller_module, ''), 'unknown')")
}
```

**后端 2 — service.go**：新增
```go
func (s *Service) GetAIUsageByCallerModule(ctx context.Context, req AIUsageListRequest) ([]AIUsageGroupItem, error) {
	return s.store.GetAIUsageByCallerModuleAggregates(ctx, buildAIUsageFilterFromRequest(req))
}
```

**后端 3 — handler.go**：新增路由 + handler（仿 `GetAIUsageByBillingSubject`，含 `applyAIUsageScope` 鉴权）：
```go
mux.Handle("GET /api/v1/ai-usage/by-caller-module", authMw(http.HandlerFunc(h.GetAIUsageByCallerModule)))
```

**前端 1 — api/ai-usage.ts**：新增
```ts
export async function getAIUsageByCallerModule(params?: AIUsageListParams): Promise<AIUsageGroupItem[]> {
  const raw = await api.get<Record<string, unknown>>('/ai-usage/by-caller-module', toQueryParams(params));
  const source = unwrapObject(raw);
  return asArray(source.items).map(normalizeGroupItem);

```

**前端 2 — attribution.tsx**：
- 新增 `byCallerModuleQuery = useQuery(... getAIUsageByCallerModule(sharedParams))`。
- 成本结构 tab 的两级构成 **改用 byCallerModuleQuery.data**（不再用 bySubjectQuery）。
- `groupStructureLevelOne` 映射键保持不变（本就是 caller_module 值），现在能对上了。
- 一级"分析"桶要覆盖全部分析类 caller_module；建议兜底逻辑：凡不是 `transcription`/`transcription_cleaning` 的都归入"分析"（防止将来新增分析步骤漏桶）：
  ```ts
  // 一级：transcription→转写ASR, transcription_cleaning→转写清洗, 其余→分析
  // 二级：按 caller_module 细分角色步骤（保留现有映射，未匹配的显示原始 module 名而非丢弃）
  ```
- `aggregateGroups` 对未在映射表里的 key，**不要丢弃**，归到"分析"(一级)或原样显示(二级)，避免漏成本。

### P0 验收

## P1（必修）anomalies 失败查询含无效 ReplaceAll，success 筛选下永远空

### 问题
`store_aiusage.go` ~656 行：
```go
` + strings.ReplaceAll(whereSQL, "g.success = $", "g.success = $") + `
```
把字符串替换成自身，**no-op**。`whereSQL` 由 `buildUsageFilter(filter,3)` 生成，若请求带 `success` 参数，whereSQL 含 `g.success = $N`，拼进 `WHERE NOT g.success ... AND g.success = $N` → 矛盾 → 失败异常永远查不出。

### 修复
failedSQL 不应受 Success 筛选影响。用一个**清空 Success 的独立 filter** 单独构建 whereSQL：
```go
failedFilter := filter
failedFilter.Success = nil
failedWhere, failedFilterArgs := buildUsageFilter(failedFilter, 3)
failedArgs := append([]any{startAt, endAt}, failedFilterArgs...)
// failedSQL 用 failedWhere，删掉那行 strings.ReplaceAll
```
注意：主查询(highCost)的 args 与 failed 查询的 args 现在独立构建，不要再用 `args[2:]` 切主查询的 args。

### P1 验收
- 传 `?success=true` 时，anomalies 的"失败烧钱"类仍能正常返回（生产近30天：obj 1861 有 4 次失败等）。
- 不传 success 时行为不变。

## P2（建议修）anomalies 的 #0 幽灵对象

### 问题
`COALESCE(recording_id, content_id, 0)` 把 recording_id 和 content_id 都为空的失败调用（生产16条）归并成 `object_id=0`，前端显示为 `recording#0`。

### 修复（二选一）
- 方案A（推荐）：failedSQL 增加 `AND (recording_id IS NOT NULL OR content_id IS NOT NULL)`，只统计能归因到对象的失败。
- 方案B：object_id=0 时前端显示"未归因调用"而非 `#0`，且不可点击下钻。

### P2 验收
异常列表不再出现 `recording#0`；或 #0 显示为"未归因调用"且不可点。

# AI 计费归因基础设施开发方案

## 1. 背景

当前系统已经通过 `llm-gateway` 记录 LLM/ASR 调用审计数据，包括 `tenant_id`、`trace_id`、`caller_module`、`function_type`、`total_tokens`、`total_cost` 等字段。但这些记录主要描述“一次模型调用”，不能稳定回答“一条录音、一次内容生成、一次业务任务总共消耗了多少 AI 成本”。

现有统计存在三个核心问题：

1. 录音分析是一组多步骤调用，不是一条 LLM 记录。一次录音可能包含转写、清洗、核心分析、补充分析、总结、行动建议等多个步骤。
2. `gateway_call_records` 没有结构化 `recording_id`、`content_id`、`analysis_run_id` 等业务归因字段，当前只能临时从 `trace_id` 字符串中解析。
3. ASR/FSR 成本当前存在记录为 0 的问题，已发现 `model_pricing.json` 使用 `per_second`，但 Go 结构体只接收 `per_minute`，导致音频单价没有正确加载。

本方案目标是建设一套通用的 AI 计费归因基础设施，为后续 AI 点数、成本报表、客户账单和毛利分析打基础。

## 2. 目标

系统需要稳定回答以下问题：

1. 哪个租户消耗了 AI。
2. 哪个业务域消耗了 AI，例如录音、内容、客户、知识库、普通对话。
3. 具体是哪条录音、哪篇内容、哪个生成任务、哪个分析任务。
4. 一次业务任务调用了几次 LLM/ASR。
5. 总 token、总音频时长、总模型成本是多少。
6. 未来应该按哪个规则扣多少 AI 点数。

本阶段只建设“归因和成本记录能力”，不直接实现扣费。

## 3. 设计原则

1. 结构化字段优先：计费、查询、报表所需字段必须是数据库列，不能只放 JSON。
2. 通用模型优先：不能只围绕录音设计，还要覆盖内容生成、选题生成、图文笔记修复、知识库等后续 AI 业务。
3. 原始成本和计费流水分离：`gateway_call_records` 记录真实调用与模型成本；未来另建 `ai_billing_events` 记录点数扣费。
4. 历史可回溯：保留 `billing_rule_version`，保证未来点数规则变化后，历史账单仍可解释。
5. 向后兼容：现有调用方不传归因字段时，LLM 调用仍可成功，只是归因字段为空。

## 4. 统一归因模型

新增一组通用字段：

```text
business_domain        // recording, content, customer, knowledge, chat
business_object_type   // recording, content_item, topic_batch, generation_task
business_object_id     // 业务对象 ID
billing_subject        // recording_analysis, transcription, content_generation, topic_generation
billing_scene          // doctor_patient, frontdesk, consultant, xiaohongshu_note
billing_rule_version   // v1
```

新增高频查询专用字段：

```text
recording_id
content_id
topic_id
customer_id
analysis_run_id
analysis_step_run_id
generation_task_id
```

通用字段用于表达统一模型；专用字段用于高频查询、索引和报表。

```go
type BillingMetadata struct {

    AnalysisRunID      int64 `json:"analysis_run_id,omitempty"`
    AnalysisStepRunID  int64 `json:"analysis_step_run_id,omitempty"`

```

在文本和音频请求中增加：

```go

```

1. 将 `BillingMetadata` 写入结构化列。
2. 同步复制一份到 `request_metadata.billing`，便于排障。
3. 不影响现有 `trace_id`、`caller_module`、`function_type`。

## 9. ASR/FSR 成本修复

当前 `model_pricing.json` 中音频模型使用 `per_second`：

```json
{
  "fun-asr": {
    "per_second": 0.00022
  },
  "paraformer-v2": {
    "per_second": 0.00008
  }
}
```

但 Go 结构体只定义了：

```go
PerMinute float64 `json:"per_minute,omitempty"`
```

因此 `per_second` 没有被解析，音频成本为 0。

修复方案：

```go
type ModelPricing struct {
    InputPer1K  float64 `json:"input_per_1k,omitempty"`
    OutputPer1K float64 `json:"output_per_1k,omitempty"`
    PerSecond   float64 `json:"per_second,omitempty"`
    PerMinute   float64 `json:"per_minute,omitempty"`
}
```

音频成本计算：

```go
unitPrice := pricing.PerSecond
if unitPrice == 0 && pricing.PerMinute > 0 {
    unitPrice = pricing.PerMinute / 60
}
totalCost := audioDurationSeconds * unitPrice
```

同时需要校验 DashScope 返回的 `duration` 单位。当前代码使用：

```go
audioDurationSeconds := float64(dsResp.Usage.Duration) / 1000.0
```

需要通过真实响应确认 `duration` 是毫秒还是秒。若上游已返回秒，则不应除以 1000。

验收要求：

1. `fun-asr` 和 `paraformer-v2` 成功转写记录的 `total_cost > 0`。
2. `usage_metadata.audio_duration_seconds` 与实际录音时长一致。
3. 单元测试覆盖 `per_second`、`per_minute` 兼容逻辑。
4. 单元测试覆盖音频成本计算。

## 10. 历史数据回填

录音历史数据可以临时从 `trace_id` 解析：

```text
transcribe_1796_1783740172094387000
clean_1796_1783740202187029000
doctor-patient-core_1796_1783740232419061000
```

回填策略：

```sql
-- 示例：具体正则按 PostgreSQL 实际语法验证后落地
UPDATE gateway_call_records
SET
  business_domain = 'recording',
  business_object_type = 'recording',
  business_object_id = parsed.recording_id,
  recording_id = parsed.recording_id,
  billing_rule_version = 'v1'
FROM (
  SELECT
    id,
    (substring(trace_id from '_(\d+)_[0-9]+$'))::bigint AS recording_id
  FROM gateway_call_records
  WHERE recording_id IS NULL
    AND substring(trace_id from '_(\d+)_[0-9]+$') IS NOT NULL
) parsed
WHERE gateway_call_records.id = parsed.id;
```

内容历史数据如果没有内容 ID、任务 ID，不建议强行精确回填。可以仅按 `caller_module = 'content'` 做粗粒度历史统计。

## 12. 统计 API 与前端查看功能

AI 计费归因基础设施最终需要被运营、客户管理员和业务使用者看见。后端归因字段落地后，应同步建设统计 API 和前端查看入口，用于验证成本归因、支持客户解释和后续点数运营。

### 12.1 用户角色与使用场景

运营管理员：

1. 查看全平台 AI 成本、调用量、token、ASR 时长趋势。
2. 按租户、业务域、模型、模块、计费主题分析成本。
3. 识别异常高消耗租户、异常高消耗业务对象。
4. 评估套餐、点数汇率、毛利水平。

租户管理员：

1. 查看本机构 AI 用量、成本或点数消耗。
2. 查看录音、内容、选题等业务维度的消耗明细。
3. 查看额度余额、预算预警、消耗趋势。
4. 对内部员工或部门的 AI 使用进行管理。

业务使用者：

1. 在录音详情页查看本条录音 AI 分析消耗。
2. 在内容详情页查看本篇内容或本次生成任务消耗。
3. 理解一次业务动作为什么产生多次 AI 调用。

### 12.8 前端权限

运营管理员：

1. 可查看所有租户。
2. 可查看真实成本 `total_cost_cny`。
3. 可查看 request_id、trace_id、模型、错误信息等排障字段。

租户管理员：

1. 只能查看本租户。
2. 默认查看点数和业务用量。
3. 是否展示真实成本由产品策略决定，建议客户侧默认不展示底层成本。

普通业务用户：

1. 只在有权限的业务对象详情中查看 AI 消耗摘要。
2. 不展示底层模型成本。
3. 不展示跨用户、跨部门、跨业务对象的汇总。

## 14. 验收标准

1. 新产生的 LLM/ASR 记录中，录音分析调用可以按 `recording_id` 汇总成本。
2. 新产生的内容生成调用可以按 `content_id` 或 `generation_task_id` 汇总成本。
3. ASR 成功调用记录的 `total_cost` 不再为 0。
4. 单条录音成本可以稳定查询，不依赖解析 `trace_id`。
5. 单篇内容或一次内容生成任务成本可以稳定查询。
6. 未传归因字段的历史/兼容调用不受影响。
7. 报表可以按 `tenant_id + business_domain + billing_subject` 聚合成本。
8. 运营后台可以查看全平台 AI 成本总览、趋势、租户排行、业务域分布和调用明细。
9. 录音详情页可以查看单条录音的 AI 调用步骤、成本、token、ASR 时长和状态。
10. 内容详情页或生成任务页可以查看一次内容生成任务下的多次 AI 调用明细。
11. 租户侧 AI 用量中心可以按周期查看点数、用量趋势、业务构成和消耗明细。
12. 权限隔离正确：租户用户不能看到其他租户数据，普通业务用户不能看到底层成本和跨对象汇总。

## 15. 风险与注意事项

1. 不能把点数扣费直接写死在网关里。网关只负责原始成本和归因记录。
2. 不要只加 `recording_id`，否则内容生成和其他 AI 业务会再次产生归因缺口。
3. 不要继续依赖 `trace_id` 解析作为正式方案。`trace_id` 只用于链路追踪和历史回填。
4. ASR 成本修复后，历史和新数据成本口径会不一致，需要在报表中标记修复时间点。
5. 内容生成存在一次用户动作触发多次 LLM 调用的情况，例如图文笔记生成后再修复页数，必须使用同一个 `generation_task_id` 汇总。
6. 客户侧页面不宜直接展示底层模型供应商成本，建议展示 AI 点数和业务用量。
7. 前端统计必须明确时间口径、成功/失败口径和是否包含重试，否则账单解释容易产生争议。

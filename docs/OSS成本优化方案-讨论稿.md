# OSS 成本优化方案（讨论稿）

> 状态：**讨论中**，未达成一致前不改任何代码。
> 创建：2026-11-20
> 目的：记录阿里云 OSS 调用现状与成本优化方向，作为讨论底稿，逐步补充数据与决策。

---

## 1. 背景与目标

- `lingce-api` 的所有录音/音频都存储在阿里云 OSS（北京），是核心依赖。
- 目标：在不影响业务与合规的前提下，降低 OSS 的 **存储成本** 与 **公网流出（流量）成本**。

### 2.3 关键事实（决定成本结构）

1. **存储类型未指定** → 全部标准存储（OSS 最贵一档）。
2. **无生命周期规则** → 文件只进不出，永不降级、不清理。
3. **无 CDN** → 播放回源 OSS 公网，公网流出按 OSS 价计。
4. **音频不压缩**：实时接诊 PCM→WAV（约 32KB/s ≈ 1.9MB/分钟），比 opus/m4a 大 8–15 倍。
5. 每次上传/播放都新建 `ossutil.NewClient`（性能小问题，基本不影响成本）。

### 2.6 file_url 直读链路排查结果（2026-11-20）

「直接读公开 `file_url`（`https://lince.oss-cn-beijing.aliyuncs.com/...`）」的链路：

| 链路 | 位置 | 读法 | ACL 改 private 影响 |
| --- | --- | --- | --- |
| **转写** | lingce-worker `transcribe.go` → llm-gateway `dashscope_audio.go` | 把 `file_url` 作为 `AudioURL` 传给 **DashScope**，由 DashScope 从公网下载 | **会断**（需改传签名 URL） |
| 遗留归集 | lingce-worker `media_normalizer.go` / lingce-api `migrateRecordingMediaToOwnedStorage` / `backfill_recording_media_to_oss` | 自己 `http.Get(file_url)` 下载再传 OSS（处理 oss_key 为空的遗留） | 会断（迁移类，低频） |
| badge vendor 转存 | lingce-api `badge/store.go` | 下载的是 **vendor URL**（非本 bucket） | 不受影响 |
| 沙盒复制 | lingce-api `sandbox/service.go` | OSS 服务端 `CopyObject`（带 AK） | 不受影响 |
| 播放 | lingce-api 播放接口 | prod 已走 `GetSignedURL` | 不受影响 |

结论：**ACL 改 private 的主要影响是「转写」**（DashScope 需从公网读 file_url）；归档**不影响**转写（转写在录音上传 90 天内完成，对象尚未归档）。

### 2.9 ⚠️ 异常发现：worker badge pull 重复上传孤儿对象（2026-11-21）

排查「一天涨 11.5GB」时发现，增长**全部来自 `recordings/4/`（tenant 4）的 mp3**，且是重复灌数据：

- 2026-11-20 21:00 → 11-21 10:50 新增 **5,497 个对象 / 13.4GB**，每小时约 390 个，**24 小时不间断**（半夜也照传）。
- 只有 **30 种固定文件大小，每种被重复上传约 258 次** → 同一批文件循环重传，非真实录音。

**根因（两个问题叠加）**：

1. worker 每 2 分钟拉取一次 badge 录音（`badge_pull_interval_minutes = 2`），请求只带 `{Page:1,Size:100}`、无时间游标，每次都拉到同一批老录音。
2. `lingce-worker/internal/base/ingest.go` 是**先 normalize（下载+上传 OSS）、后 InsertQueuedRecording 查重**；查重命中返回 `duplicate_order_no` 跳过，但 OSS 对象已多传一份 → 每次拉取产生一批孤儿对象。

**影响**：约 **24GB/天、700GB/月** 孤儿对象，纯浪费（~70–100 元/月），且无清理会持续累积。

**修复建议**：

- 止损（不改代码）：调大 `badge_pull_interval_minutes` 或临时停 pull，并清理孤儿对象。
- 根治（需改代码）：把「查重」前移到「下载/上传」之前。
- 与本方案的 ACL / 生命周期改动**无关**，是既有问题。

✅ **已修复并上线（2026-11-21 12:02）**：worker 拉取加时间游标 + 入库前查重；api 回调入库前查重。发布复核通过：首轮回填 28 条全部 skipped（零上传），之后每轮 pulled=0，OSS 不再新增孤儿；回调路径持续收到新录音。发布详情见 `docs/badge拉取去重修复-发布说明.md`。存量约 2TB 孤儿对象的清理为独立后续任务。

## 3. 优化方向（按「省钱力度 / 改动风险」排序）

### 方案 0：修复 Bucket ACL（安全，优先级最高）

现状 ACL 为 `public-read-write`，任何人无凭证即可读/写/覆盖对象，既泄露患者录音，又可能被灌垃圾数据制造存储费。**无论是否做成本优化都应先处理。**

- 分两步：
  1. **立即（零代码）**：ACL 改为 `public-read`——去掉匿名写权限（消除「被灌数据」风险），保留匿名读（转写链路依赖 DashScope 从公网取 `file_url`，见 2.6）。
  2. **后续（需改代码）**：彻底 `private`，转写/回放全部走签名 URL。
- ⚠️ 关键依赖：转写链路 = worker → llm-gateway → **DashScope 从公网下载 `file_url`**（`llm-gateway/internal/provider/dashscope_audio.go` 把 `AudioURL` 作为 `FileURLs` 传给 ASR）。改 private 前，必须让转写传**签名 URL** 替代公开 URL。

### 方案 1：存储降级 + 生命周期（收益最大，代码改动≈0，含到期删除）

存储类型差异（ZRS，北京，元/GB/月，单价以阿里云现价为准）：

| 类型 | 单价 | 读取方式 | 最短存储 | 适用 |
| --- | --- | --- | --- | --- |
| 标准 Standard | 0.15 | 即时 | 无 | 热数据 |
| 低频 IA | 0.10 | **即时**（毫秒） | 30 天 | 访问少但需即时读 |
| 归档 Archive | 0.033 | **需解冻**（标准 1–5 分钟） | 60 天 | 几乎不读，长期存档 |
| 冷归档 Cold Archive | 0.015 | 需解冻（数小时） | 180 天 | 极冷 |

- 「直接转归档」比「经低频中转」**存储费更省**（省掉 30–90 天这段 IA 与 Archive 差价，当前约 5–6 元/月）；标准→归档转换请求免费；留存 1 年下对象在归档待 335 天 > 60 天，无提前删除罚款。
- 但「直接归档」牺牲 30–90 天（回听窗口内）的**即时回听**，且归档回听需先解冻（代码加 `RestoreObject`）。
- **推荐规则（留存 1 年，均衡）**：
  1. 0–30 天：标准
  2. 30–90 天：低频 IA（保回听窗口内即时性）
  3. 90–365 天：归档 Archive（出回听窗口，合规存档）
  4. 365 天：**过期删除**（留存期满，自动清理，顺带解决孤儿对象）
- 激进版（存储最低）：30 天后直接归档、365 天删除，代价是 30–90 天回听也需解冻。

### 方案 2：实时录音压缩（收益大，需改代码）

把 `FinalizeRecording` 的 `pcmToWAV` 换成 **opus / m4a(AAC) / mp3** 再上传，体积缩小 ~10 倍，存储 + 流出双省。

- 需要引入转码能力（ffmpeg 或 Go 编码库）。
- ⚠️ 风险：需确认转码不影响 ASR/质检（当前 16k PCM 是转写输入，需确认 worker 是否直接读 OSS 的 WAV）。

### 方案 3：播放走 CDN（收益中等，涉及合规）

播放签名 URL 直连 OSS 公网，公网流出单价高；套阿里云 CDN（回源 OSS + 鉴权）可降低流出单价。

- ⚠️ 风险：录音是患者敏感数据，CDN 缓存/节点分布可能引入合规顾虑，且需回源鉴权改造。**不建议第一个动。**

### 方案 4：清理孤儿对象（收益小–中，需加后台任务）

目前 `DeleteFile` 只在「上传后 DB 写入失败」回滚时调用；录音软删除、试用过期、测试数据对应的 OSS 对象无配套清理，永久占存储。

- 可加定期任务：按 `recordings` 软删除状态 + `oss_key` 对账删除。

### 方案 5：大文件分片上传（收益小，主要是健壮性）

200MB 以内目前都是 `PutObject` 一次性传，中途失败整个重传；OSS SDK 支持 Multipart，可减少重传浪费。

> **MVP 最小方案见《计费缴费设计-MVP.md》**：系统只做额度+扣量+订单，其余人工。

编写日期：2026-11-10
状态：设计稿（演进版）
依据：2026 年 11 月定稿的定价体系（六产品年包 + 四个套餐 + 增量包 + 工牌）

> 业务口径以 `lingce-gtm/05-内部/2026-11-02-本轮决策记录.md` 与 `03-销售/商务待定问题清单.md` 为准。

## 1. 总览与目标

把已定稿的商业规则落到系统层面，回答三个问题：

1. **客户买了什么、还剩多少**（额度模型）
2. **每次交付怎么扣、扣多少**（计量模型）
3. **怎么买、怎么付、怎么开、怎么续**（缴费模型）

目标：

- 计量口径与《销售速查》完全一致，客户看到的是"剩余额度"，不是人民币
- 扣钱的事自动、发钱的事手动，每一笔额度可追溯
- 优惠一律通过"赠送增量包"实现，价格表永远不动
- 与现有生产库结构（订阅、功能组、归因）兼容，不推倒重来

## 2. 现状盘点（生产库）

### 2.1 已有、可复用

| 表/体系 | 现状 | 本设计怎么用 |
|---|---|---|
| `gateway_call_records` | 归因字段已上线：business_domain / business_object_type / business_object_id / billing_subject / billing_scene / recording_id / total_cost | **内部结算层**：真实成本、对账、毛利；客户不可见 |
| `tenant_subscriptions` | 一个租户一条订阅（plan_id、status、started_on/expired_on、宽限） | 扩展后承载"统一到期日" |
| `tenant_feature_groups` / `tenant_feature_assignments` | 功能开关（开关型，不是额度型） | 保持不动，只管"有没有这个功能" |
| `tenant_subscription_events` | 订阅变更审计 | 继续用，并补产品级事件 |

### 2.2 缺失、要新建

| 缺 | 说明 |
|---|---|
| 产品额度 | 6 个产品各自的额度（异构单位：小时/份/次/张/题次/人次），现在没有任何表记录 |
| 计量扣量 | 交付成功扣多少、扣到哪，没有落点 |
| 订单/支付/发票 | 现在没有订单概念，只有"订阅" |
| 赠送/审批/留痕 | 没有 0 元赠送、审批、审计 |
| 结转/折算 | 没有实现 |

### 2.3 分层结构

```text
┌───────────────────────────────────────────┐
│ 客户层（本设计新增）：产品额度（自然单位）    │
│   交付成功 → 扣额度 → 显示剩余              │
├───────────────────────────────────────────┤
│ 内部结算层（已有）：归因 + 真实成本         │
│   gateway_call_records → 成本/毛利/对账     │
└───────────────────────────────────────────┘
```

客户永远只看到"自然单位额度"（小时/份/次/张/题次/人次），
看不到人民币、看不到成本；归因层只用于内部成本核算与对账。

## 3. 核心原则（已与业务方确认）

| # | 原则 | 内容 |
|---|---|---|
| 1 | 交付才扣 | 计费点在"交付成功"，不是"大模型返回"。失败/无效/草稿不扣，重试不重复扣 |
| 2 | 自动扣、手动发 | 扣量自动（交付事件触发）；发额度手动（回款确认后运营下发） |
| 3 | 优惠走赠送 | 一切优惠、变相折扣都用"赠送增量包"实现（0 元订单 + 审批 + 留痕），价格表不动 |
| 4 | 跑了就记 | 质控每实际跑一轮扣一轮（含打回重提）；安抚客户用赠送 |
| 5 | 一个机构一个订阅 | 一个机构一条订阅、一个统一到期日；后买按剩余天数折算 |
| 6 | 按交付物计，不按操作计 | 改字、保存、预览、下载都不扣；只有"交付"和"完整质控"扣 |

## 4. 术语

| 术语 | 含义 |
|---|---|
| 额度（entitlement） | 某产品某单位的可消耗量：已授（granted）、已用（consumed）、余额（balance） |
| 单位（unit） | hour（小时）、record（份）、round（轮/次）、shot（张）、prompt（题次）、person（人次） |
| 交付成功 | 按第 6 章交付判定表，交付物送达客户可用 |
| 统一到期日 | 一个机构所有产品/增量共用的到期日 = 首个产品开通日 + 12 个月 |
| 折算 | 中途加购按"剩余天数 ÷ 365"折算价格和额度，不足 30 天按 30 天 |
| 结转 | 续费时未用余额滚入新周期一次，优先扣减，第二周期结束清零 |
| 增量包 | 每款产品的整包增量（＋20% 标准额度），不拆卖 |
| 赠送 | 0 元订单，带审批和留痕的额度下发 |
| 回款确认 | 财务确认钱到账，是"手动发"的触发点 |
| 档位（edition） | 同一产品的规格版本：标准档（现价目）、轻量档（未来）、试用（特殊档位） |
| 额度类型（quota_type） | official（正式额度，可结转）/ trial（试用额度，到期清零、不结转、不退款） |

## 5. 数据模型

> 新表落在 `lingce_api` 库（与业务表同库，便于 JOIN 对账）。均为建议结构，评审后再定稿。

### 5.1 订阅（扩展 `tenant_subscriptions`）

```text
保持现有"一个租户一条订阅"，语义改为"统一服务期"：
  started_on    = 首个产品开通日
  expired_on    = 统一到期日（开通日 + 12 个月）
  status        = active / expired / renewed / terminated

新增字段：
  first_product_code   varchar  首个开通的产品（标记服务期起点）
  contract_id          varchar  关联合同号（可选）
```

```text
规则：
· 后买产品不新建订阅，只在其额度表里追加，到期日 = 本订阅 expired_on
· 套餐 = 一次购买多个产品额度，各自一条额度，共用同一到期日
· 续费 = 新订阅周期（新 started_on/expired_on），触发结转
```

**与旧模型的关系（重要）：**

```text
· 旧的"订阅 plan → 功能组 → 菜单可见性"已废弃：
  菜单权限已交给各产品的管理员直接管理，订阅不再决定"拥有哪个菜单"。
· 订阅只承载"时间"：服务期起止（统一到期日）。
· "开通产品"的动作 = 订阅时间生效 + 该产品的额度下发
  （记录 product_code / edition / quota_type / period_start）。
· 旧的两档订阅计划（standard 365 天 / trial 7 天）不再作为档位存在：
  试用改由"试用额度包"承载（见 7.3），正式改由"产品年包"承载。
```

### 5.2 产品额度（新表 `product_entitlements`，即"通用额度表"）

```text
id            bigint
tenant_id     bigint
product_code  varchar     赢客专家 / 客户总监 / 随访顾问 / 听写病历 / 合规卫士 / 获客先锋
unit          varchar     hour / record / round / shot / prompt / person
granted       numeric     已授总额（所有授予之和）
consumed      numeric     已用（所有扣减之和）
balance       numeric     余额 = granted − consumed（物化，事务内维护）
rollover_bal  numeric     结转余额（来源=结转、尚未扣完的部分）
period_start  date        当前周期开始
period_end    date        统一到期日
status        varchar     active / paused / expired / cleared
edition       varchar     档位：standard / light / trial
quota_type    varchar     额度类型：official（正式）/ trial（试用）
updated_at    timestamp
```

```text
一个产品一个单位一行（赢客=hour 一行；听写病历=record、round、hour 三行；获客先锋=hour、prompt、record、shot 四行）。

扣量顺序：rollover_bal → 试用额度（trial）→ 正式额度（official）。
即：结转先扣，试用次之，正式额度最后扣（客户买的额度尽量保留）。
```

### 5.2.1 产品档位与价目表（新增 `product_catalog`）

一个产品可以有多个"档位"（edition）：

| 档位 | 现状 |
|---|---|
| standard 标准档 | 现行六产品年包（400 小时等） |
| light 轻量档 | 未来可能推出（如 200 小时、更低年价） |
| trial 试用 | 限期 + 限量（现状：全租户 7 天 + 最多 N 条录音） |

```text
product_catalog：
  product_code + edition → 各单位的额度、年价、增量包规格

· 订单、额度都记录 edition；价目表版本化（billing_orders.price_list_version 引用它）
· 增量包按"产品 + 档位"配置：标准档有自己的增量包，轻量档将来也有自己的
· 新增档位 = 价目表加一行 + 发布新版本，不动存量数据
```

**额度类型（quota_type，写在 product_entitlements 上）：**

```text
official（正式额度）：购买的，可结转、可退（仅开通前）
trial（试用额度）  ：限期额度，到期清零、不结转、不退款、不折现
```

**现状对齐：**

```text
生产里的试用是"全租户一条试用订阅 + 全租户录音条数限额"（TrialMaxRecordings）。
新版改为"按产品发试用额度包"（每个产品一个试用额度），
试用订阅（7 天）由试用额度包的期限自然表达，不再单独维护一条试用订阅。
```

### 6.2 通用扣量规则

```text
· 未交付（失败/无效/草稿未定稿）→ 不扣
· 系统重试、修复补做 → 不重复扣（幂等键去重）
· 查看 / 保存 / 复制 / 下载 → 不扣
· 同一录音被多产品分析 → 各产品分别扣各自额度（基础链路 ASR/医生/咨询师分析不在计量内）
· 医生改字、保存草稿、自动保存 → 不扣（保存级程序化检查不算"完整质控"）
· 提交时复用了保存的质控结果（QualityRunID）→ 质控不扣
```

### 6.3 病历质控的特例（代码已确认）

```text
三种动作：
  自动保存（PATCH /working-draft） → 不做质控、不扣
  手动保存（POST /save）           → 跑保存级质控（程序化规则，不含大模型）→ 不扣轮次
  提交（POST /submit）             → 跑完成级质控（程序化 + 大模型语义，3 次调用）
                                    → 实际新跑 = 扣 1 轮
                                    → 复用 QualityRunID = 不扣

打回重提 → 每次实际新跑都扣 1 轮（跑了就记）。
安抚打回多的客户 → 赠送质控增量包。
```

### 6.4 扣量引擎（伪流程）

```text
交付成功事件（幂等键）
  → 定位额度：tenant + product_code + unit
  → 扣 rollover_bal 优先，再扣试用额度（trial），再扣正式额度（official）
  → 事务内：写 usage_events + 更新 balance
  → 余额不足 → 记欠扣、拒绝交付（100% 暂停）
  → 触达阈值：扣后余额 ≤20% → 提醒；=0 → 暂停该产品交付
```

### 6.5 提醒与暂停

```text
80% 用完 → 系统提醒（站内 + 推送）
100% 用完 → 暂停对应产品的"交付"入口，购买增量包后恢复
进行中的服务允许跑完。
```

### 6.6 漏扣补偿与对账

**扣量失败兜底：**

```text
· 交付已成功、扣量失败 → 先写"欠扣"记录（usage_event 标记 retry_pending），交付照常
· 定时任务重试扣量，成功置为已扣；持续失败 → 运营告警，人工处理
```

**余额对账（防漂移）：**

```text
· 每日任务校验：balance == Σgrants − Σusage，不一致 → 告警 + 差异报告
· 额度层 × 归因层对账：某产品某时段的用量事件与归因层的交付记录比对，差集人工核对
```

## 7. 缴费流程

### 7.1 首购（单品 / 套餐 / 工牌）

```text
销售报价（官方报价单）
  → 下单 billing_orders（order_type=single/bundle/hardware）
  → 客户全款支付 billing_payments（pending）
  → 财务回款确认（confirmed）
  → 运营开通：订阅时间生效（首个产品开通日起算 12 个月，统一到期日）
               + 额度授予（source=purchase，记录 product_code / edition / quota_type=official）
  → 客户可用
```

### 7.2 增量包

```text
客户已购产品要加量
  → 下单 billing_orders（order_type=increment，items=整包 +20%）
  → 全款支付 → 回款确认
  → 运营下发：额度授予（source=purchase，到期日 = 统一到期日）
  → 中途购买：价格与额度都按剩余天数折算（不足 30 天按 30 天）
```

### 7.3 赠送（优惠的统一实现）

```text
申请（销售/商务，填客户、产品、数量、原因）
  → 审批 billing_approvals（商务/老板）
  → 下单 billing_orders（order_type=gift，payable_amount=0）
  → 运营下发：额度授予（source=gift，reason 必填）
  → 全程留痕 billing_audit_logs
```

```text
赠送的形态：赠送增量包（最常见）、赠送试用（限期增量包）、赠送工牌（硬件行金额 0）。
价格表不动，只是多授了一笔 0 元、带审批、带留痕的额度。
```

**审批口径（按包数，已定）：**

```text
· 赠送 ≤ 1 个增量包 → 运营直接挂（订单记原因 + 操作人）
· 赠送 > 1 个增量包 → 老板审批
· 系统自动按价目表换算金额，用于展示和老板决策
审批时效承诺：24 小时内处理（销售安抚场景不能拖）。
```

**试用包（quota_type=trial 的固定形态）：**

```text
· 试用 = 下发一个"试用额度包"（quota_type=trial）
· 默认规格：任一单品 7 天，额度 = 标准年额度 × 7/365（向上取整，兜底最小值待定）
· 与生产现状对齐：旧试用是"全租户 7 天 + 录音条数限额"，
  新版按产品发试用额度，不再用全租户录音条数
· 需销售申请 → 商务审批 → 运营下发
· 商务口径不变：试用需申请、视情况提供，不对外承诺免费试用
· 试用额度到期清零：不结转、不退款、不折现
```

### 7.4 退款

```text
开通前 → 可全额退（payment → refunded，order → refunded）
"开通"的时点 = 额度下发（grant）完成：下发前可退，下发后不退款
开通后 / 已使用额度 → 不退款
工牌：未拆封 7 天内可退；拆封不退
```

### 7.5 折算（中途加购）

```text
金额 = 年价 × 剩余天数 ÷ 365
额度 = 标准额度 × 剩余天数 ÷ 365
不足 30 天按 30 天计
```

### 7.6 结转（续费）

```text
到期时：
  不续费 → 余额清零（entitlement.status=cleared）
  续费   → 新周期：余额快照为"结转"（rollover_bal），新周期授新额度
          扣量先扣 rollover_bal，再扣当期
          第二个周期结束，rollover_bal 未扣完 → 清零，不再滚存

续费窗口：到期后 30 天内补续视为"续费"，可触发结转；超过 30 天视为新购，不结转。
结转由定时任务触发：到期日当天跑，失败自动重跑并告警运营。
```

### 7.7 到期与暂停

```text
额度 100% 用完 → 暂停对应产品交付（不影响已交付结果的查看）
服务期到期 → 订阅 expired → 所有额度进入结转/清零流程
```

### 7.8 纠正（余额调整）流程

```text
什么情况：错扣（系统 bug）、误发（下发放错对象/数量）、客户异议成立

流程：
  运营提交纠正单（原因、证据、调整方向与数量）
  → 老板/财务复核（双人，纠正必须有第二人确认）
  → 执行：source=correction 的 grant（退回）或负向 usage（冲正）
  → 全程留痕 billing_audit_logs

禁止：任何直连数据库改余额的操作。
```

### 7.9 客户异议流程（与"异议期 7 个工作日"对齐）

```text
客户提出异议（站内 / 销售转达）
  → 运营核对：拉 usage_events + 归因记录，逐条对给客户看
  → 成立 → 走 7.8 纠正流程退回
  → 不成立 → 出具明细（哪条录音/病历、扣了多少、对应规则）
SLA：7 个工作日内答复。
```

### 7.10 服务时效（SLA，建议值）

| 事项 | 承诺 |
|---|---|
| 回款确认 | ≤ 1 个工作日 |
| 开通 / 额度下发 | 回款确认后 ≤ 1 个工作日 |
| 赠送审批 | ≤ 24 小时 |
| 客户异议答复 | ≤ 7 个工作日 |
| 工牌发货 | ≤ 3 个工作日 |
```

## 8. 状态机

### 8.1 订单（billing_orders）

```text
created → paid → settled → （refunded | 完成）
            ↘ cancelled（未付取消）
gift 单：created → approval(approved) → granted（无 paid 环节）
```

### 8.2 支付（billing_payments）

```text
pending → confirmed → （refunded）
            ↘ 超期未付 → cancelled
```

### 8.3 订阅（tenant_subscriptions）

```text
active → expired → （renewed（触发结转）| terminated）
```

### 8.4 额度（product_entitlements）

```text
active → （用量 80% → 提醒）→ （用量 100% → paused）
paused → （买增量包 → active）
到期 → expired → （续费 → rollover）|（不续费 → cleared）
试用额度（quota_type=trial）：到期 → cleared（不结转、不退款）
```

### 8.5 审批（billing_approvals）

```text
pending → approved | rejected
```

## 9. 前端配套（剩余额度等展示数据）

### 9.1 医院侧（客户视角）

```text
· 每个产品还剩多少：赢客 400 小时 → 剩余 X 小时
· 已用/剩余、到期日
· 用量明细（每次交付扣了多少、对应哪条录音/病历）
· 80% 提醒、100% 暂停提示、买增量包入口
```

```text
数据来源：
  剩余额度   → product_entitlements.balance
  到期日     → tenant_subscriptions.expired_on
  用量明细   → entitlement_usage_events
只展示"自然单位额度"，不展示人民币、不展示成本。
```

### 9.2 运营侧（内部视角）

```text
· 订单 / 支付 / 发票查询
· 回款确认（手动发的入口）
· 额度授予（增量/赠送）与纠正
· 赠送审批流
· 租户余额与用量查询、到期/暂停列表
· 真实成本与毛利（用 gateway_call_records 归因层，与额度层对账）
```

### 9.3 销售侧

```text
· 报价计算器：输入产品/套餐/剩余天数 → 输出折算价格与额度
  （与订单计算同一套代码，销售不允许手算）
· 我的客户额度视图：销售名下客户的余额、到期日、用量趋势 → 催增购的抓手
```

### 9.4 一个产品多个单位的展示

```text
听写病历 = 病历份数 + 质控轮次 + 录音小时，三个单位：
· 客户页：三个数字并排 + 一句解释
  "一份病历 = 生成 1 次 + 约 2 轮质控，录音时长随病历走"
· 销售话术配套：
  "您买的是 2,500 份病历，每份含两轮质控预算，录音时长随病历扣"
```

## 11. 实施顺序建议

```text
第一阶段：额度 + 计量（product_entitlements / grants / usage_events + 交付判定 + 漏扣补偿 + 对账）
第二阶段：订单 + 支付 + 回款确认（含 price_list_version、佣金基数、手动开通/下发、权限矩阵）
第三阶段：赠送审批（分级阈值 + 24h 时效）+ 审计留痕 + 纠正/异议流程
第四阶段：到期/结转/折算 + 续费窗口 + 提醒/暂停
第五阶段：前端三端（医院侧剩余额度 + 销售侧报价器/客户视图 + 运营后台全功能）
```

> 本设计是业务与技术之间的桥。评审通过后，由实现方在此基础上拆开发计划与迁移脚本。

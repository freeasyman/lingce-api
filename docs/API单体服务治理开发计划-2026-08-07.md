# API单体服务治理开发计划

日期：2026-08-07

## 1. 目标

在不拆微服务的前提下，完成 lingce-api 的单体治理：

- 收紧系统日志写入口
- 统一鉴权与租户隔离
- 收敛路由注册和模块边界
- 保持现有业务路径尽量不变

## 2. 范围

### 2.1 本期要做

- `POST /api/v1/inst/system-logs` 加认证和字段约束
- 新增内部写日志入口
- 统一路由鉴权声明
- 统一租户 scope 处理规则
- 整理 `support`、`recording` 等大模块的边界

### 2.2 本期不做

- 不拆微服务
- 不全量重写现有路由
- 不改数据库业务表结构大面
- 不处理 `splitdemo` 的临时问题

## 3. 里程碑

### M1. 系统日志收口

目标：让审计日志写入口可控、可信。

交付：

- `inst/system-logs` 增加 JWT 鉴权
- 新增 `internal/system-logs`
- 服务端内部写日志不再依赖匿名入口

验收：

- 未登录请求无法写入系统日志
- 内部调用可通过内部 token 写入
- 日志字段存在白名单和敏感信息清洗

### M2. 鉴权与租户隔离统一

目标：让路由、鉴权、租户边界走同一套规则。

交付：

- 新接口统一走声明式路由注册
- 统一 `AuthMode / UserTypes / TenantMode / Permission`
- 清理高风险模块里的手写鉴权分支

验收：

- 新增接口不再默认裸露
- handler 中不再新增散落的身份判断
- tenant scope 的处理路径清晰且一致

### M3. 模块边界收敛

目标：降低单体后续扩展的耦合成本。

交付：

- `support` 模块按职能细分
- `recording` 模块按子域拆文件
- 保持 store 的单表职责更明确

验收：

- 大模块职责说明清晰
- 同一张核心表的访问点减少
- 新功能能明确落到对应子域

## 4. 任务拆分

### 4.1 系统日志治理

1. 给 `POST /api/v1/inst/system-logs` 加 JWT。
2. 校验 `employee/mobile` 用户类型。
3. 服务端补齐 tenant/actor 快照。
4. 新增 `POST /api/v1/internal/system-logs`。
5. 给日志写入增加请求体大小限制和字段白名单。
6. 清洗敏感字段，避免 token、密码、secret 原样落库。

### 4.2 路由统一

1. 统一路由声明结构。
2. 把新接口统一注册到声明式路由器。
3. 保留旧路径不变。
4. 清理模块内重复的 `middleware.Auth` 包装。
5. 对运营类接口补齐 `AllowedUserTypes` 和 `TenantMode`。

### 4.3 租户隔离统一

1. 统一 scope 计算入口。
2. 明确 admin / employee / mobile 的 tenant 访问规则。
3. 强制 store/service 显式接收 tenant 条件。
4. 对跨租户查询使用显式 scope，不允许隐式全局查询。

### 4.4 模块边界整理

1. 梳理 `support` 模块子职责。
2. 梳理 `recording` 模块子职责。
3. 将超长文件继续拆分为同 package 下的子文件。
4. 避免一个模块继续吞掉多个业务域。

## 5. 优先级

### P0

- 系统日志写入口收口
- 内部日志入口补齐

### P1

- 统一路由鉴权模型
- 收敛 tenant scope 规则

### P2

- 模块边界细化
- 文档同步和旧说明清理

## 6. 推荐执行顺序

1. 先改系统日志写入口。
2. 再引入内部写日志入口。
3. 再统一路由注册和鉴权声明。
4. 再收敛 tenant scope。
5. 最后整理大模块文件边界。

## 7. 风险与控制

### 风险 1：改入口影响现有调用方

控制：

- 保留旧路径
- 先兼容，再收紧
- 给内部调用准备单独入口

### 风险 2：统一鉴权引发误伤

控制：

- 先覆盖高风险模块
- 先做只读接口验证
- 逐步迁移，不一次切全量

### 风险 3：模块拆分导致引用混乱

控制：

- 保持同 package 内拆文件
- 不轻易跨包搬运业务逻辑
- 先理清职责，再动代码

## 8. 验收清单

- `go test ./...` 通过
- 系统日志写入入口已收口
- 内部日志入口已落地
- 新路由默认走统一鉴权模型
- tenant scope 规则不再散落
- 大模块职责边界更清楚

## 9. 说明

这是一份单体治理计划，不包含微服务拆分方案。
后续所有新增功能，应优先按这份计划下的路由、鉴权、租户和模块边界规范执行。

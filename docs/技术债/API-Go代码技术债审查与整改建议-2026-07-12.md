# API Go代码技术债审查与整改建议

日期：2026-07-12
仓库：`lingce-api`

## 1. 审查范围与结论

本次对 `lingce-api` 的 Go 代码做了完整编译与结构性检查，重点关注：
- 是否存在未参与编译的 Go 代码
- 是否存在严重运行风险
- 是否存在需要系统梳理的结构性技术债

已执行的检查：
- `go test ./...`
- `go build ./...`
- `go vet ./...`
- `//go:build` / `// +build` 条件编译扫描

结论：
- 当前仓库内未发现“没有参与编译”或“主程序能编但其他包实际上已损坏”的 Go 代码。
- 当前 API 可以编译、可以运行、可以发布。
- 但存在若干中高风险技术债，主要集中在：
  - 租户/组织边界的错误默认行为
  - 启动链路承载一次性数据修复逻辑
  - 路由注册方式分裂且缺少冲突防护
  - 参数解析和错误处理不统一

整体判断：
- 目前不是“代码已坏掉”的状态。
- 但已经进入“功能持续迭代会不断放大风险，值得专门整治一轮”的阶段。

---

## 2. 主要问题清单

### 2.1 管理员查询缺少租户参数时，存在硬编码租户兜底

位置：
- `internal/employee/handler.go`

现象：
- 管理员访问员工列表接口时，如果没有传 `tenant_id`，代码会：
  - 优先尝试用 `claims.TenantID`
  - 如果还没有，则直接回退到 `tenantID = 1`

示例位置：
- `internal/employee/handler.go:47-57`

风险：
- 这会把“参数缺失”变成“返回 1 号租户数据”。
- 本质上属于错误默认行为，不是安全兜底。
- 在多租户/组织隔离系统里，这类逻辑非常危险，容易导致：
  - 查错租户
  - 串租户
  - 排查时误以为是前端问题或数据问题

判断：
- 这是当前最优先清理的问题之一。

建议：
- 对管理员接口明确约束：
  - 必填租户就返回 `400`
  - 没有租户上下文就返回 `403`
  - 禁止任何固定租户默认值

---

### 2.2 启动链路中挂载一次性历史修复逻辑

位置：
- `cmd/lingce-api/main.go`

现象：
- API 启动时会执行 `tenantStore.RealignTrialTenantValidity(ctx)`
- 如果执行失败，直接 `os.Exit(1)`，服务无法启动

示例位置：
- `cmd/lingce-api/main.go:141-145`

风险：
- 这段逻辑本质上属于：
  - 历史数据修复
  - 一次性 backfill
  - 兼容性对齐
- 它不应长期停留在 API 主启动链路中。
- 一旦线上遇到：
  - 脏数据
  - 锁等待
  - 字段不一致
  - 事务失败
- 会直接把整个 API 拉死。

判断：
- 这是典型的“把 migration/backfill 和服务启动职责混在一起”。
- 适合短期救火，不适合作为长期架构。

建议：
- 将其迁移为以下三种之一：
  1. 一次性脚本
  2. 带幂等记录的 migration
  3. 显式后台任务
- API 启动链路只保留必要初始化，不承载历史修复。

---

### 2.3 路由注册体系分裂，存在重复注册与冲突风险

位置：
- `internal/router/router.go`
- 多个模块的 `RegisterRoutes`
- `cmd/lingce-api/main.go`

现象：
- 代码库中同时存在两套路由组织方式：
  1. 声明式路由注册器 `internal/router/router.go`
  2. 各模块直接对 `http.ServeMux` 手工 `mux.Handle(...)`
- 但主程序仍主要依赖各模块手工注册。
- 这意味着系统并未真正收敛到统一路由模型。

示例位置：
- `internal/router/router.go:30-60`
- `internal/rbac/handler.go:25-70`
- `cmd/lingce-api/main.go:148` 之后的大量模块注册

风险：
- 路由管理分散，容易出现：
  - 重复注册
  - 方法不一致
  - 路径冲突
  - 迁移时遗漏
- 你之前碰到过的 `ServeMux` 重复注册 panic，本质上就是这类问题的直接表现。

判断：
- 这不是单点 bug，而是结构性问题。
- 如果不梳理，后续模块越多，重复注册与边界不一致的问题会越来越难控。

建议：
- 统一为一种注册方式：
  - 要么全部使用声明式路由注册
  - 要么全部使用 `ServeMux` 手工注册
- 不建议长期混用。
- 同时增加“启动期路由冲突检测”。

---

### 2.4 同一项目中混用 Go 1.22 方法路由与手工方法判断

位置：
- `internal/recording/handler.go`

现象：
- 大部分接口已经使用 Go 1.22 风格：
  - `mux.Handle("POST /path", ...)`
- 但仍有个别路径只注册路径，不指定方法，再在 handler 内手工判断 `r.Method`

示例位置：
- `internal/recording/handler.go:86-94`

风险：
- 同一路由体系内出现两种写法，会导致：
  - 405/404 行为不一致
  - 路由冲突排查复杂化
  - 未来统一迁移成本增加

判断：
- 单点风险不算特别高，但明显属于应收口的风格债。

建议：
- 在已升级到 Go 1.22 方法路由后，统一改为方法显式注册。
- 避免继续保留“路径注册 + 手工判方法”的旧写法。

---

### 2.5 审计/变更日志失败时被静默弱化处理

位置：
- `internal/sysconfig/store.go`

现象：
- 在设置功能覆盖项时，主数据写入成功后，如果变更日志写入失败，只 `fmt.Printf` 输出，不中断流程。

示例位置：
- `internal/sysconfig/store.go:910-919`

风险：
- 结果会变成：
  - 功能配置已修改
  - 审计日志可能丢失
- 对后续排查权限、功能变化、责任归属会造成困难。
- 另外这里用 `fmt.Printf` 也不符合当前项目的统一日志风格。

判断：
- 不是立即阻断级问题，但属于典型的“观测性债务”。

建议：
- 明确该日志的业务级别：
  - 如果审计日志必须存在，则纳入事务失败回滚
  - 如果允许降级，则至少通过统一日志系统 `slog` 输出结构化告警
- 不建议继续使用 `fmt.Printf`

---

### 2.6 参数解析大量静默吞错，接口行为不透明

位置：
- 多个 handler，尤其是：
  - `internal/employee/handler.go`
  - `internal/mobile/handler.go`
  - `internal/customer/handler.go`
  - `internal/tenant/handler.go`
  - `internal/organization/...`

现象：
- 大量代码模式如下：
  - `page, _ := strconv.Atoi(...)`
  - `tenantID, _ := strconv.ParseInt(...)`
  - `bool` 参数自行比较字符串
- 解析失败时通常不会返回 `400`，而是变成零值或默认值继续执行。

风险：
- 容易产生：
  - 接口不报错但结果不符合预期
  - 前后端联调成本上升
  - 参数写错时排查困难
- 这类问题通常不会立刻炸，但会持续制造“隐性错误”。

判断：
- 这是广泛分布的风格/行为债务，值得尽快收口。

建议：
- 增加统一参数解析 helper，例如：
  - `parseIntQuery`
  - `parseOptionalIntQuery`
  - `parsePage`
  - `parsePageSize`
  - `parseBoolQuery`
- 对非法值明确返回 `400`，不要静默吞掉。

---

### 2.7 辅助脚本风格零散，但不构成当前主链路阻断

位置：
- `scripts/cmd/...`

现象：
- 脚本入口混用：
  - `panic`
  - `log.Fatal`
  - `os.Exit`
- 日志风格与参数校验风格不统一。

风险：
- 主要影响可维护性，不直接影响主 API 运行。
- 但会增加后续运维脚本、数据脚本的理解和复用成本。

判断：
- 属于后续可整理项，不是本轮最优先问题。

建议：
- 后续统一脚本脚手架：
  - 配置加载方式统一
  - 日志输出统一
  - 退出码与错误信息统一

## 3. 严重程度分级

### P0：必须优先处理

1. 租户默认值与错误兜底清理
- 禁止任何默认回退到固定租户
- 缺参数即报错
- 无上下文即拒绝

2. 启动链路剥离一次性 backfill / 历史修复
- 启动失败不能依赖历史修复成功与否

3. 路由注册冲突治理
- 统一注册模式
- 增加启动期冲突检测

### P1：应尽快处理

1. 参数解析标准化
2. 错误处理与日志输出统一
3. 权限/租户边界收口到统一 helper 或中间件

### P2：可排期处理

1. `scripts/cmd` 脚手架统一
2. 大模块按子域拆文件
3. 增加更系统的自动检查与集成测试

---

## 4. 建议整改方案

### 阶段一：先控风险

目标：先消灭“容易查错租户、容易起不来、容易重复注册”这类问题。

建议动作：
1. 清理所有固定租户/静默兜底逻辑
2. 将历史修复逻辑从 `main` 中迁移出去
3. 增加路由注册冲突检查
4. 统一最核心模块的参数错误返回行为

建议先覆盖模块：
- `employee`
- `tenant`
- `customer`
- `organization`
- `dashboard`

### 阶段二：统一行为

目标：让接口层行为更可预期。

建议动作：
1. 建公共参数解析 helper
2. 建统一错误返回规范
3. 收口 `tenant scope` 判定逻辑
4. 替换散落的 `fmt.Printf`、零散错误输出

### 阶段三：结构整理

目标：降低后续迭代的复杂度。

建议动作：
1. 统一路由注册体系
2. 拆分超长 handler / service / store
3. 整理 `scripts/cmd` 结构
4. 补关键集成测试

---

## 5. 建议新增的质量门禁

建议至少补充以下检查为默认流程：
- `go test ./...`
- `go vet ./...`
- 路由冲突检测
- 关键租户隔离接口的集成测试
- 参数非法值测试

建议在本地和 CI 中都默认执行，而不是只依赖主入口编译。

---

## 6. 最终判断

当前 `lingce-api`：
- 不是“代码编不过”的状态
- 不是“立刻要重构重写”的状态
- 但已经存在明确的结构性技术债，需要一次针对性梳理

最危险的不是代码风格不好，而是以下三类错误默认行为：
1. 租户边界错误默认值
2. 启动期承担历史修复职责
3. 路由体系分裂导致冲突与不一致

建议将本次整改视为“稳定性与边界治理”专项，而不是零散修 bug。

# 企业微信自建应用接入清单与提醒规则总表

更新时间：2026-07-19

适用范围：

- 新企业客户接入灵策员工端企业微信自建应用。
- 企业微信卡片消息推送，包括录音分析完成、任务提醒、成交机会提醒。
- 当前是多客户共用一套灵策 API、每个客户各自创建一套企业微信自建应用。

## 1. 新企业客户接入时的信息清单

### 1.1 客户企业微信管理员需要提供给灵策

| 信息 | 从哪里获取/配置 | 用途 | 是否必需 |
| --- | --- | --- | --- |
| 企业 ID `CorpID` | 企业微信管理后台 > 我的企业 | 区分不同客户企业；用于 OAuth 登录、换取企业 access_token、回调识别 | 必需 |
| 自建应用 `AgentId` | 企业微信管理后台 > 应用管理 > 自建应用详情 | 标识客户自己的灵策应用；用于 OAuth 授权和发送应用消息 | 必需 |
| 自建应用 `Secret` | 自建应用详情页 | 服务端换取企业 access_token，用于读取企业微信用户信息和发送消息 | 必需 |
| 应用可见范围 | 自建应用详情页 | 决定哪些员工能看到并使用灵策应用 | 必需配置 |
| 通讯录手机号 | 企业微信通讯录 | 企业微信自动登录会读取员工手机号，与灵策员工手机号匹配 | 必需维护准确 |
| 可信域名配置结果 | 自建应用详情页 | 确认 `employee.khgl.xyz` 已配置并通过 | 必需 |
| 接收消息服务器 `Token` | 自建应用详情页 > 接收消息服务器配置 | 企业微信回调签名校验；客户可生成后提供给灵策保存 | 如启用回调则必需 |
| 接收消息服务器 `EncodingAESKey` | 自建应用详情页 > 接收消息服务器配置 | 企业微信回调加解密；客户可生成后提供给灵策保存 | 如启用回调则必需 |

注意：

- `Secret`、`Token`、`EncodingAESKey` 都是敏感信息，只能通过安全渠道交付，不应截图群发、写入普通文档或提交代码仓库。
- 企业微信通讯录手机号必须和灵策机构员工手机号一致，否则员工从企业微信进入会被拒绝登录。
- 如果企业微信没有返回手机号，或同一租户内手机号无法唯一匹配员工，登录会失败，需要管理员先修正通讯录或灵策员工资料。

### 1.2 灵策需要提供给客户管理员填写

| 配置项 | 填写值/规则 | 企业微信填写位置 | 用途 |
| --- | --- | --- | --- |
| 应用主页地址 | `https://employee.khgl.xyz/login?corp_id={客户CorpID}&agent_id={客户AgentId}` | 自建应用 > 应用主页 | 员工从企业微信工作台进入灵策员工端 |
| 可信域名 | `employee.khgl.xyz` | 自建应用 > 网页授权及 JS-SDK | 允许企业微信 OAuth 跳转到灵策员工端 |
| 接收消息服务器 URL | `https://employee.khgl.xyz/api/v1/wecom/callback` | 自建应用 > 接收消息服务器 | 企业微信回调验证和事件接收入口 |
| OAuth 授权能力 | 前端使用 `snsapi_privateinfo` | 代码实现，客户无需填写 | 获取 `user_ticket`，服务端读取用户手机号 |

填写要求：

- 应用主页地址建议必须带 `corp_id` 和 `agent_id`。这是多客户共用同一个 H5/API 时识别客户自建应用的最稳方案。
- 企业微信卡片消息详情链接由灵策服务端生成，会按收件人的企业微信绑定自动补充 `corp_id` 和 `agent_id`。
- 接收消息服务器 URL 是统一入口，灵策服务端根据企业微信回调内容、签名和已保存的客户自建应用配置匹配具体租户。

### 1.3 灵策后台需要保存

灵策平台侧需要为每个客户保存一条企业微信自建应用配置：

| 字段 | 说明 |
| --- | --- |
| `tenant_id` | 灵策内部租户/机构 ID |
| `corp_id` | 客户企业微信企业 ID |
| `corp_name` | 企业名称，便于运营识别 |
| `agent_id` | 客户自建应用 AgentId |
| `secret_ciphertext` | 加密后的应用 Secret |
| `token` | 企业微信回调 Token |
| `encoding_aes_key` | 企业微信回调 EncodingAESKey |
| `home_url` | 员工端 H5 入口 |
| `trusted_domain` | 一般为 `employee.khgl.xyz` |
| `enabled` | 是否启用该客户自建应用 |

## 2. 企业微信自动登录原则

员工从企业微信进入灵策时，必须使用企业微信身份自动登录，不允许复用之前手机密码登录过的本地账号。

当前流程：

1. H5 检测到企业微信环境，或入口 URL 带 `code/corp_id/agent_id`。
2. H5 清理旧本地登录态，并发起企业微信 OAuth。
3. 企业微信回跳 H5，返回授权 `code`。
4. H5 调用 `POST /api/v1/wecom/oauth/login`，传入 `code` 和 `corp_id`。
5. API 根据 `corp_id` 查到该客户自建应用配置。
6. API 使用该应用 `Secret` 换企业 access_token。
7. API 用 `code` 获取企业微信用户 `UserId` 和 `user_ticket`。
8. API 读取企业微信用户手机号。
9. API 用手机号匹配同租户唯一灵策员工。
10. 匹配成功后签发员工端 token；匹配失败则拒绝登录。

关键边界：

- 企业微信入口不允许员工手工输入手机号密码绕过匹配。
- 手机号不匹配时，应提示联系管理员，不应展示其他机构或其他员工数据。
- 旧登录态不可信，企业微信环境下每次入口都应校验当前企业微信身份。

## 3. 当前会触发哪些企业微信提醒

当前企业微信提醒分为两类：

- 普通工作提醒：由 `lingce-worker` 推送，包括录音分析完成、新任务、今日待办、即将逾期/已逾期。
- 成交机会提醒：由 `lingce-api` 创建业务提醒，再通过企业微信推送。

### 3.1 录音分析已完成

| 项 | 当前实现 |
| --- | --- |
| `message_scene` | `recording_analysis_completed` |
| 标题 | `录音分析已完成` |
| 正文 | 默认：`您有 1 条新录音已完成分析，请及时查看。`；如果录音有发生时间，则显示录音时间 |
| 接收人 | 录音所属员工 `recordings.employee_id` |
| 详情页 | `https://employee.khgl.xyz/recordings/{recording_id}` |
| 按钮 | `查看详情` |
| 去重 | `recording-analysis-completed:{recording_id}` |

触发规则：

- worker 完成录音分析后调用 `emitAnalysisNotifications`。
- 如果录音存在有效 `employee_id`，则给该员工发送一条企业微信卡片。
- 同一条录音按 `recording_id` 去重，不应重复发送同一条完成提醒。

规则性质：

- 触发时机、标题、正文模板、按钮文案、接收人规则都是代码硬编码。
- 不支持后台配置是否发送，也不支持按角色/科室配置不同模板。

### 3.2 新任务提醒

| 项 | 当前实现 |
| --- | --- |
| `message_scene` | `new_tasks_summary` |
| 标题 | `收到新任务` |
| 正文 | `您有 {count} 个新的跟进任务，请及时处理。` |
| 接收人 | 新任务负责人，目前来自分析后的 `FollowupAssistantID` |
| 详情页 | `https://employee.khgl.xyz/tasks` |
| 按钮 | `查看任务` |
| 去重 | `new-tasks:{recording_id}:{employee_id}` |

触发规则：

- worker 完成录音分析后读取分析后摘要。
- 当 `FollowupCreatedCount > 0` 且 `FollowupAssistantID > 0` 时发送。
- 按员工聚合发送，不会每个任务发一条。

规则性质：

- 触发条件、接收人、聚合方式、消息模板都是代码硬编码。
- 当前不是后台可配置规则。

### 3.3 今日待办提醒

| 项 | 当前实现 |
| --- | --- |
| `message_scene` | `today_tasks_summary` |
| 标题 | `今日待办提醒` |
| 正文 | `您今天还有 {count} 个待办任务，请及时处理。` |
| 接收人 | 当天有待办任务的员工 |
| 详情页 | `https://employee.khgl.xyz/tasks?tab=pending` |
| 按钮 | `查看待办` |
| 去重 | `today-tasks:{biz_date}` |

触发规则：

- worker 定时任务运行时，只有当前小时等于配置的提醒小时才执行；非法配置时默认 9 点。
- 查询 `recording_tasks` 中状态为 `pending`、`assigned`、`in_progress` 的任务。
- 只统计 `due_at` 在当天 00:00 到次日 00:00 之间的任务。
- 按 `assigned_to` 分组，给每个员工发送聚合提醒。

规则性质：

- 提醒小时可由 worker 配置影响。
- 任务状态范围、到期日范围、标题和正文模板是代码硬编码。

### 3.4 即将逾期/已逾期任务提醒

| 项 | 当前实现 |
| --- | --- |
| `message_scene` | `due_soon_summary` 或 `overdue_summary` |
| 标题 | `任务即将逾期` 或 `任务已逾期` |
| 正文 | 即将逾期：`您有 {count} 个任务即将逾期，请尽快处理。`；已逾期：`您有 {count} 个任务已逾期，请立即处理。` |
| 接收人 | 有即将逾期或已逾期任务的员工 |
| 详情页 | `https://employee.khgl.xyz/tasks?tab=pending` |
| 按钮 | `查看任务` |
| 去重 | `{scene}:{bucket}`，其中 `bucket` 是当前时间按 4 小时截断后的时间桶 |

触发规则：

- worker 定时查询 `recording_tasks`。
- 任务状态必须是 `pending`、`assigned`、`in_progress`。
- `due_at <= NOW() + INTERVAL '1 hour'` 的任务会进入提醒范围。
- 其中 `due_at >= NOW()` 且 `due_at <= NOW() + INTERVAL '1 hour'` 统计为即将逾期。
- 其中 `due_at < NOW()` 统计为已逾期。
- 如果同一员工同时有已逾期和即将逾期任务，优先使用 `overdue_summary` 和“任务已逾期”的文案。

规则性质：

- 查询范围、1 小时窗口、4 小时去重桶、消息模板都是代码硬编码。
- 查询 limit 可由 worker 配置影响。

### 3.5 成交机会提醒

| 项 | 当前实现 |
| --- | --- |
| `message_scene` | `opportunity_alert` |
| 提醒类型 | `opportunity_not_advanced` |
| 业务含义 | 客户有明确意向，但本次沟通没有锁定下一步 |
| 默认标题 | `客户有明确意向，但没有锁定下一步` |
| 默认优先级 | `high` |
| 详情页 | `https://employee.khgl.xyz/opportunity-alerts/{alert_id}` |
| 按钮 | `查看补救建议` |
| 去重 | `tenant:{tenant_id}:recording:{recording_id}:type:{alert_type}` |

触发规则：

- 当录音状态更新为 `completed` 时，API 尝试基于该录音创建成交机会提醒。
- 只在分析结果中命中 `意向明确未成交` 时创建提醒。
- 当前读取字段顺序：
  - `analysis_result.deal_outcome.result`
  - `analysis_result.persuasive.deal_status`
  - `analysis_result.deal_status`
- 如果最终文本包含 `意向明确未成交`，则生成提醒；否则不生成。

接收人规则：

- 默认接收人是录音所属员工 `recordings.employee_id`，接收类型为 `owner`。
- 机构后台“成交机会提醒配置”里配置的抄送人也会收到，接收类型为 `cc`。
- 抄送人可以查看提醒详情；是否可处理由 H5 详情页权限逻辑控制。

提醒内容来源：

| 内容 | 优先取值 |
| --- | --- |
| 摘要 | `status_summary`、`conversation_summary`、证据文本 |
| 原因 | `concern_strategy.stuck_point_headline`、`concern_strategy.real_reason`、`analysis_summary.conversion_opportunity`、`analysis_result.conversion_opportunity`、`persuasive.stuck_point_headline` |
| 客户顾虑 | `concern_strategy.real_reason`、`persuasive.real_concern`、`persuasive.real_reason`、`analysis_result.core_blockers` |
| 证据 | `deal_outcome.evidence`、`concern_strategy.evidence`、`status_summary`、`conversation_summary` |
| 建议动作 | `concern_strategy.next_action`、`analysis_summary.next_action`、`analysis_summary.conversion_opportunity`、`analysis_result.follow_up_advice` |
| 建议话术 | `concern_strategy.script`、`concern_strategy.suggested_script`、`analysis_summary.suggested_script` |

规则性质：

- 触发时机、提醒类型、命中文本、字段读取顺序、默认文案、优先级、按钮文案都是代码硬编码。
- 当前后台可配置的是抄送关系，不是触发规则。

## 4. 当前哪些规则是配置的，哪些是写死的

### 4.1 已配置化

| 配置 | 位置/来源 | 影响 |
| --- | --- | --- |
| 企业微信自建应用配置 | 灵策平台侧 `tenant_wecom_apps` | 决定某个租户是否可企业微信登录和推送 |
| 员工企业微信绑定 | `wecom_user_bindings`，可自动按手机号绑定 | 决定某个员工是否能自动登录、是否能收到企业微信消息 |
| 成交机会提醒抄送关系 | 机构后台“成交机会提醒配置”，表 `opportunity_alert_cc_rules` | 决定某员工的成交机会提醒额外抄送给谁 |
| 今日待办提醒小时 | worker 配置 | 决定今日待办汇总在哪个小时触发 |
| 逾期提醒查询 limit | worker 配置 | 控制定时任务单次扫描上限 |

### 4.2 当前硬编码

| 规则 | 当前状态 |
| --- | --- |
| 录音分析完成是否推送 | 硬编码发送 |
| 新任务是否推送 | 硬编码：分析后有新任务则发送 |
| 今日待办统计任务状态 | 硬编码：`pending`、`assigned`、`in_progress` |
| 即将逾期窗口 | 硬编码：1 小时内 |
| 逾期去重时间桶 | 硬编码：4 小时 |
| 成交机会命中关键词 | 硬编码：`意向明确未成交` |
| 成交机会提醒优先级 | 硬编码：`high` |
| 企业微信消息标题、正文、按钮文案 | 硬编码 |
| 不同角色/部门差异化提醒 | 当前不支持 |
| 消息模板配置 | 当前不支持 |
| 通用规则引擎 | 当前不支持 |

## 5. 实施检查清单

新客户上线前至少检查以下项目：

1. 灵策后台已创建该租户的企业微信自建应用配置，且 `enabled = true`。
2. 客户企业微信应用主页已配置为灵策提供的员工端 H5 地址。
3. 客户企业微信可信域名已配置 `employee.khgl.xyz`。
4. 如启用回调，接收消息服务器 URL、Token、EncodingAESKey 已配置并验证通过。
5. 应用可见范围包含需要使用灵策的员工。
6. 企业微信通讯录手机号与灵策员工手机号一致。
7. 至少用一个员工账号从企业微信工作台进入，验证自动登录成功。
8. 至少触发一条企业微信卡片消息，验证点击后能进入对应 H5 详情页。
9. 对成交机会提醒，如需抄送，先在机构后台配置抄送关系。
10. 如果员工收不到消息，优先检查员工是否在应用可见范围内、是否存在企业微信绑定、是否有手机号匹配。

## 6. 当前产品边界

当前企业微信提醒不是通用消息中心，也不是可视化规则引擎。

当前设计原则：

- 企业微信是触达渠道，不是业务数据主表。
- 录音/任务类提醒由 worker 直接触发。
- 成交机会提醒使用专门业务表 `opportunity_alerts` 承载，企业微信只是推送入口。
- 后台当前只配置“谁额外收到成交机会提醒”，不配置“什么内容触发提醒”。

后续如果要增强配置化，建议按以下顺序推进：

1. 增加每类提醒的启停开关。
2. 增加成交机会提醒的命中词或分析结果枚举配置。
3. 增加不同角色/部门的接收策略。
4. 增加消息模板配置。
5. 最后再考虑通用规则引擎和消息中心。

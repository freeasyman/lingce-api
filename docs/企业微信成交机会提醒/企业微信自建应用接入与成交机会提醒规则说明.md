# 企业微信自建应用接入与成交机会提醒规则说明

更新时间：2026-07-18

## 1. 新企业客户接入企业微信自建应用

当前方案是“多个客户共用一套灵策 API，每个客户在自己的企业微信里创建一套自建应用”。灵策通过客户提供的企业微信自建应用配置，完成该客户员工端 H5 自动登录、企业微信消息推送和应用回调。

### 1.1 客户企业微信管理员需要提供给灵策的信息

客户需要在企业微信管理后台创建自建应用，并把以下信息提供给灵策：

| 信息 | 获取位置 | 用途 | 是否必需 |
| --- | --- | --- | --- |
| 企业 ID `CorpID` | 企业微信管理后台 > 我的企业 | 标识客户企业，用于 OAuth 登录、获取企业 access_token、区分不同客户应用 | 必需 |
| 应用 `AgentId` | 企业微信管理后台 > 应用管理 > 自建应用 | 标识客户自建应用，用于 OAuth 授权和消息推送 | 必需 |
| 应用 `Secret` | 自建应用详情页 | 服务端换取企业 access_token，用于读取企业微信用户信息和发送应用消息 | 必需 |
| 应用可见范围 | 自建应用详情页 | 决定哪些员工能从企业微信工作台看到并使用灵策应用 | 必需配置 |
| 可信域名 | 自建应用详情页 | 企业微信 OAuth 页面域名校验 | 必需配置 |
| 接收消息服务器 `Token` | 自建应用详情页 > 接收消息 | 企业微信回调签名校验 | 如启用回调则必需 |
| 接收消息服务器 `EncodingAESKey` | 自建应用详情页 > 接收消息 | 企业微信回调加解密 | 如启用回调则必需 |
| 企业通讯录手机号 | 企业微信通讯录 | 灵策企业微信自动登录会读取企业微信手机号，与灵策员工手机号匹配 | 必需维护正确 |

注意：

- `Secret` 属于敏感信息，只应通过安全渠道交付，不应写入文档、截图群发或提交到代码仓库。
- 企业微信通讯录里的员工手机号必须与灵策系统里的员工手机号一致，否则自动登录会失败。
- 如果企业微信没有返回手机号，灵策会拒绝登录，并提示联系管理员检查企业微信通讯录手机号和灵策员工手机号。

### 1.2 灵策需要提供给客户管理员填写的信息

客户管理员需要在企业微信自建应用中填写以下灵策侧信息：

| 配置项 | 当前值/规则 | 填写位置 | 用途 |
| --- | --- | --- | --- |
| 应用主页地址 | `https://employee.khgl.xyz/login?corp_id={客户CorpID}&agent_id={客户AgentId}` | 自建应用 > 应用主页 | 员工从企业微信工作台点击应用后进入灵策员工端 |
| 可信域名 | `employee.khgl.xyz` | 自建应用 > 网页授权及 JS-SDK | 允许企业微信 OAuth 跳转到灵策员工端 |
| 接收消息服务器 URL | `https://employee.khgl.xyz/api/v1/wecom/callback` | 自建应用 > 接收消息服务器 | 企业微信回调验证和事件接收入口 |
| OAuth 授权范围 | 灵策前端使用 `snsapi_privateinfo` | 由灵策前端实现，客户无需填写 | 获取 `user_ticket`，服务端进一步读取企业微信用户手机号 |

说明：

- 应用主页地址必须带上客户自己的 `corp_id` 和 `agent_id`，因为所有客户共用同一个 H5 域名和 API，灵策需要通过入口参数识别当前客户企业微信应用。
- 如果企业微信后台不接受带参数的主页地址，可以先配置到 `https://employee.khgl.xyz/login`，但需要确保灵策后台已保存该客户的企业微信应用配置，且入口能通过运行时配置补齐企业信息。
- 接收消息服务器 URL 当前统一使用同一个域名入口，服务端会根据企业微信回调内容、签名和已配置的客户应用信息匹配具体客户。

### 1.3 灵策后台需要维护的配置

灵策需要在平台侧为每个客户保存一条企业微信自建应用配置：

| 字段 | 说明 |
| --- | --- |
| 租户 ID `tenant_id` | 灵策内部客户机构 ID |
| 企业 ID `corp_id` | 客户企业微信 CorpID |
| 企业名称 `corp_name` | 便于运营识别 |
| 应用 ID `agent_id` | 客户自建应用 AgentId |
| 应用 Secret | 加密保存，服务端用于换 token |
| Token | 企业微信回调校验 Token |
| EncodingAESKey | 企业微信回调解密 Key |
| 应用主页 `home_url` | 员工端 H5 入口 |
| 可信域名 `trusted_domain` | 一般为 `employee.khgl.xyz` |
| 是否启用 `enabled` | 未启用时不允许登录和推送 |

## 2. 企业微信自动登录逻辑

员工从企业微信工作台进入灵策应用后，流程如下：

1. H5 检测到企业微信环境或入口 URL 带 `code/corp_id/agent_id` 等参数。
2. H5 清理旧的本地登录态，强制走企业微信 OAuth。
3. 企业微信返回授权 `code`。
4. H5 调用灵策 API：`POST /api/v1/wecom/oauth/login`。
5. API 根据 `corp_id` 找到对应客户自建应用配置。
6. API 使用客户应用 `Secret` 换取企业 access_token。
7. API 使用 `code` 获取企业微信用户 `UserId` 和 `user_ticket`。
8. API 优先用 `user_ticket` 获取企业微信用户手机号；失败时回退读取通讯录用户详情。
9. API 用企业微信手机号匹配同租户下唯一的灵策员工手机号。
10. 匹配成功后签发灵策员工端登录 token；匹配失败则拒绝登录。

核心原则：

- 企业微信入口不允许复用之前手机密码登录的旧账号。
- 企业微信入口必须校验当前企业微信账号手机号。
- 手机号不匹配或无法获取手机号时，不允许进入员工端。

## 3. 成交机会提醒触发内容

当前系统只实现了一类成交机会提醒：

| 项 | 当前实现 |
| --- | --- |
| 提醒类型 | `opportunity_not_advanced` |
| 业务含义 | 客户有明确意向，但本次沟通没有锁定下一步 |
| 默认标题 | `客户有明确意向，但没有锁定下一步` |
| 默认优先级 | `high` |
| 推送场景 | 企业微信应用消息 |
| 详情页 | `https://employee.khgl.xyz/opportunity-alerts/{alert_id}` |

### 3.1 触发时机

当录音状态被更新为 `completed` 时，API 会尝试从该录音创建成交机会提醒。

当前触发入口在录音更新逻辑中：

- 当 `recordings.status = completed`
- 且已配置 `opportunityAlertDispatcher`
- 则调用 `CreateFromRecording(recording_id, "recording_completed")`

说明：

- 录音正常分析完成后，如果状态更新为 `completed`，会触发检查。
- 手工重新分析如果最终也走到录音状态更新为 `completed` 的逻辑，也会触发检查。
- 系统有去重键，同一租户、同一录音、同一提醒类型不会重复创建多条提醒。

去重规则：

```text
dedupe_key = tenant:{tenant_id}:recording:{recording_id}:type:{alert_type}
```

### 3.2 命中条件

当前命中条件是：分析结果中的成交结果包含 `意向明确未成交`。

字段读取顺序如下：

1. `analysis_result.deal_outcome.result`
2. `analysis_result.persuasive.deal_status`
3. `analysis_result.deal_status`

只要最终取到的文本中包含 `意向明确未成交`，就生成提醒。

如果没有命中该文本，则不会生成成交机会提醒。

### 3.3 提醒内容从哪里来

提醒内容优先从录音分析结果中提取，字段不完整时使用默认兜底文案。

| 内容 | 优先取值 |
| --- | --- |
| 摘要 `summary` | `analysis_result.status_summary`、`analysis_result.conversation_summary`、证据文本 |
| 原因 `reason` | `deal_outcome.concern_strategy.stuck_point_headline`、`deal_outcome.concern_strategy.real_reason`、`analysis_summary.conversion_opportunity`、`analysis_result.conversion_opportunity`、`persuasive.stuck_point_headline` |
| 客户顾虑 `customer_objection` | `concern_strategy.real_reason`、`persuasive.real_concern`、`persuasive.real_reason`、`analysis_result.core_blockers` |
| 证据 `evidence` | `deal_outcome.evidence`、`concern_strategy.evidence`、`analysis_result.status_summary`、`analysis_result.conversation_summary` |
| 建议动作 `suggested_action` | `concern_strategy.next_action`、`analysis_summary.next_action`、`analysis_summary.conversion_opportunity`、`analysis_result.follow_up_advice` |
| 建议话术 `suggested_script` | `concern_strategy.script`、`concern_strategy.suggested_script`、`analysis_summary.suggested_script` |

默认兜底文案：

- 摘要：`客户表达过明确意向，但本次沟通没有锁定下一步，存在可补救机会。`
- 原因：`分析结果显示客户并非明确拒绝，而是带着顾虑离开，需要尽快二次跟进。`
- 建议动作：`建议尽快联系客户，先接住顾虑，再明确约定下一步到院、复查或方案确认时间。`
- 建议话术：`我刚复盘了一下您的情况，您不是没有需求，主要是还有几个顾虑没完全放下。我们可以先把您最担心的点讲清楚，再一起确认下一步怎么安排。`

### 3.4 谁会收到提醒

默认接收人：

- 录音所属员工，即 `recordings.employee_id`。

额外接收人：

- 机构后台“成交机会提醒配置”里，为该员工配置的抄送人。

接收人落库逻辑：

- 提醒创建时，会给录音所属员工创建一条 `owner` 接收记录。
- 会给所有有效抄送人创建 `cc` 接收记录。
- 企业微信消息发送时，会向这些接收人逐一推送。

如果某个接收人没有绑定企业微信：

- 企业微信消息会跳过该接收人。
- 提醒本身仍然存在于系统内。

## 4. 触发内容和规则是否配置化

当前结论：触发规则是写死的，抄送关系是配置的。

### 4.1 当前写死的内容

以下内容都在代码中硬编码：

- 触发时机：录音状态更新为 `completed`。
- 触发类型：只生成 `opportunity_not_advanced`。
- 命中文本：`意向明确未成交`。
- 字段读取顺序。
- 默认标题。
- 默认摘要、原因、建议动作、建议话术。
- 默认优先级：`high`。
- 企业微信按钮文案：`查看补救建议`。

### 4.2 当前可配置的内容

目前后台配置只包括“抄送关系”：

- 某个员工的成交机会提醒，可以额外抄送给哪些人。
- 对应接口是：
  - `GET /api/v1/opportunity-alert-cc-rules`
  - `POST /api/v1/opportunity-alert-cc-rules`
  - `DELETE /api/v1/opportunity-alert-cc-rules/{id}`

当前后台配置不包括：

- 不支持配置哪些分析字段触发。
- 不支持配置“意向明确未成交”以外的关键词。
- 不支持配置提醒优先级。
- 不支持配置不同业务角色的不同触发规则。
- 不支持配置消息模板。
- 不支持按时间、金额、项目、客户等级等条件组合触发。

## 5. 当前设计边界

当前版本是一个最小可用版本，核心目标是先把客户最关心的“没成交、没谈好、需要马上补救”的场景跑通。

当前不是通用消息中心，也不是完整规则引擎：

- 没有独立 `message` 中心表承载所有系统消息。
- 成交机会提醒使用专门业务表 `opportunity_alerts`。
- 企业微信消息是触达渠道。
- H5 详情页是统一承接页面。

这样的好处是：

- 产品逻辑简单。
- 使用者不需要理解复杂规则。
- 数据模型直接对应业务问题。
- 后续可以在已有业务闭环上逐步扩展，而不是一开始就建设抽象消息平台。

后续如果需要做配置化，建议按以下顺序扩展：

1. 先配置“触发开关”：是否启用成交机会提醒。
2. 再配置“触发结果”：例如是否包含 `意向明确未成交`、`高意向未锁单` 等。
3. 再配置“接收人策略”：负责人、抄送人、固定角色。
4. 最后再考虑消息模板和多规则组合。

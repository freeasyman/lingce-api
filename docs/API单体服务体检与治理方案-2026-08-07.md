# API单体服务体检与治理方案

日期：2026-08-07

## 1. 目标

lingce-api 继续保持为**单体 API 服务**，不拆微服务。

本方案只做三件事：

1. 收紧高风险写入口，尤其是系统日志。
2. 统一鉴权、租户隔离和路由注册方式。
3. 约束模块边界，避免后续功能扩展把单体继续写散。

## 2. 当前结论

### 2.1 允许保留的现状

- 继续使用单体服务。
- 继续使用 `handler -> service -> store` 三层结构。
- 继续使用 PostgreSQL + pgx。
- 继续保留现有业务路由路径，不做全量迁移。

### 2.2 需要治理的问题

- `POST /api/v1/inst/system-logs` 当前没有认证门禁。
- 鉴权方式并存：路由声明式、中间件手写、handler 内硬编码判断。
- 租户隔离并存：部分走 `tenancy.ResolveScope()`，部分不走。
- `support`、`recording` 等模块职责偏宽，后续扩展容易继续膨胀。

## 3. 系统日志写入口治理

### 3.1 现状问题

系统日志属于审计数据，必须可追溯、可信、不可随意伪造。当前写入口是开放的，不适合作为正式审计通道。

### 3.2 建议方案

#### A. 机构端写入口

- 路径：`POST /api/v1/inst/system-logs`
- 鉴权：JWT
- 允许用户类型：`employee`, `mobile`
- 后端补齐：
  - `tenant_id`
  - `actor_id`
  - `actor_name`
  - `actor_role_code`
  - `actor_role_name`

前端传入的身份字段只能作为参考，不能作为可信来源。

#### B. 服务端内部写入口

- 路径：`POST /api/v1/internal/system-logs`
- 鉴权：`X-Internal-Token`
- 用途：worker、内部任务、后台服务写审计日志

#### C. 登录失败和认证失败日志

- 保持在 `auth` 模块内部直接写库。
- 不通过公开 HTTP 写入口。

### 3.3 接口约束

- 限制请求体大小。
- 对 `log_type`、`action_code`、`result` 做白名单校验。
- `request_summary`、`before_summary`、`after_summary` 必须做敏感字段清洗。
- 支持 `request_id` / `trace_id` 作为幂等辅助字段，减少重复写入。

### 3.4 实施顺序

1. 给 `inst/system-logs` 加 JWT。
2. 新增 `internal/system-logs`。
3. 调整调用方，把内部写日志的场景迁到内部入口或直接落库。
4. 为敏感字段清洗补测试。

## 4. 鉴权与租户隔离治理

### 4.1 目标原则

所有路由统一按照同一套规则执行：

`认证 -> 用户类型 -> 租户范围 -> 权限 -> handler`

### 4.2 建议统一模型

建议把路由注册收敛成一个声明式结构：

```go
type Route struct {
    Method     string
    Path       string
    Handler    http.HandlerFunc
    AuthMode   string   // public / jwt / internal
    UserTypes  []string // admin / employee / mobile
    TenantMode string   // none / tenant / self / admin
    Permission string
}
```

### 4.3 约束规则

- 路由层只声明规则，不写业务判断。
- handler 不再自己判断 `admin/employee/mobile`。
- handler 不再自己拼租户权限逻辑。
- `store` 方法签名尽量显式接收 `tenantID` 或 `Scope`。

### 4.4 租户隔离分层

#### HTTP 层

- 解析 JWT。
- 计算 scope。
- 对 admin/employee/mobile 做访问边界约束。

#### service/store 层

- 所有租户相关查询必须显式带 tenant 条件。
- 对跨租户读取使用 `Scope.TenantIDs`，不要隐式偷用全局态。
- 不能只依赖 handler 做保护。

### 4.5 迁移策略

1. 新增接口全部走声明式注册。
2. 先迁高风险模块：
   - `support`
   - `recording`
   - `tenant`
   - `rbac`
   - `employee`
3. 旧接口保持路径不变。
4. 最后清理 handler 内重复鉴权代码。

## 5. 单体架构下的模块边界

### 5.1 总体原则

保持单体，不拆服务，但要按业务域分层收口。

### 5.2 结构原则

每个模块仍然保持：

- `handler.go`
- `service.go`
- `store.go`
- `model.go`
- `dto.go`

如果一个模块继续膨胀，就按子域拆成多个文件，但不强行拆 package。

### 5.3 推荐的模块收口方向

#### support

建议逐步拆成：

- `notification`
- `auditlog`
- `aiusage`
- `databrowser`
- `visit`
- `encounter`

#### recording

建议按子域拆文件：

- 录音主流程
- 分析流程
- 任务流程
- prompt/debug
- 周报与统计
- 销售/前台特化逻辑

#### organization / customer / badge

继续保留单 package，但每个表尽量只由一个 store 负责，避免多个模块重复碰同一张表。

## 6. 路由组织建议

### 6.1 现状

当前路由已经按模块注册，但不同模块的风格不完全一致：

- 有的模块用 `router.Register`
- 有的模块自己 `mux.Handle`
- 有的模块在 handler 里硬编码鉴权

### 6.2 建议

- 新路由一律走统一注册器。
- 业务模块只暴露路由定义，不自己拼鉴权链。
- 公开接口、内部接口、运营接口分组明确。

### 6.3 路由分组建议

- `/api/v1/auth/*`
- `/api/v1/mobile/*`
- `/api/v1/ops/*`
- `/api/v1/inst/*`
- `/api/v1/internal/*`

其中：

- `ops` 仅 admin
- `inst` 仅机构端用户
- `internal` 仅内部调用

## 7. 分阶段执行方案

### Phase 1

- 给系统日志写入口加保护。
- 新增内部写日志入口。
- 补基础测试。

### Phase 2

- 抽出统一路由声明。
- 让新接口全部走统一鉴权链。
- 清理最明显的 handler 内硬编码鉴权。

### Phase 3

- 收敛 tenant scope 计算。
- 统一 store 的 tenant 约束传参方式。
- 把 support 和 recording 的大模块继续拆细。

## 8. 验收标准

满足以下条件后，认为治理完成：

- 系统日志写入只能通过认证入口或内部入口。
- 新接口默认必须声明鉴权和租户模式。
- handler 中不再新增散落的 `admin` 判断。
- tenant 隔离规则能从路由层一路传到 store 层。
- `go test ./...` 保持通过。

## 9. 不做的事

- 不拆微服务。
- 不改所有旧路由路径。
- 不强制一次性重构全部模块。

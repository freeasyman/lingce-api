# 发布交接：病历「接诊时间」晚 8 小时（时区）— 2026-11-24

- **日期**：2026-11-24
- **影响**：电子病历列表的「接诊时间」比实际晚 **8 小时**（例：昨晚 22:53 的录音，病历显示成次日 06:53）
- **涉及**：`lingce-worker`（主因）+ `lingce-api`（次要路径）+ 一次历史数据修正
- **不改**：数据库结构、录音文件、转写内容

---

## 一、现象

电子病历列表中：

| 占位客户名（对的） | 接诊时间（错的） |
|---|---|
| `[11-19 22:53 钱小强接待的客户]` | 2026/11/20 **06:53:40** |
| `[11-19 22:40 钱小强接待的客户]` | 2026/11/20 **06:40:31** |
| `[11-20 06:08 钱小强接待的客户]` | 2026/11/20 **06:08:02** |
| `[11-19 17:43 钱小强接待的客户]` | 2026/11/19 17:43:03（实时链路的，正确） |

规律：凡是由**上传录音**（`source=desktop` / `smart_badge`）派生出的病历，时间都 **+8 小时**。

## 二、根因（一条链）

1. `recordings.recorded_at` 是 **`timestamp without time zone`**，库里存的就是**北京时间**；
2. `pgx` 读这种列时会给 `time.Time` 打上 **UTC location**（挂钟值不变，仍是 22:53）；
3. worker 在 `internal/job/business_api.go` 直接 `input.RecordedAt.Format(time.RFC3339)`
   → 输出 `2026-11-19T22:53:40Z`（**被标成了 UTC**）；
4. API 侧 `parseRecordedAt` 解析后 `.UTC()`，写入 `emr_records.started_at`（**timestamptz**）
   → 实际存成 `2026-11-19T22:53:40Z` = `2026-11-20 06:53:40+08`；
5. 前端按北京时间展示 → **+8 小时**。

> 注意：占位客户名里的时间之前也踩过同一类坑（worker 里 `.In(CST)` 重复加 8），
> 那个已单独修过；这次是**发给 EMR 的 recorded_at** 这一条链。

## 三、代码改动

### 1. `lingce-worker`（主因，2 行 + 1 个 helper）

`internal/job/business_api.go`：

```go
// cBeijingTime 把「timestamp without time zone」的录音时间转成带 +08:00 的 time.Time。
// pgx 读出来会带 UTC location，直接 Format(RFC3339) 会输出 "...Z"，下游按 UTC 解析后整体晚 8 小时。
func cBeijingTime(t time.Time) time.Time {
	if t.IsZero() {
		return t
	}
	cst := time.FixedZone("CST", 8*3600)
	return time.Date(t.Year(), t.Month(), t.Day(), t.Hour(), t.Minute(), t.Second(), t.Nanosecond(), cst)
}
```

两处赋值改为：

```diff
-		RecordedAt:              recording.RecordedAt.Time,
+		RecordedAt:              cBeijingTime(recording.RecordedAt.Time),
...
-		RecordedAt:        recording.RecordedAt.Time,
+		RecordedAt:        cBeijingTime(recording.RecordedAt.Time),
```

单测：`internal/job/timezone_test.go`（2 个用例，已通过）。

### 2. `lingce-api`（次要路径：从历史录音建病历）

`internal/emrrecord/handler.go` 的 `timePtr`：

```go
// recorded_at 是 timestamp without time zone（北京时间），pgx 解析成 UTC，
// 这里按 +08:00 重新解释，避免下游再整体晚 8 小时。
cst := time.FixedZone("CST", 8*3600)
t := time.Date(y, m, d, h, min, s, ns, cst)
```

## 五、历史数据修正（7 行，需要执行）

先预览（应看到 7 行，时间都晚 8 小时）：

```sql
SELECT er.id, er.encounter_id, er.started_at AS 当前, r.id AS recording_id, r.recorded_at AS 录音时间, r.source
FROM emr_records er
JOIN encounters e ON e.id = er.encounter_id AND e.source_type = 'recording'
JOIN recordings r ON r.id = e.source_id
ORDER BY er.created_at DESC;
```

执行修正（只动「由录音派生」的病历，实时链路的不受影响）：

```sql
UPDATE emr_records er
SET started_at = er.started_at - interval '8 hours'
FROM encounters e
JOIN recordings r ON r.id = e.source_id AND e.source_type = 'recording'
WHERE er.encounter_id = e.id
  AND r.source IN ('desktop', 'smart_badge');
```

预期结果：

| emr_records.id | 修前 | 修后 |
|---|---|---|
| aa72c991… | 2026-11-24 22:18:39+08 | 2026-11-24 **14:18:39**+08 |
| 21a07fa3… | 2026-11-24 22:19:07+08 | 2026-11-24 **14:19:07**+08 |
| 0e849ab2… | 2026-11-20 06:53:40+08 | 2026-11-19 **22:53:40**+08 |
| afbdb536… | 2026-11-20 06:40:31+08 | 2026-11-19 **22:40:31**+08 |
| 5517b364… | 2026-11-20 06:08:02+08 | 2026-11-19 **22:08:02**+08 |

> 该 UPDATE 只在「`source IN ('desktop','smart_badge')`」范围内生效，
> 实时链路（`source='realtime'`）的病历本来就是对的，不会被动到。

## 六、验证

1. 发完 worker 后，录一条新音（上传链路），等病历生成：
   ```sql
   SELECT er.started_at, r.recorded_at
   FROM emr_records er
   JOIN encounters e ON e.id = er.encounter_id AND e.source_type='recording'
   JOIN recordings r ON r.id = e.source_id
   ORDER BY er.created_at DESC LIMIT 1;
   ```
   **`er.started_at` 应等于 `r.recorded_at` 对应的北京时间**（两者差值应为 0，而不是 8 小时）。

2. 电子病历列表里「接诊时间」应与占位客户名里的时间一致。

## 七、回滚

- 代码：回滚二进制即可；
- 数据：`UPDATE emr_records SET started_at = started_at + interval '8 hours' WHERE ...`（同范围），
  但不建议——修复后的值才是正确的。

## 八、影响面

- 只影响**病历的「接诊时间」显示**；
- 不影响录音、转写、分析、质控评分、客户档案；
- 无 DDL、无迁移。

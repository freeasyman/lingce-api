# API 迁移体系设计

> 目标：让 lingce-api 的每次功能迭代都带着明确的迁移动作进入主干，避免“代码先上、表后补”或“启动时靠兼容逻辑兜底”的模式。

## 1. 设计目标

1. 新功能开发必须同步产生对应迁移。
2. 迁移只执行一次，不在正常启动路径重复跑。
3. 任何 schema 变化都可追踪、可校验、可回放。
4. 启动阶段只检查版本，不猜测库状态。
5. 不引入常驻任务，不引入独立迁移服务。

## 2. 核心原则

### 2.1 一次性迁移

表结构、索引、约束、种子数据、回填动作都必须进入版本化迁移，不再放进正常启动流程。

### 2.2 代码和迁移同提交

每个涉及数据库变化的 API 改动，必须同时包含对应 migration 文件。

### 2.3 启动只做校验

API 启动时只判断数据库是否已经达到代码要求版本。
如果没有达到，直接报错退出，提示先跑迁移。

### 2.4 迁移文件不可变

已发布迁移文件不得回改。
后续修复必须新增新版本迁移。

## 3. 推荐结构

保留在当前仓库内完成：

```text
docs/
scripts/sql/
internal/store/
```

建议再补一个迁移目录约定：

```text
scripts/sql/
  2026-08-06_001_create_api_migration_state.sql
  2026-08-06_002_add_xxx_table.sql
  2026-08-06_003_add_xxx_columns.sql
  ...
```

每个文件只表达一个版本点，粒度宁可小，不要把几十个表拼进一个大文件。

## 4. 迁移账本

数据库中应有独立账本表，例如：

```sql
CREATE TABLE api_migration_state (
  migration_key TEXT PRIMARY KEY,
  applied_version INTEGER NOT NULL,
  checksum TEXT NOT NULL,
  applied_at TIMESTAMP NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMP NOT NULL DEFAULT NOW()
);
```

账本职责：

- 记录当前已应用版本
- 记录版本 checksum
- 防止版本跳跃
- 防止同版本文件被篡改

## 5. 版本规则

### 5.1 版本号

采用单调递增版本号。
推荐格式：

- `20260806_001`
- `20260806_002`
- `20260806_003`

### 5.2 checksum

每个 migration 文件都计算 checksum。
启动或 CI 发现 checksum 不一致时，直接失败。

### 5.3 依赖顺序

迁移必须按版本顺序执行。
不允许跳版本执行，也不允许回退执行。

## 6. 开发流程

### 6.1 新增字段

例如新增 `customers.source_channel`：

1. 先写 migration 文件，添加列和必要索引。
2. 再改 Go 代码读取/写入这个字段。
3. 在同一个 PR 里提交。
4. CI 校验 migration 文件存在且版本连续。

### 6.2 新增表

1. 写建表 migration。
2. 如果需要回填种子，单独写 seed migration。
3. Go 代码只能依赖已存在的表。

### 6.3 修改约束或索引

1. 新增版本迁移，不改旧文件。
2. 如涉及数据清洗，先清洗后加约束。

## 7. 代码执行模型

### 7.1 启动模式

API 启动时：

1. 连接数据库
2. 读取 `api_schema_migrations`
3. 对比代码要求版本
4. 如果版本不足，退出
5. 如果版本足够，继续启动 HTTP 服务

### 7.2 迁移模式

同一个 API 二进制可以保留一个显式模式，例如：

- `--migrate-only`

这个模式只在部署时运行一次，不进入常驻服务流程。

当前实现已经接入：

```bash
./bin/lingce-api --config ./configs/dev.toml --migrate-only
```

普通启动会先校验 `api_schema_migrations`，再校验兼容迁移基线。如果校验不通过，API 不会自动补写数据库，而是退出并提示先执行迁移模式。

## 8. 与现有兼容迁移的关系

`internal/store/compat_migration.go` 里的内容应分三类处理：

1. **纯 schema 变更**
   - 拆到版本化 SQL 文件
2. **一次性数据回填**
   - 拆到单独 migration 或显式维护命令
3. **启动期检查**
   - 只保留轻量校验，不做实际写入

当前的“哨兵对象存在就短路”只能作为过渡，不是最终方案。

## 9. 防遗漏机制

要做到“每次开发新功能，自动产生对应迁移动作”，不能只靠人记忆，要靠流程约束：

### 9.1 PR 必填项

每个涉及 DB 变更的 PR 必须满足：

- 有 migration 文件
- 有代码引用更新
- 有自检说明

### 9.2 CI 检查

CI 至少检查：

- 迁移文件版本连续
- migration 文件未被修改后复用旧版本号
- 代码里声明的最低 schema 版本与 migration 账本一致
- 新增数据库对象是否有对应 migration

### 9.3 启动失败策略

如果代码版本高于数据库版本：

- 不自动补迁移
- 不在启动时猜测执行
- 直接失败并给出明确提示

这样才能避免“线上跑着跑着才发现漏了一步”。

## 10. 推荐落地顺序

1. 引入 `api_migration_state` 账本
2. 把启动期兼容逻辑改成版本检查
3. 把 `compat_migration.go` 中的 schema 语句拆成版本化 SQL
4. 把数据回填拆成独立迁移或维护命令
5. 给 CI 加版本连续性和遗漏检查
6. 逐步删除启动时的兜底写库逻辑

## 11. 结论

要和 API 迭代形成严密体系，关键不是“迁移也写在代码里”，而是：

- 每次 schema 变化都必须有明确版本
- 每次部署都必须先对齐版本
- 启动时只检查，不补写
- 回填和结构变更分开

这样才能把“无任何遗漏”从口头要求，变成可执行的工程纪律。

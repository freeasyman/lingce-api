# 合成测试集与标注归因 — Codex 任务书

日期：2026-08-03
交付对象：Codex
前置代码：`internal/splitdemo/`（已有切分 demo）

## 为什么做这两件事

现在 demo 能跑切分，但缺两个能力，导致 prompt 无法有效迭代：

**缺口一：没有 ground truth，无法量化准确率。** 医生说"好像还行"不是数据。要知道 prompt v0.1 到 v0.2 是变好还是变差，必须有一批已知正确答案的测试录音，跑完直接对比。

**缺口二：修正操作没记录原因。** 现有 6 种修正操作（confirm/merge/split/adjust/delete/add）只记录"改了什么"，不记录"为什么改"。没有原因归类，就不知道 prompt 该往哪个方向改 —— 是"患者离开返回"误判多，还是"医生与同事交流"误判多，改法完全不同。

解决方式：

- **合成测试集** —— 从生产短录音里拼接转写文本，人工标注拼接点秒数作为 ground truth。构造成本约 10 分钟一条，跑测试 5 分钟出结果，不需要运营介入。
- **标注归因** —— 修正操作时增加原因分类字段，让错误分布可统计。

两件事都在现有 demo 页面上加，不新建服务、不新建页面。

### 原因枚举

定义为 Go 常量，前端下拉框用同一套值：

| `reason_code` | 中文标签 | 说明 | 常见于 |
|---|---|---|---|
| `patient_returned` | 患者中途离开后返回 | 患者去做检查/取药后回到诊室，被误判为两次就诊 | merge |
| `colleague_talk` | 医生与同事交流 | 医生和护士/同事讨论，被误判为一次就诊 | delete |
| `multi_patient` | 多患者同诊 | 夫妻同诊、母子同诊被切成多段 | merge |
| `family_proxy` | 家属代述 | 家属替患者描述病情，被误判为独立就诊 | merge |
| `topic_shift` | 同一患者话题跳转 | 同一患者连续问不相关问题，被误判为两次 | merge |
| `missed_boundary` | 漏切边界 | 两个不同患者被合并成一段 | split |
| `boundary_offset` | 边界位置偏移 | 类型判对了，但起止秒数不准 | adjust |
| `not_encounter` | 非就诊内容 | 问路、取报告、纯闲聊被判成就诊 | delete |
| `missing_encounter` | 遗漏的就诊 | AI 完全没识别出这段就诊 | add |
| `other` | 其他 | 填 `reason_note` 说明 | 任意 |

前端在不同操作下只展示相关的原因项（"常见于"列），但不做强限制 —— 允许选任意值，因为实际情况可能超出预期。

### 前端改动

`internal/splitdemo/static/index.html`：

- 执行 merge / split / adjust / delete / add 操作时，弹出原因选择（下拉框 + 可选备注输入）
- confirm 操作不需要原因（没有错误）
- 选 `other` 时展开 `reason_note` 输入框
- 原因是**必填**（除 confirm），不填不能提交 —— 这是数据质量的关键，允许跳过就没人填
- 保持快捷键流畅：下拉框支持数字键 1-9 快速选择

## 任务二：合成测试集

### 核心思路

从生产数据库里取多条**已知只有一个患者**的短录音，把它们的转写文本首尾相接拼成一条长文本。拼接点的秒数就是 ground truth。AI 跑完，直接用代码对比它是否在正确位置切开。

**关键点：不需要处理音频文件。** AI 的输入只有转写文本，它从未接触音频。

### 2.1 候选录音查询

新增 `Store` 方法，查询适合做拼接素材的短录音：

```sql
SELECT
  r.id,
  r.duration,
  COALESCE(e.name, '') AS employee_name,
  r.recorded_at,
  LENGTH(COALESCE(r.transcription_text, '')) AS transcript_length
FROM recordings r
LEFT JOIN employees e ON e.id = r.employee_id
WHERE r.tenant_id = $1
  AND r.deleted_at IS NULL
  AND LOWER(COALESCE(r.business_scope, '')) = 'doctor'
  AND r.transcription_text IS NOT NULL
  AND r.duration BETWEEN $2 AND $3      -- 默认 180 到 900 秒（3-15 分钟）
ORDER BY r.duration ASC
LIMIT $4
```

时长上下界作为参数，默认 180-900 秒。短录音大概率是单患者，但**不保证** —— 所以构造界面上要能预览转写文本，让人确认这条真的只有一个患者再选用。

### 2.2 拼接逻辑

新增 `internal/splitdemo/synthetic.go`。

输入：一组 `{recording_id, gap_seconds, gap_type}`，按顺序排列。

处理：

1. 逐条读取录音的转写文本，复用现有的转写解析逻辑（`RecordingDetail` 已经处理了 `structured_transcript` / `timeline_transcript` / `transcription_segments` 多种来源的兼容，直接复用）
2. 第一条从 0 秒开始，原样保留时间戳
3. 后续每条的所有时间戳统一加上偏移量：`offset = 前一条的结束秒数 + gap_seconds`
4. 拼接点按 `gap_type` 插入不同内容：

| `gap_type` | 插入内容 | 测试目标 |
|---|---|---|
| `silence` | 什么都不插，只留时间戳空隙 | 静默信号（`gap_seconds` 可调，测 30s / 60s / 120s 的效果差异） |
| `call_next` | 一行 `[T-T+3] 医生: 下一个` | 强信号：叫号 |
| `closing` | 一行 `[T-T+4] 医生: 好，就这样，回去吃药` | 强信号：结束语 |
| `abrupt` | 无空隙、无提示，直接首尾相接（`gap_seconds=0`） | 最难场景：无任何显式信号 |
| `colleague` | 插入一段医生与同事的对话（预置几条文本模板，随机选） | 干扰项：非就诊内容应被判为 `non_encounter_talk` |

5. 输出拼接后的完整转写文本 + ground truth 边界列表

### 2.3 数据模型

```go
// 合成测试录音定义
type SyntheticCase struct {
	ID              string             `json:"id"`               // 人工指定或自动生成
	Name            string             `json:"name"`             // 如 "静默60s-3患者"
	Description     string             `json:"description"`      // 这条测试什么
	Segments        []SyntheticSource  `json:"segments"`         // 素材录音序列
	DurationSeconds int                `json:"duration_seconds"` // 拼接后总时长
	Transcript      string             `json:"transcript"`       // 拼接后的转写文本
	GroundTruth     []GroundTruthMark  `json:"ground_truth"`     // 正确边界
	CreatedAt       time.Time          `json:"created_at"`
}

type SyntheticSource struct {
	RecordingID  int64  `json:"recording_id"`
	GapSeconds   int    `json:"gap_seconds"`    // 与前一条之间的间隔，第一条为 0
	GapType      string `json:"gap_type"`       // silence/call_next/closing/abrupt/colleague
	StartSeconds int    `json:"start_seconds"`  // 在拼接结果中的起始位置（计算得出）
	EndSeconds   int    `json:"end_seconds"`
}

type GroundTruthMark struct {
	AtSeconds   int    `json:"at_seconds"`    // 正确边界位置
	MarkType    string `json:"mark_type"`     // encounter_boundary / non_encounter_start / non_encounter_end
	GapType     string `json:"gap_type"`      // 该边界对应的 gap_type，用于按信号类型统计准确率
	Description string `json:"description,omitempty"`
}
```

存储：复用 `AnnotationStore` 的文件方式，存在 `data/synthetic/case_{id}.json`。不入库。

### 2.4 评测逻辑

新增 `Evaluate(caseData *SyntheticCase, result *SplitResponse) *EvalReport`。

对比规则：

- **命中（hit）** —— AI 的某个边界落在 ground truth 边界的容差窗口内。容差默认 ±15 秒，可配置。
- **漏切（missed）** —— ground truth 有边界，容差窗口内 AI 没有任何边界。**这是最严重的错误**（两个患者被合并）。
- **过切（extra）** —— AI 有边界，但不对应任何 ground truth。
- **偏移（offset）** —— 命中的边界，记录实际偏移秒数。

```go
type EvalReport struct {
	CaseID          string           `json:"case_id"`
	ToleranceSeconds int             `json:"tolerance_seconds"`

	TotalGroundTruth int             `json:"total_ground_truth"`
	Hits             int             `json:"hits"`
	Missed           int             `json:"missed"`
	Extra            int             `json:"extra"`

	Precision       float64          `json:"precision"`         // hits / (hits + extra)
	Recall          float64          `json:"recall"`            // hits / total_ground_truth
	MeanOffset      float64          `json:"mean_offset"`       // 命中边界的平均偏移绝对值
	MaxOffset       int              `json:"max_offset"`

	Details         []EvalDetail     `json:"details"`
	ByGapType       map[string]*GapTypeStat `json:"by_gap_type"` // 按信号类型分组的准确率
}

type EvalDetail struct {
	Kind            string `json:"kind"`             // hit/missed/extra
	GroundTruthAt   int    `json:"ground_truth_at,omitempty"`
	PredictedAt     int    `json:"predicted_at,omitempty"`
	OffsetSeconds   int    `json:"offset_seconds,omitempty"`
	GapType         string `json:"gap_type,omitempty"`
	ContextText     string `json:"context_text"`      // 该位置前后各约 80 字，用于人眼判断
}

type GapTypeStat struct {
	Total  int `json:"total"`
	Hits   int `json:"hits"`
	Missed int `json:"missed"`
}
```

`ByGapType` 是重点：它直接回答"AI 在哪种信号上最弱"。如果 `silence` 的召回率 0.9 但 `abrupt` 只有 0.4，说明 prompt 对无显式信号的场景处理不足。

`ContextText` 也是重点：报告里光有数字没用，必须能看到"漏切的那个位置，原文长什么样"，才知道 prompt 要怎么改。

### 2.5 API

在 `RegisterRoutes` 追加：

```
GET  /internal/split-demo/synthetic/candidates   # 候选素材录音列表（带转写预览）
POST /internal/split-demo/synthetic/preview      # 试拼接，返回拼接结果和 ground truth，不保存
POST /internal/split-demo/synthetic/cases        # 保存合成用例
GET  /internal/split-demo/synthetic/cases        # 列出所有用例
GET  /internal/split-demo/synthetic/cases/{id}   # 用例详情
DELETE /internal/split-demo/synthetic/cases/{id} # 删除用例
POST /internal/split-demo/synthetic/run          # 对某用例跑切分 + 评测
GET  /internal/split-demo/synthetic/runs/{id}    # 异步任务进度（复用现有 JobManager）
```

`POST /synthetic/run` 的请求体复用 `SplitRequest` 的 prompt 字段，但用 `case_id` 替代 `recording_id`：

```json
{
  "case_id": "silence60-3p",
  "model": "qwen-max",
  "system_prompt": "...",
  "user_prompt": "...",
  "prompt_version": "v0.2",
  "tolerance_seconds": 15
}
```

响应包含 `SplitResponse` + `EvalReport`。

**复用要求：** 切分执行必须复用现有的 `splitRecording` 核心逻辑（分块、重试、修复 JSON 输出、校验时间轴连续性），只是输入从"数据库里的录音"换成"合成用例的文本"。不要复制一份并行实现 —— 否则 prompt 在合成集上的表现和真实录音不一致，测试就失去意义。

建议把 `splitRecording` 里"取转写文本"的部分抽出来，让它接受 `(transcript string, durationSeconds int)` 而不是 `recordingID`。

### 2.6 前端

在现有页面加一个 tab 或独立区块，两部分：

**构造区**

- 素材候选列表：时长、员工、转写字数、**转写文本预览**（可展开看全文，确认是单患者）
- 已选素材按顺序排列，每条后面配置 `gap_seconds`（数字输入）和 `gap_type`（下拉）
- 支持拖动调整顺序、删除某条
- 「预览拼接结果」按钮 → 显示拼接后的文本、总时长、ground truth 边界列表
- 用例命名 + 描述（描述要写清"这条测什么"，如"测 60 秒静默 + 无提示直接切换的混合场景"）
- 「保存用例」

**测试区**

- 用例列表：名称、描述、素材条数、ground truth 边界数、上次跑的准确率
- 选一个用例 → prompt 编辑框（预填当前 prompt）→「运行测试」
- 结果展示（这是最重要的部分）：

```
用例：静默60s-3患者          prompt: v0.2
────────────────────────────────────────
召回率 0.83 (5/6)   精确率 0.71 (5/7)
平均偏移 8.2s       最大偏移 22s

按信号类型：
  silence      3/3  ✓
  call_next    2/2  ✓
  abrupt       0/1  ✗  ← 弱点
────────────────────────────────────────
边界明细：

✓ 命中  GT 412s → AI 408s  (偏移 -4s)  silence
  ...上文：好，那就这样，回去按时吃药
  ...下文：（静默 60s）医生: 来，坐

✗ 漏切  GT 1087s            abrupt      ← 严重
  ...上文：那我就先这样吃着看看吧
  ...下文：医生: 你这个多久了？

✗ 过切  AI 1520s                        
  ...上文：这个药一天三次
  ...下文：另外你那个血压也要注意
```

漏切必须视觉上最醒目（红色/加粗），因为它对应临床安全风险。

- 「对比上次运行」：同一用例的两次运行并排显示，看改 prompt 后哪些边界变好、哪些变差。这是 prompt 迭代的核心工具，运行记录复用 `RunStore` 存储。

## 验收标准

任务一：

1. 执行 merge/split/adjust/delete/add 时必须选原因才能保存
2. 保存后能看到本条录音的错误分布
3. 能看到跨录音的汇总统计（至少 2 条录音标注后验证）
4. `data/annotations/recording_*.json` 里能看到 `reason_code` 字段

任务二：

1. 能从数据库拉出候选短录音，并预览转写文本
2. 能选 3 条以上素材，配置不同 `gap_type`，预览拼接结果
3. 拼接后的时间戳连续、无重叠、无倒退
4. 保存的用例能重新加载
5. 对用例跑切分，得到召回率/精确率/按信号类型的分组统计
6. 每个漏切/过切都能看到上下文原文
7. 同一用例两次运行能并排对比
8. 合成测试用的是 `splitRecording` 同一套核心逻辑，不是并行实现

## 不做

- 不做音频文件的拼接或处理
- 不做用户认证
- 不入库（合成用例和标注都是文件存储）
- 不做多人协作标注
- 不接 llm-gateway
- 不做自动 prompt 优化（改 prompt 是人的判断）

## 实现顺序建议

1. 任务一（改动小，先拿到归因数据）
2. 任务二的拼接和评测逻辑（后端，可用单元测试验证）
3. 任务二的前端（结果展示是重点，值得多花时间）

任务一和任务二的后端可以并行。

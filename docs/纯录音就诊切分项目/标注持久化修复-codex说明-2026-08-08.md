# 标注持久化修复 — 给 Codex 的说明

日期：2026-08-08
文件：`internal/splitdemo/static/index.html`（主要）、`internal/splitdemo/service.go`（次要）

## 现象

用户在「真实录音标注」页面把两个就诊合并了。合并的瞬间界面是对的（两张卡片变一张）。但保存后刷新页面、或者重启服务再进来，**就诊列表又变回合并前的样子**，合并白做了。

## 这不是合并逻辑的 bug

`handleEncounterAction` 里的合并代码本身是对的（index.html 约 996-1001 行）：它把两个 encounter 在数组里 splice 成一个，然后重新渲染。所以你会看到界面立刻变了。

真正的问题在**重新加载的路径**上。

## 需要先理解的数据模型

这个页面同时存在两层数据，它们的角色完全不同：

| 层 | 变量 | 含义 | 可变性 |
|---|---|---|---|
| AI 原始输出 | `run.result.encounters` | 这次 LLM 切出来的就诊，是一份历史快照 | **不可变**。它记录"AI 当时是怎么切的"，是评估 prompt 效果的依据，绝不能被人工修正覆盖 |
| 人工标注 | `annotation` | 人做了哪些修正 + 修正后的最终就诊列表 | 可变，每次修正都更新 |

**页面上应该显示的是「AI 原始输出 + 人工修正后的结果」，也就是标注层，不是 AI 原始层。**

现在的代码在加载录音详情时是这样做的（index.html 约 478-481 行）：

```js
state.annotate.result = state.annotate.detail.latest_run.result;      // 拿到 AI 原始输出
state.annotate.annotations = state.annotate.detail.latest_annotation;  // 拿到已保存的标注
```

两份数据都取到了，但**取完就各自躺着，从来没有把标注应用到 result 上**。渲染函数 `renderAnnotateResult()` 读的是 `state.annotate.result.encounters`，也就是 AI 原始输出。所以人工合并的结果在刷新后就消失了。

在内存里合并有效，是因为合并代码直接改了 `state.annotate.result.encounters` 这个数组。一旦重新从服务器加载，这个内存中的修改就没了。

## 要做的第一件事：加载时应用标注

新增一个函数，职责是「把标注叠加到 AI 原始输出上，得出应该显示的就诊列表」。

输入：AI 原始的 encounters 列表 + 已保存的 annotation
输出：修正后的 encounters 列表

应用规则（按 annotation.corrections 的顺序依次执行）：

| correction.type | 应该做什么 |
|---|---|
| `merge` | 把 `encounter_seq` 指向的那段并入它前一段：前段的 `end_seconds` 取两段的较大值，`full_text` 拼接，然后删除被并入的那段 |
| `delete` | 删除 `encounter_seq` 指向的那段 |
| `split` | 在 `split_at_seconds` 处把该段拆成两段 |
| `adjust` | 按记录的新边界更新该段的 `start_seconds` / `end_seconds` |
| `add` | 插入一段新的 encounter |
| `correct`（确认） | 不改变边界，只标记为已确认 |

注意：corrections 里的 `encounter_seq` 是**修正发生那一刻**的序号。如果先合并了 #2、再合并 #3，第二次合并时的 #3 已经因为第一次合并而变成了原来的 #4。所以：

- 要么在保存 correction 时就记录稳定的标识（比如原始 encounter 的 `start_seconds`，它不会因为其他段的合并而改变）
- 要么严格按 corrections 的记录顺序重放，每次重放后重新编号

**推荐前者**，用 `start_seconds` 作为定位依据比依赖重放顺序稳健得多。如果改成这样，`AnnotationCorrection` 结构里需要加一个字段记录目标段的原始 `start_seconds`。

加载录音详情后，如果 `latest_annotation` 存在，就用这个函数算出显示用的列表，而不是直接用 AI 原始输出。

## 要做的第二件事：保存时存完整的最终状态

现在的保存逻辑（index.html 约 1024 行）有问题：

```js
encounters: (state.annotate.annotations?.encounters || state.annotate.result.encounters.map(...))
```

`state.annotate.annotations.encounters` 这个数组只在用户点「切分正确」时才追加元素。所以会出现这种情况：

- 用户合并了 #2 和 #3，一次「确认」都没点 → `annotations.encounters` 是空的 → 走 `||` 后面的分支，保存了完整的合并后列表 → 正确
- 用户先确认了 #1，然后合并了 #2 和 #3 → `annotations.encounters` 里只有 #1 → 走前面的分支，**只保存了 #1，合并后的其他段全丢了** → 错误

修法：保存时始终存**当前显示的完整就诊列表**（也就是修正后的最终状态），每段带上它是「AI 原样确认」还是「人工修正产生」的来源标记。确认状态作为每段的一个字段，不要用「在不在这个数组里」来表达确认。

这样 `annotation.encounters` 的语义就变成了「这条录音最终有哪些就诊」，这也正是后续要写进 `encounters` 表的东西。corrections 数组则单独保留，作为改 prompt 的依据和审计记录。

## 要做的第三件事：合并后重新生成摘要

两段合并成一段后，卡片上显示的患者/主诉/处置还是前一段的旧摘要，内容已经不完整了（缺了被并入那段的信息）。

合并后应该用合并后的完整文本重新调一次摘要接口（`POST /internal/split-demo/encounter-summary`，现成的），更新这张卡片的三行摘要。

调用期间卡片上给个「正在更新摘要…」的提示，不要让界面看起来卡住。

## 要做的第四件事：让用户看得见状态

现在用户完全不知道自己的修正有没有被记住。需要三个可见信号：

1. **卡片上的来源标记** —— 人工修正产生的就诊卡片，标注一个「已人工合并」之类的小标签，和 AI 原样的卡片区分开
2. **保存状态** —— 保存成功后除了「已保存基准」这句提示，还要更新「本条修正 N 处」的计数
3. **重新进入时的提示** —— 打开一条已标注过的录音时，在就诊列表上方显示一行：「这条录音已标注过（N 处修正），当前显示的是修正后的结果」

第 3 条最重要。用户现在的困惑正是因为无法判断"看到的是原始结果还是我修正过的结果"。

## 验收标准

1. 合并两个就诊 → 保存 → 刷新页面 → 仍然是合并后的状态
2. 合并两个就诊 → 保存 → 重启服务 → 重新进入 → 仍然是合并后的状态
3. 先点一个「切分正确」，再合并另外两段 → 保存 → 刷新 → 确认状态和合并状态都还在
4. 合并后卡片的主诉/处置包含了两段的内容，不是只有前一段的
5. 打开已标注的录音，列表上方能看到「已标注过（N 处修正）」的提示
6. `data/annotations/recording_{id}.json` 里的 `encounters` 数组是完整的最终列表，`corrections` 数组记录了每一次修正及其原因码

## 不要做的

- **不要修改 `run.result`**（保存到 RunStore 里的那份 AI 原始输出）。它是评估 prompt 效果的基准，被人工修正污染后就没法回答"AI 当时切得对不对"这个问题了。人工修正只存在 annotation 层。
- 不要动切分核心逻辑
- 不要动 prompt
- 不要动另外两个页面

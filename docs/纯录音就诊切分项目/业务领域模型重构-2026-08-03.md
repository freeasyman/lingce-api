# 灵策业务领域模型重构

日期:2026-08-03
状态:设计讨论中

## 一、核心判断

灵策的业务本质是:**帮助医疗/健康服务机构,把员工与客户之间的每一次服务交互,变成可追踪、可分析、可优化的结构化资产。**

当前系统以"录音"为中心组织一切。这个模型的问题不是技术上的,而是业务上的:

- 录音是手段,不是目的。机构关心的是"这个医生今天看了几个患者、质量如何",不是"今天有几条录音"
- 录音和服务不是 1:1 的。长录音包含多次服务,实时流可能一次服务跨多段录音
- 以录音为中心无法回答客户维度的问题:"这个患者来过几次、每次看的什么、该随访了没有"

新模型的核心实体是**服务(encounter)**——一个员工对一个客户的一次连续业务交互。

## 二、领域实体全景

```
┌─────────────────────────────────────────────────────────────┐
│                        租户 (Tenant)                         │
│  一家医疗机构,所有数据的隔离边界                              │
└─────────────────────────────────────────────────────────────┘
        │
        ├── 员工 (Employee)
        │     角色:医生 / 咨询师 / 康复师 / 前台
        │
        ├── 客户 (Customer)
        │     即患者/来访者,所有服务历史的归属主体
        │
        ├── 录音 (Recording)                ← 物理素材层
        │     来源:badge设备 / 手动上传 / app / 实时流
        │     一条录音可能产出 0~N 个服务
        │
        ├── 服务 (Encounter)                ← 业务核心层
        │     一个员工 × 一个客户 × 一段时间的连续交互
        │     │
        │     ├── 结构化记录
        │     │     医生 → 电子病历 (EMR)
        │     │     咨询师 → 咨询记录
        │     │     康复师 → 治疗记录
        │     │
        │     ├── 定量评分
        │     │     沟通质量(segue)/ 专业度 / 效率
        │     │
        │     ├── 跟进任务 (随访/回访/复查)
        │     │     挂在服务上(触发来源)
        │     │     同时挂在客户上(客户维度可见)
        │     │
        │     └── 素材线索 (ContentSeed)
        │           引用服务作为来源,进入独立素材库
        │
        ├── 客户中心
        │     客户主档 + 服务历史 + 随访计划 + 病历/治疗记录汇总
        │
        └── 素材库 (Content)
              候选选题 → 内容生产 → 发布 → 效果追踪
```

## 三、"服务 (Encounter)"的统一定义

### 本质

一个员工对一个客户的一次连续业务交互。三个要素:

- **谁服务谁**:employee_id × customer_id(customer_id 可后补)
- **什么时候**:start_at / end_at
- **什么类型**:由 employee 的 business_scope 决定
  - doctor → 就诊 (consultation)
  - consultant → 接待 (reception)
  - therapist → 治疗 (treatment)
  - frontdesk → 接待(另一种)

### 来源路径

服务可以从三条路径产生:

```
路径 A:事后切分
  长录音 → 转写 → AI 切分 → N 个 encounter → 人工确认

路径 B:实时流
  实时录音 → 实时识别就诊边界 → 即时创建 encounter → 实时填充 EMR

路径 C:短录音 1:1
  短录音(一次服务一条录音)→ 自动创建 1 个 encounter
```

三条路径的产出是同一张表、同一个数据结构。下游分析代码不区分来源。

### 客户关联

服务创建时,客户可能已知也可能未知:

- **已知**(实时流场景,或短录音已关联客户):直接绑定 customer_id
- **未知**(事后切分,录音时不知道患者是谁):
  - 先用兜底标识:`{employee_name}_{start_time}`,如"张医生_14:35"
  - AI 从对话中提取姓名/特征作为候选
  - 人工确认时绑定到客户主档(可新建客户或匹配已有)
  - 绑定后,该服务下的病历/任务等自动归入客户中心

### 确认状态

```
pending     → AI 切分产出,未经人工确认
confirmed   → 人工确认边界和客户归属正确
corrected   → 人工修正过(合并/切开/调边界)
```

未确认的服务仍可进入下游分析(否则什么都看不到),但展示时标注"待确认"。

## 四、录音与服务的关系

```
Recording 1 ──→ N Encounter     (长录音切分)
Recording 1 ──→ 1 Encounter     (短录音)
Recording N ──→ 1 Encounter     (实时流:一次服务跨多段录音片段)
Recording 0 ──→ 1 Encounter     (未来:手动创建服务,无录音)
```

所以关系是 M:N,但大部分情况是 1:N(一条长录音切出多个服务)或 1:1(短录音)。

数据模型上用中间表还是直接外键?

建议:encounter 上保留 `recording_id`(主录音来源),另有 `encounter_recordings` 关联表处理实时流的多段场景。MVP 先只用 `recording_id` 单值,覆盖 95% 情况。

## 五、客户中心的定位

客户中心不是一个独立模块,而是**以客户为主键的聚合视图**:

```
客户 张阿姨
├── 基本信息:女,58岁,138xxxx1234
├── 服务历史:
│   ├── 2026-07-28 就诊 #张医生 - 胃痛(已生成病历)
│   ├── 2026-07-20 就诊 #张医生 - 复查(已生成病历)
│   └── 2026-06-15 咨询 #李咨询师 - 初诊咨询
├── 病历/记录:
│   ├── 2026-07-28 病历:慢性胃炎,奥美拉唑 20mg
│   └── 2026-07-20 病历:复查,症状改善
├── 待随访:
│   └── 2026-08-05 复查(来源:7-28就诊)
└── 沟通记录:
    └── 3 次服务,平均 segue 82 分
```

技术上:不需要新建表,是对已有 customer + encounter + emr + task 的关联查询。但需要 encounter 有 customer_id 才能聚合。

## 六、下游分析的输入统一为 encounter

### 当前(以 recording 为输入)

```
recording → LLM 分析 → EMR + segue + 素材 + 任务
```

问题:长录音的分析结果是混合的(多个患者的内容混在一起)。

### 目标(以 encounter 为输入)

```
encounter → LLM 分析 → EMR + segue + 素材线索 + 任务
```

每个 encounter 的分析是独立的、针对单一患者的。

### 具体变化

| 功能 | 当前输入 | 目标输入 | 变化 | 迁移批次 |
|---|---|---|---|---|
| EMR 生成 | recording 全文 | encounter 段落文本 | 更精准,不混患者 | **第一批** |
| Segue 评分 | recording 全文 | encounter 段落文本 | 评的是一次就诊而不是一上午 | **第一批** |
| 随访任务 | recording | encounter | 任务关联到具体患者 | **第一批** |
| 能力排名 | 按 recording 统计 | 按 encounter 统计 | 更准确(10 次就诊 vs 3 条录音) | 第二批 |
| 周报 | N 条录音 | M 次就诊 | 指标含义变了 | 第二批 |
| 素材提取(ContentSeed) | recording 全文 | 暂不迁 | — | **暂不迁** |
| 成交机会(OpportunityAlert) | recording | 暂不迁 | — | **暂不迁** |

### 暂不迁移的两条线

**ContentSeed(素材线索)和 OpportunityAlert(成交机会提醒)保持挂在 `recording_id` 上不动。**

理由:两者主要服务于运营和咨询师短录音场景(一条录音一个客户),挂 recording 和挂 encounter 语义等价,迁移收益不明显。而 EMR / segue / 随访任务是医生长录音的直接产出,不迁就会出现"病历分患者、评分不分患者"的语义割裂,必须第一批做。

等切分能力推广到咨询师、康复师(那时他们的长录音也会切出多个客户)再统一迁移这两条线。届时按"双写过渡"处理:新增可空的 `encounter_id`,新数据同时写两个字段,旧数据不动,查询层兼容。

### 短录音兼容

短录音自动 1:1 创建 encounter 后,下游代码统一基于 encounter,不需要分支逻辑。

## 八、实时流与事后切分的统一

另一个 agent 在做的"实时流录音 + 实时记录客户和 EMR",和事后切分的关系:

```
实时流:                        事后切分:
录音边识别边创建 encounter        录音结束后 AI 切分出 encounter
↓                              ↓
实时流自己的确认逻辑              批量确认页面(6 种修正操作)
↓                              ↓
        同一张 encounters 表
        同一张 EMR 表
        同一套下游分析
```

**共享的:** encounters 表、EMR 表、下游分析链路、客户中心。
**独立的:** 人工确认交互。

为什么确认交互独立:实时流场景下客户已知(前端选了再录),医生在录音结束时就地确认边界即可,不需要走"从候选客户里挑一个"的流程;事后切分是批量场景,医生一次要过一整天的录音,需要摘要卡片 + 快捷键 + 6 种修正操作。两者的交互密度和信息需求差太远,强行统一会让实时流用户重复确认已知信息。

区别:
- 实时流的 encounter 在录音过程中就创建了,状态可能是 `in_progress`
- 事后切分的 encounter 在分析完成后才创建,状态是 `pending`
- 实时流的 EMR 是逐步 UPDATE 填充的(边录边写),事后的 EMR 是一次性 INSERT 生成的 —— 但落在同一张表,`encounter_id` 关联,客户中心看到的病历视图是统一的

但从数据模型角度,它们是同一个 encounter,只是 `source_type` 不同:
- `realtime` — 实时流产生
- `ai_split` — 事后 AI 切分产生
- `single_recording` — 短录音 1:1 映射
- `manual` — 人工手动创建

## 九、患者识别策略

从服务到客户的绑定,按可靠性分层:

### 即时绑定(录音时就知道)
- 实时流场景:前端已选择客户再开始录音
- Badge + 排班:挂号系统告知当前患者是谁

### AI 推荐 + 人工确认
- 从对话中提取姓名/特征
- 匹配已有客户主档(姓名 + 手机号模糊匹配)
- 页面上给 2-3 个候选,人一键确认

### 兜底标识
- `{employee_name}_{date}_{start_time}`:如"张医生_2026-08-03_14:35"
- 保证 encounter 一定有唯一标识,不会因为不知道患者是谁就丢数据
- 后续任何时候都可以补绑客户

### 去重合并

同一客户如果被多次识别成不同客户(不同录音里出现、AI 提取的姓名有差异),需要合并。合并后,该客户下的服务历史、病历、任务自动汇总。

**入口有两处:**

| 位置 | 形态 | 时机 |
|---|---|---|
| 确认 encounter 时 | 轻量提示:"该患者可能与「张伟(138****5678)」是同一人",可一键合并、可跳过 | 医生确认服务时顺手处理,不强制 |
| 客户中心 | 完整的"疑似重复客户"列表 + 合并工具(选主档、字段取舍、历史归并) | 运营/前台定期批量清理 |

设计原则:确认服务时的提示必须可跳过,不能打断医生的验证节奏(3 秒一条的目标);客户中心兜底,保证漏掉的最终会被处理。合并操作本身的真值和审计都在客户中心,encounter 侧只是发起入口。

## 十、Encounter 表结构(新建 `encounters` 表)

```sql
encounters (
  id              BIGSERIAL PRIMARY KEY,
  tenant_id       BIGINT NOT NULL,
  
  -- 谁服务谁
  employee_id     BIGINT NOT NULL,
  customer_id     BIGINT,                    -- 可后补
  customer_hint   VARCHAR(100),              -- 兜底标识:"张医生_14:35" 或 AI 提取的姓名
  
  -- 什么类型(后端枚举固定,前端显示名走租户字典)
  encounter_type  VARCHAR(32) NOT NULL,      -- consultation/reception/treatment
  business_scope  VARCHAR(32) NOT NULL,      -- doctor/consultant/therapist/frontdesk
  
  -- 什么时候
  start_at        TIMESTAMP,
  end_at          TIMESTAMP,
  duration_seconds INT,
  
  -- 来源
  source_type     VARCHAR(32) NOT NULL,      -- ai_split/realtime/single_recording/manual
  recording_id    BIGINT,                    -- 主来源录音(可空,手动创建时无录音)
  start_seconds   INT,                       -- 在录音中的起止偏移
  end_seconds     INT,
  
  -- 内容
  transcript_text TEXT,                      -- 该段转写文本
  
  -- 切分元数据
  split_run_id    BIGINT,                    -- 哪次切分产出的(事后切分场景)
  split_confidence FLOAT,                   -- 切分置信度
  sequence_no     INT,                       -- 在同一录音中的序号
  
  -- 确认状态
  status          VARCHAR(16) DEFAULT 'pending',  -- pending/confirmed/corrected
  confirmed_by    BIGINT,
  confirmed_at    TIMESTAMP,
  
  -- 下游分析
  analysis_status VARCHAR(16),               -- pending/completed/failed
  analysis_payload JSONB,                    -- 分析结果(EMR/评分等)
  
  -- 审计
  created_at      TIMESTAMP NOT NULL DEFAULT NOW(),
  updated_at      TIMESTAMP NOT NULL DEFAULT NOW()
);
```

### 关键设计说明

**`recording_id` 可空**:支持手动创建服务、实时流跨多段录音的场景。

**没有唯一索引 `(recording_id, sequence_no)`**:重切时需要保留旧版本,不能强制唯一。改用 `split_run_id` 区分不同批次的切分结果。

**`customer_id` 可空 + `customer_hint` 兜底**:保证 encounter 一定有唯一标识,不因为不知道患者是谁就丢数据。

**不平铺存 patient_name/age/phone**:患者信息的真值在 customer 主档。encounter 上只留 `customer_hint` 作为识别线索和未绑定时的显示名。

**`status` 是核心字段**:pending → confirmed/corrected 的流转是整个产品的关键流程,不是附加属性。

**修正不删除重建**:人工合并/切开产生的变更直接 UPDATE/INSERT,并在 `encounter_corrections` 表留审计。绝不能像旧表那样"先 DELETE 再 INSERT"。

### 配套表

```sql
-- 人工修正审计
encounter_corrections (
  id, tenant_id, encounter_id, corrected_by,
  correction_type,        -- confirm/merge/split/adjust/delete/add
  details JSONB,          -- 修正详情(合并了哪些、切在哪里)
  created_at
);

-- 实时流场景:一次服务跨多段录音(MVP 可暂不建)
encounter_recordings (
  encounter_id, recording_id, sequence_no,
  start_seconds, end_seconds
);
```

## 十一、从现状到目标的迁移路径

不是推倒重来,而是渐进替换:

1. **阶段 0:切分质量验证**(进行中)—— demo 页面调 prompt,积累医生修正数据作为基线,不建表不改下游
2. **新建 `encounters` 表**,旧 `op_encounters` 保留不动
3. **短录音自动创建 encounter**(1:1 映射),下游代码开始基于 encounter 读数据
4. **长录音切分产出 encounter** + 医生确认流程上线
5. **第一批下游迁移**:EMR、segue、随访任务改为以 encounter 为输入
6. **实时流产出 encounter**(另一个 agent 的工作,需先对齐字段语义)
7. **前端入口从录音列表切到服务列表**
8. **第二批下游迁移**:能力排名、周报口径改为按 encounter 统计
9. **录音库退化为后台管理**
10. **ContentSeed / OpportunityAlert 迁移**(等切分推广到咨询师、康复师后)

每一步都向下兼容。在任何中间状态,系统都是可用的。

关键顺序约束:第 5 步必须在第 4 步之后(要有确认过的 encounter 才有意义);第 6 步必须在第 2 步之后(表要先存在);第 8 步指标口径变更是对外可见的,需要提前和客户沟通。

## 十二、已决策事项

### 12.1 新建 `encounters` 表,不改造 `op_encounters`

**决定:新建表。**

现有 `op_encounters` 是 MVP 阶段的"分析结果投射视图",不是业务实体。从设计细节可以确认:

| 现有设计 | 说明 | 与新模型的冲突 |
|---|---|---|
| `source_type DEFAULT 'analysis'` | 默认来自分析 | 新模型有 4 种来源 |
| `recording_id NOT NULL` | 必须有录音 | 新模型允许手动创建、实时流 |
| `UNIQUE (recording_id, sequence_no)` | 每录音每序号唯一 | 重切时无法保留版本 |
| `patient_name/age/phone` 直接存 | 患者信息平铺 | 新模型要关联 customer_id |
| 无 `status`/`confirmed_by` | 无确认流程 | 新模型核心是人工确认 |
| 无 `encounter_type` | 只有 scene | 新模型需要服务类型 |
| `ProjectEncounterFromRecording()` 先 DELETE 再 INSERT | 投射视图模式 | 人工修正会被冲掉 |

最后一条是关键:现有实现每次分析都会删除该录音的所有 encounter 再重建。这意味着人工修正的结果在下次分析时全部丢失。这与"人工确认是核心流程"的新模型根本冲突。

**处理方式:**
- 新建 `encounters` 表(不带 `op_` 前缀,因为它是业务主表而非运营视图)
- 旧 `op_encounters` 保留,现有 3 个 ops API 继续用,不影响
- 新功能全部基于新表
- 旧表在新表稳定后可废弃(它没有生产数据依赖)

### 12.2 切分能力必须角色无关

**确认:咨询师、康复师也存在"一条录音多个客户"的情况,只是当前没做切分。**

这意味着切分不是"医生专属功能",而是所有角色的通用能力。设计上:

- **切分框架统一**:同一套 segment 契约、同一套确认交互、同一张 encounter 表
- **边界信号按角色配置**:
  - 医生:"下一个"、"哪里不舒服"、叫号
  - 咨询师:"您好请坐"、换来访者、咨询主题切换
  - 康复师:换课时、器械交接、治疗项目切换
- **prompt 按角色版本化**:通过现有的 `analysis_role_routes`(tenant + role + scene → pipeline)路由到不同的切分 prompt

阶段 0 验证时:先用医生录音把框架和方法论跑通(因为长录音场景最典型),然后各角色分别调 prompt。不需要三个角色同时验证。

### 12.3 实时流与事后切分:共享数据,独立交互

**决定:共用 `encounters` 表、共用 EMR 表,但人工确认交互各自独立。**

| 维度 | 实时流 | 事后切分 |
|---|---|---|
| encounters 表 | 共用,`source_type='realtime'` | 共用,`source_type='ai_split'` |
| EMR 表 | 共用,逐步 UPDATE 填充 | 共用,一次性 INSERT |
| 确认交互 | 自己的逻辑(客户已知,录完就地确认边界) | 批量确认页面(摘要卡片 + 快捷键 + 6 种修正) |
| 下游分析 | 共用 | 共用 |
| 客户中心 | 共用 | 共用 |

数据层统一保证了客户中心的服务历史、病历视图不需要区分来源。交互层分开是因为两者的信息需求不同:实时流客户已知,不该让用户重复确认;事后切分是批量场景,要优化单条判断速度。

**对接实时流 agent 的接口约定:** 实时流侧只需要保证写入 `encounters` 表时字段语义一致(`source_type`、`status`、`customer_id`/`customer_hint`、`encounter_type`),确认交互怎么做由实时流侧自行决定。

### 12.4 服务类型:后端枚举固定,显示名租户可配

**决定:数据库层用固定枚举,前端显示名走租户配置字典。**

后端固定枚举(不随机构叫法变化):

| `encounter_type` | 默认显示名 | 对应角色 |
|---|---|---|
| `consultation` | 就诊 | doctor |
| `reception` | 接待 | consultant / frontdesk |
| `treatment` | 治疗 | therapist |

前台和咨询师后端都用 `reception`,靠 `business_scope` 区分。原因:两者的业务本质相同(接待来访者、推进转化),切分的边界信号也相似,没必要在类型层面拆开。需要区分统计口径时按 `business_scope` 分组即可。

显示名可配置的必要性:不同机构叫法差异大 —— 医美叫"面诊",齿科叫"初诊/复诊",康复机构叫"课时"。硬编码"就诊"会让非诊所类客户觉得系统不贴合。配置粒度:tenant + encounter_type → 显示名。

### 12.5 客户去重合并:双入口

**决定:确认 encounter 时给可跳过的轻量提示,客户中心提供完整合并工具。**

详见第九节"去重合并"。核心约束:轻量提示不能打断医生的批量验证节奏。

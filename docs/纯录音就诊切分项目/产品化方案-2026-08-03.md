# 就诊切分产品化方案

日期:2026-08-03
状态:方案设计中

## 一、当前状态

### 已完成(MVP Demo)

- 独立测试页面,挂在 `/internal/split-demo`
- 从开发数据库读取灵策医院(tenant_id=1)的医生长录音
- 调千问 qwen-max 做切分,产出 segment 列表
- 就诊摘要卡展示(患者/主诉/处置/开场/结束)
- 边界检查区(切口前后对话)
- 人工确认与修正(6 种操作)
- 修正结果保存为基准 JSON
- 分块处理超长录音
- 进度显示

### 已有基础设施(主系统)

- `analysis_runs` / `analysis_step_runs`:分析任务审计,含 pipeline_code、prompt_version、token 用量、成本
- `analysis_role_routes`:按 tenant + role + scene 路由到具体 pipeline
- `op_encounters` 表:已存在,有 recording_id、sequence_no、start/end_seconds、analysis_payload 等
- `ProjectEncounterFromRecording()`:从分析结果投射 encounter 记录
- `pkg/llmgateway`:LLM 调用 + 计费归因
- `lingce-worker`:异步任务队列(transcribe/analyze/clean)
- 菜单权限体系:`institution_menus` + role 级控制
- 幂等迁移模式:`internal/store/compat_migration.go`

## 二、产品化目标

把 demo 验证通过的切分能力,变成**所有医生长录音自动触发、医生/助手可确认修正、下游分析基于 encounter 运行**的生产功能。

## 三、产品化与 Demo 的关键差异

| 维度 | Demo | 产品 |
|---|---|---|
| 触发方式 | 手动选一条点按钮 | 录音完成转写后自动触发 |
| LLM 调用 | 直接调千问,不计费不审计 | 走 llm-gateway,纳入计费归因 |
| 结果存储 | 不写数据库 | 写 `op_encounters` 表 |
| 切分 prompt | 页面上随便改 | 版本化管理,走 analysis_step_runs 审计 |
| 用户界面 | 独立测试页,无权限 | 正式页面,挂菜单,走权限 |
| 人工修正 | 保存为本地 JSON | 写数据库,修正记录可追溯 |
| 下游消费 | 无 | EMR、沟通分析、素材提取基于 encounter 运行 |
| 错误处理 | 基本 | 重试、告警、降级 |
| 多租户 | 只有 tenant_id=1 | 所有租户,按路由配置启用 |

## 四、分阶段计划

### 阶段 0:切分能力验证(当前)

目标:确认 prompt 效果达标(漏切 < 0.5 次/录音,多切 < 1 次/录音)

工作:
- 用 demo 页面跑 10 条录音,医生修正并保存基准
- 反复调 prompt 直到指标达标
- 建立自动评测脚本(3-5 条基准即可)

产出:稳定的切分 prompt(带版本号)、评估基准集、达标的评测报告

前置条件:无,现在就在做

### 阶段 1:切分接入正式 pipeline

目标:切分作为分析链路的一个 step,自动触发,结果入库

#### 1.1 新增 pipeline step:encounter_split

在现有 analysis pipeline 里加一步:

```
transcribe → [encounter_split] → analyze(per encounter)
```

具体:
- 新建 pipeline_code: `doctor_encounter_split` (或作为现有 doctor pipeline 的一个 step_code)
- step_code: `encounter_split`
- 输入:录音的转写文本
- 输出:segment 列表(符合第六节契约)
- prompt_code 和 prompt_version 走 `analysis_step_runs` 审计

#### 1.2 LLM 调用切换到 llm-gateway

- 从 demo 的直接调千问,改为走 `pkg/llmgateway`
- 补上 BillingMetadata:
  - BusinessDomain: `recording`
  - BillingSubject: `encounter_split`
  - BillingScene: `recording_encounter_split`
  - RecordingID: 对应录音 ID

#### 1.3 结果写入 op_encounters

- 切分完成后调用 `ProjectEncounterFromRecording()`(已有)
- 但需要改造:当前它从 analysis_payload 里找 `encounters` key,新的切分结果格式需要适配
- encounter 记录的 `source_type` 标记为 `ai_split`
- `source_prompt_code` / `source_prompt_version` 记录切分用的 prompt

#### 1.4 自动触发逻辑

判断条件:录音满足以下条件时自动触发切分:
- `business_scope = 'doctor'`
- `duration > N 秒`(阈值待定,建议 600 秒 = 10 分钟)
- 转写已完成(`transcription_status = 'completed'`)
- 尚未切分过(或配置了自动重切)

触发点:在 lingce-worker 完成 transcribe job 后,自动入队一个 `encounter_split` job

#### 1.5 路由配置

- 在 `analysis_role_routes` 里为需要切分的 tenant + role 配置路由
- 初期只给灵策医院(tenant_id=1)+ doctor 角色启用
- 后续逐租户开放

工作量估算:后端 3-5 天

### 阶段 2:医生确认页面(正式版)

目标:把 demo 的确认修正功能做成正式产品页面

#### 2.1 页面位置

两种方案:
- A: 在现有"医生录音详情"页里加一个"就诊列表" tab
- B: 独立"就诊确认"页面,从录音列表跳转

建议 A,因为录音是入口,就诊是录音的子内容。

#### 2.2 菜单与权限

- 新增菜单 code:`doctor_recordings_encounters`
- 挂在"医生录音"菜单组下
- 需要角色配置才能看到

#### 2.3 核心交互复用 demo

从 demo 迁移:
- 就诊摘要卡(患者/主诉/处置/开场/结束)
- 六种操作(确认/合并/切开/调边界/删除/补充)
- 键盘快捷键
- 验证进度和汇总

改造点:
- 去掉"提示词编辑区"(生产环境不暴露 prompt)
- 去掉"原始 JSON"面板
- 加上权限校验
- 修正结果写数据库而不是 JSON 文件

#### 2.4 修正结果持久化

新增表 `encounter_corrections`:
```sql
CREATE TABLE IF NOT EXISTS encounter_corrections (
  id BIGSERIAL PRIMARY KEY,
  tenant_id BIGINT NOT NULL,
  recording_id BIGINT NOT NULL,
  corrected_by BIGINT NOT NULL,  -- employee_id
  correction_type VARCHAR(32) NOT NULL,  -- confirm/merge/split/adjust/delete/add
  original_encounter_id BIGINT,
  details JSONB,
  created_at TIMESTAMP NOT NULL DEFAULT NOW()
);
```

修正后:
- 更新 `op_encounters` 表(合并/切开/调整/删除/新增)
- 被确认的 encounter 标记 `confirmed_at` / `confirmed_by`
- 所有操作记录到 `encounter_corrections` 表(审计用)

#### 2.5 确认状态影响下游

- 未确认的 encounter:可以跑下游分析,但结果标记"待确认"
- 已确认的 encounter:正式进入下游(EMR、沟通分析、素材)
- 被删除/合并的 encounter:下游结果作废

是否硬阻断未确认的 encounter 进入下游?建议先不硬阻断(否则医生不确认就什么都看不到),但在展示时明确标注"基于未确认的切分结果"。

工作量估算:前端 5-7 天,后端 3-4 天

### 阶段 3:下游分析基于 encounter 运行

目标:EMR、沟通分析、素材提取的输入从"整条录音"变成"单次 encounter"

#### 3.1 分析触发改造

现有:录音 → 整体分析 → 结果
改为:录音 → 切分 → N 个 encounter → 每个 encounter 独立分析

技术实现:
- 切分完成后,对每个 encounter 独立触发分析 run
- 每个 run 的输入是该 encounter 的转写文本(按时间裁取)
- 各 run 独立成功/失败,互不影响

#### 3.2 现有功能适配

需要改造的:
- **EMR**:从 recording 级变成 encounter 级,一条录音 N 份 EMR 草稿
- **沟通分析(segue)**:从 recording 级变成 encounter 级,每次就诊独立评分
- **素材提取(benchmark)**:从 recording 级变成 encounter 级,更精准

不需要改的(聚合类):
- 周报、能力排名:仍然按员工聚合,只是数据源从 recording 变成 encounter
- 质控 dashboard:同上

#### 3.3 数据模型调整

EMR:
- `recording_emr_drafts` 加 `encounter_id` 字段
- 一条录音可能有 N 条 EMR draft

Benchmark clips:
- `recording_benchmark_clips` 加 `encounter_id` 字段
- 候选来源从录音变成 encounter

Segue scores:
- 需要 encounter 级评分字段(可以放在 encounter 的 analysis_payload 里)

#### 3.4 短录音兼容

现有短录音(一条录音 = 一次就诊)不需要走切分,但需要统一模型:
- 自动为短录音创建一条 encounter 记录(1:1 映射)
- `source_type = 'single_recording'`(区别于 `ai_split`)
- 下游代码统一基于 encounter 运行,不区分来源

工作量估算:后端 7-10 天,前端 5-7 天(EMR/segue 页面改造)

### 阶段 4:录音列表向就诊列表过渡

目标:前端主入口从"录音列表"逐步切换到"就诊列表"

这是产品形态的根本变化(业务标的物从录音变为就诊),需要产品设计介入,不在纯技术层面展开。

技术上的准备工作在阶段 3 完成后已具备:
- 所有分析结果挂在 encounter 上
- encounter 有独立列表接口(`GET /api/v1/ops/encounters` 已存在)
- 短录音也有 encounter 记录

前端改版可以渐进:先加"就诊列表"入口,和"录音列表"并存,后者逐步退化为后台管理入口。

## 五、阶段依赖关系

```
阶段 0 (现在)
  │
  ▼ prompt 达标
阶段 1 (切分入 pipeline)
  │
  ├──▶ 阶段 2 (确认页面) ──可并行
  │
  ▼ 切分稳定运行
阶段 3 (下游基于 encounter)
  │
  ▼
阶段 4 (就诊列表)
```

阶段 1 和 2 可以并行(pipeline 接入和确认页面互不阻塞)。
阶段 3 依赖阶段 1(得先有 encounter 数据)。
阶段 4 依赖阶段 3(得先有 encounter 级的分析结果)。

## 六、风险与应对

### 切分准确率不够

风险:prompt 调不到 < 0.5 漏切,上线后医生修正负担太重
应对:阶段 0 不过关就不进入阶段 1。如果千问效果不够,考虑换模型(Claude、GPT-4o)或加后处理规则

### 超长录音成本

风险:240 分钟录音分 4 块调用,成本较高;如果每天几百条,费用不可忽略
应对:
- 阶段 1 先用 llm-gateway 计费归因看清实际成本
- 如果太贵,考虑:用更便宜的模型做粗切 + 贵模型做精切;或者 VAD + 规则做粗切,只在边界模糊处调模型

### 短录音兼容性

风险:给短录音强制创建 encounter 记录,可能产生大量无意义数据和额外处理
应对:设置时长阈值,低于阈值的短录音只在需要时懒创建 encounter(比如第一次访问就诊详情时)

### 重切后数据一致性

风险:重新切分后旧 encounter 的下游数据(EMR、评分)失效
应对:
- 重切产生新的 analysis_run,旧 encounter 不删除,标记 `superseded_by_run_id`
- 下游数据挂在 encounter_id 上,旧 encounter 的下游数据保留但标记为"基于旧版切分"
- 前端默认展示最新版本

## 八、当前最重要的一件事

**完成阶段 0:把 prompt 调到达标。**

这是所有后续工作的前置条件。如果切分效果不够好,后面的产品化全部没有意义。

具体做法:
1. 用 demo 页面跑完 10 条录音
2. 每条让医生确认修正,保存为基准
3. 看指标:漏切、多切、医生平均修正次数
4. 如果指标不达标,调 prompt,重跑,再看指标
5. 直到达标(漏切 < 0.5、多切 < 1、平均修正 < 1)

达标后,阶段 1 和 2 可以同时启动。

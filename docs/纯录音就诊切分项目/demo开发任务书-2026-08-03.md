# 切分 Demo 开发任务书

日期:2026-08-03
交付对象:Codex
依据文档:就诊定义与切分判据-2026-08-03.md(第六节为输出契约)

## 目标

做一个独立的测试页面,用于验证 encounter 切分效果。核心循环是:选录音 → 调 prompt → 看切分结果 → 快速验证 → 调整 → 再跑。

## 整体调用链路

一次完整的切分验证包含两步 LLM 调用:

1. **切分调用**(重):对整条转写文本调千问,产出 segment 列表(含 encounter / idle / non_encounter_talk / uncertain)
2. **摘要调用**(轻):对每个 encounter 的文本单独调千问,只提取患者、主诉、处置三个字段,用于就诊摘要卡展示

两步都用千问 qwen-max。切分调用可能需要分块(超长录音);摘要调用每个 encounter 一次,输出只有一行 JSON,非常轻量。

前端的处理进度显示:
- 切分阶段:"正在切分... 第 2/4 块"
- 摘要阶段:"正在生成摘要... 第 3/8 个就诊"
- 全部完成后展示结果

## 范围

### 做

- 一个独立页面(不挂菜单、不做权限、不做登录)
- 从数据库读取 tenant_id=1 的长录音列表(只需 id、时长、员工名、日期)
- 选一条录音后,读取其转写文本
- 用转写文本调用 LLM 做切分,产出符合第六节契约的 segment 列表
- 在页面上展示切分结果:就诊摘要卡 + 边界检查区 + 时间轴总览
- 切分完成后自动对每个 encounter 生成就诊摘要(患者、主诉、处置)
- 可在页面上编辑/切换提示词,重新跑切分
- 医生/助手可通过摘要卡 3 秒快速验证每次就诊,标记正确或有问题
- 展示本次调用的 token 用量和耗时

### 不做

- 不做用户认证和权限
- 不走 llm-gateway,直接调 LLM API,配置 API key 即可
- 不写入数据库(切分结果和摘要只在页面展示,不持久化)
- 不做 encounter 的下游分析(病历、评分等)
- 不做批量跑(一次只跑一条)
- 不做前端构建工具链优化

不强制,Codex 可根据实际情况调整:

## 数据怎么取

### 数据在哪里

我们已经从生产环境选了 10 条超长医生接诊录音,放在**开发数据库**(`lingce_dev`,连接配置在 `configs/dev.toml`)的 **租户 ID = 1(灵策医院)** 里。这些录音应该已经完成了转写。

筛选条件:
- 数据库:`lingce_dev`(即 `configs/dev.toml` 里配置的那个)
- `tenant_id = 1`
- `business_scope = 'doctor'`(医生接诊录音,不是咨询师也不是康复师)
- 长录音(时长较大的那些)
- 已完成转写(`transcription_text` 非空)

### 重要:数据库真实列名和 Go 结构体字段名不一致

`recordings` 表的实际列名(从 `internal/recording/store.go` 的查询里确认过):

| Go 结构体字段 | 数据库真实列名 |
|---|---|
| `TranscriptText` | `transcription_text` |
| `RecordingDuration` | `duration` |
| `RecordingURL` | `file_url` |
| `RecordingStartedAt` | `recorded_at` |

写 SQL 时用右边那列,不要用 Go 字段名。

### 录音列表查询

```sql
SELECT
  r.id,
  r.duration,
  COALESCE(e.name, '') AS employee_name,
  r.recorded_at,
  r.business_scope,
  LENGTH(COALESCE(r.transcription_text, '')) AS transcript_length,
  r.transcription_status,
  r.analysis_status
FROM recordings r
LEFT JOIN employees e ON e.id = r.employee_id
WHERE r.tenant_id = 1
  AND r.deleted_at IS NULL
  AND LOWER(COALESCE(r.business_scope, '')) = 'doctor'
  AND r.transcription_text IS NOT NULL
  AND LENGTH(r.transcription_text) > 2000
ORDER BY r.duration DESC NULLS LAST
LIMIT 20;
```

`business_scope = 'doctor'` 是医生接诊录音的筛选条件(其他值:`consultant` 咨询师、`therapist` 康复师、`frontdesk` 前台)。

### 取单条录音的转写

```sql
SELECT
  r.id,
  r.duration,
  r.transcription_text,
  COALESCE(r.analysis_result, '{}'::json) AS analysis_result
FROM recordings r
WHERE r.id = $1 AND r.tenant_id = 1;
```

### 开发第一步:先确认转写数据形态

在写任何切分逻辑之前,先跑上面的列表查询,确认:

1. 有几条录音满足条件,时长分布如何
2. `transcription_text` 是纯文本还是带说话人标记的文本
3. `analysis_result` 里有没有带时间戳的分段结构

第 3 点最关键。检查方法:

```sql
SELECT
  r.id,
  jsonb_pretty(r.analysis_result::jsonb) 
FROM recordings r
WHERE r.tenant_id = 1 AND r.id = <某条录音id>;
```

看里面是否有 `segments` / `sentences` / `timeline` 之类的字段,以及是否带 `start_time` / `begin_time` / `start_ms` 这类时间戳。

**如果有时间戳分段**:切分的输入用它,输出的 `start_seconds` / `end_seconds` 是真实值。

**如果只有纯文本没有时间戳**:切分只能给出文本位置(字符 offset 或句子序号),`start_seconds` / `end_seconds` 需要按比例估算,精度会差。这种情况下要在页面上标注"时间为估算值",并且这是一个需要反馈给我们的重要发现——它会影响整个方案的可行性判断。

现有代码 `internal/recording/service.go` 里的 `buildTranscriptFromSegments` 函数(约 4405 行)展示了系统支持的 segment 格式,兼容 `start_seconds` / `start_time` / `start` / `start_ms` 多种写法,可以参考它来解析。

## 提示词初版

以下是 v0.1 初版提示词,直接用,不要改写。页面上要能编辑它,后续靠调这个来提升效果。

### System Prompt

```
你是一个医疗录音结构化助手。你的唯一任务是把一段连续的门诊录音转写文本,按时间轴切分成连续的片段,并判断每个片段的类型。

## 你要做的事

把整条时间轴切成连续、不重叠、完整覆盖的片段。每个片段判断两件事:
1. 它的类型(是一次就诊,还是非就诊内容)
2. 它的起止位置

## 你不要做的事

- 不要识别患者姓名、年龄、性别、电话
- 不要生成主诉、诊断、病历、处方
- 不要评价医生表现
- 不要总结对话内容
- 不要提取任何可用于宣传的片段

以上都由后续环节处理。你只回答"边界在哪里、这段是什么类型"。

## 片段类型定义

- `encounter`:一次就诊。一个患者(含陪同家属)与医生的连续诊疗交互,包含问诊、查体、解释、开方、医嘱中至少一项。
- `non_encounter_talk`:非就诊对话。医生与同事讨论排班/器械、接电话、闲聊。即使内容涉及某位患者的病情,只要患者不在场,也归此类。
- `idle`:静默或无有效内容。
- `uncertain`:无法判断类型,需人工复核。

## 就诊边界的裁定规则

判定为同一次就诊(不切开):
- 同一患者连续讲多个不相关的问题
- 家属代述,患者本人不在场
- 患者中途离开做检查后返回
- 医生短暂离开,患者留在诊室
- 内部短静默(30 秒以内)
- 医生查阅资料、书写记录时的静默
- 夫妻同诊、母子同诊等多位患者同时在场、医生交替问诊的情况 —— 判为一次 encounter,并标记 multi_patient: true

判定为不是就诊:
- 患者只是问路、拿报告、取药,没有诊疗内容
- 医生与同事的任何交流

## 边界信号(按可靠性排序)

强信号:
- 叫号或点名:"下一个"、"张三"、"李阿姨来了"
- 明确的结束语:"没什么问题了"、"回去吃药"、"下周再来"、"好,就这样"
- 明确的开场语:"哪里不舒服"、"什么时候开始的"、"坐吧"
- 长静默(超过 90 秒)

中等信号:
- 主诉突变且与前文无关联
- 称谓变化:"阿姨"变成"小伙子"
- 中等静默(30 到 90 秒)
- 寒暄模式重现

弱信号:
- 固定问诊句式重复出现
- 语气回到问诊开场状态

## 最重要的原则:宁可多切,不要漏切

把两个不同患者错误地合并成一段,是严重错误。它会导致 A 患者的主诉和 B 患者的诊断混进同一份病历,产生临床安全风险,而且很难被发现。

把一次就诊错误地切成两段,是轻微错误。人工合并即可修复。

因此:
- 遇到疑似不同患者时,优先切开
- 拿不准的边界,切开并标记低置信度
- 不要为了让片段"看起来完整"而合并可疑区域

## 输出格式

只输出 JSON,不要任何解释文字、不要 markdown 代码块标记。

{
  "segments": [
    {
      "index": 1,
      "segment_type": "encounter",
      "start_seconds": 0,
      "end_seconds": 412,
      "boundary_confidence": 0.93,
      "boundary_reasons": ["closing_phrase:没问题了回去吧", "silence_38s"],
      "silence_gap_seconds": 38,
      "needs_review": false,
      "multi_patient": false,
      "contains_clinical_info": null,
      "text_preview": "医生:坐吧,哪里不舒服? 患者:最近胃一直疼..."
    }
  ]
}

字段说明:
- index: 从 1 开始的连续序号
- segment_type: encounter | non_encounter_talk | idle | uncertain
- start_seconds / end_seconds: 相对录音开始的偏移秒数
- boundary_confidence: 0.0 到 1.0,你对这个片段边界判定的可信程度
- boundary_reasons: 你依据了哪些信号,写成 "信号类型:具体证据" 的形式
- silence_gap_seconds: 该片段与下一片段之间的静默秒数,不确定时填 null
- needs_review: boundary_confidence 低于 0.75 时必须为 true
- multi_patient: 仅 encounter 类型有意义,疑似多位患者同时就诊时为 true,否则 false
- contains_clinical_info: 仅 non_encounter_talk 类型有意义,该段是否涉及患者病情。其他类型填 null
- text_preview: 该片段开头约 100 字,用于列表快速识别

## 硬性约束

1. 第一个片段的 start_seconds 必须是 0
2. 最后一个片段的 end_seconds 必须等于录音总时长
3. 相邻片段必须首尾相接:segments[i].end_seconds == segments[i+1].start_seconds
4. 不允许有间隙,不允许重叠
5. 每个片段的 end_seconds 必须大于 start_seconds
```

### User Prompt

```
录音总时长:{{duration_seconds}} 秒

转写文本:

{{transcript}}

请按 system prompt 的要求切分这条录音的时间轴,输出 JSON。
```

### 变量说明

- `{{duration_seconds}}`:从 `recordings.duration` 取
- `{{transcript}}`:转写文本。如果有带时间戳的 segments,格式化成每行 `[起始秒-结束秒] 说话人: 内容`,例如:

```
[0-8] 医生: 坐吧,哪里不舒服?
[9-25] 患者: 最近胃一直疼,吃了东西就胀
[26-31] 医生: 疼多久了?
```

如果只有纯文本没有时间戳,直接给原文,并在 user prompt 里加一句说明:`转写文本没有时间戳,请按文本长度比例估算时间。`

### 分块策略(超长录音)

如果转写文本超过模型上下文限制(qwen-max 上下文约 32k tokens,实际可用文本约 2 万字):

1. 按时间切成若干块,每块约 15-20 分钟,**块之间保留 2 分钟重叠**
2. 每块独立调用一次,得到局部 segments
3. 合并时处理重叠区:如果两块在重叠区都判定了边界且时间接近(相差 30 秒内),视为同一个边界,取置信度高的那个
4. 合并后重新编号 index,并校验硬性约束 1-5

重叠区的作用是避免边界正好落在块的切口上被漏掉。

MVP 阶段合并逻辑做最简版本即可,先把单块跑通再处理分块。

### 完整文本从哪来:不要让模型返回

模型只返回边界(`start_seconds` / `end_seconds`)和 `text_preview`。**每段的完整对话文本由后端按时间区间从转写数据里裁取**,不要求模型把原文抄回来。

理由:
- 让模型重复输出原文会浪费大量 output token,240 分钟录音可能翻几倍成本
- 模型抄写时可能改字、漏句,导致展示的文本和真实转写不一致,人工验证就失去了意义
- 后端按时间裁取是确定性操作,不会出错

所以后端返回给前端的数据结构是:模型给的 segments,每段补上一个 `full_text` 字段(或 `utterances` 数组,带每轮的时间和说话人),由后端从转写数据裁取后填充。

如果转写数据只有纯文本没有时间戳,裁取只能按字符比例估算,这种情况下要在页面上明确标注文本可能不准。

## 页面需要展示什么

### 设计目标:人能判断切得对不对

这一点是整个 demo 的成败关键。只显示"第 1 段 0-412 秒 置信度 0.93"这种信息,人是无法验证切分质量的。

人判断切分对不对的实际过程是:
1. 读这一段的完整对话,判断它是不是一个完整的、单一患者的就诊
2. 看切口处前后几句,判断这一刀切在了正确的位置
3. 如果切错了,能看出是漏切(两个患者粘在一起)还是多切(一次就诊被拆开)

页面必须支撑这三个动作。

### 1. 录音选择区

下拉或列表,显示 id、时长(格式化成"38分12秒"而不是 2292 秒)、员工名、录音日期、转写字数。

### 2. 提示词编辑区

两个 textarea 分别放 system prompt 和 user prompt,预填任务书里的 v0.1。一个"执行切分"按钮。

### 3. 时间轴总览

一条横向色条,按时长比例显示各 segment,颜色区分类型:
- `encounter` 绿色
- `non_encounter_talk` 蓝色
- `idle` 灰色
- `uncertain` 黄色

`needs_review = true` 的段加红色边框或斜纹标记。

鼠标悬停显示该段的时间和类型,点击滚动到下面对应的详情。

这个条形图的价值是让人一眼看出:切了几段、时长分布是否合理、有没有异常碎片、非就诊内容占比多少。

### 4. 就诊视图(默认显示,这是主视图)

**这是整个页面最重要的部分。** 页面的目的是验证"就诊切分对不对",所以主视图只展示 encounter,不要把 23 段平铺。

encounter 和 idle / non_encounter_talk 混在一个列表里,人无法聚焦到要验证的对象上。

#### 关键设计原则:让医生3秒判断一次就诊

医生或助手判断切分对不对的真实需求是:**这一段是不是一个完整的患者,而且只有这一个患者。**

他们不需要读完整段对话才能判断。他们只需要看几个关键信息:**患者是谁、主诉什么、怎么处理的、开场和结束的话对不对。** 3 秒就能判断出来。

所以每次就诊先显示一张**就诊摘要卡**,而不是直接展开完整对话。

#### 就诊摘要卡的结构

```
┌─ 就诊 #3 ──────────────────────────────────┐
│                                             │
│  👤 患者:阿姨,58岁                          │
│  🗣️ 主诉:胃疼一周,吃东西就胀                │
│  💊 处置:开了奥美拉唑,嘱一周后复诊           │
│  ⏱️ 14:35 - 21:20 (6分45秒)                │
│  📊 置信度:0.93 高                          │
│                                             │
│  开场:"坐吧阿姨,哪里不舒服?"               │
│  结束:"好,没问题了,回去按时吃药"            │
│                                             │
│  [✓ 切分正确]  [✗ 有问题,需查看]            │
│                                             │
│  ▶ 展开完整对话                              │
└─────────────────────────────────────────────┘
```

医生看这张卡,3 秒判断:对,这是那个胃疼的阿姨,开始和结束都对。点 `✓ 切分正确`,自动跳到下一张。

如果摘要看着不对(比如"主诉:胃疼"但他记得那是个咳嗽的患者),点 `▶ 展开完整对话` 细看,再决定标记正确还是有问题。

#### 摘要卡的字段从哪来

**患者、主诉、处置** 三个字段:需要对每个 encounter 的文本单独调用一次 LLM(轻量),只生成一行 JSON。

System prompt:
```
你是医疗记录助手。从就诊对话中提取关键信息,只输出 JSON,不要任何解释。

输出格式:
{"patient_hint":"患者特征,如'阿姨,58岁'或'小伙子,20多岁'", "chief_complaint":"主诉,10-20字", "disposition":"处置,如'开了XX药'或'建议XX检查',10-20字"}

如果某项信息对话中未提及,该字段填空字符串 ""。
```

User prompt:
```
就诊对话:

{{该段encounter的完整文本}}

提取患者、主诉、处置,输出 JSON。
```

这次调用很轻量(输入一段就诊文本约 1000-3000 字,输出只有一行 JSON 不超过 100 字),成本可忽略。而且只在切分完成后对 encounter 调用,不是对所有 segment 调用。

**开场句和结束句**:直接取该 encounter 文本的第一轮和最后一轮对话,不需要 LLM。每句截取前 30 字。

**时间、置信度**:切分结果里已有。

#### 就诊摘要卡的交互

默认状态:摘要卡收起,只显示上面那些信息,完整对话不可见。

点击 `▶ 展开完整对话`:摘要卡下方展开一个区域,显示该 encounter 的完整转写文本(按轮次分行,带时间戳)。箭头变成 `▼ 收起对话`。

点击 `✓ 切分正确`:
- 该卡片右上角显示绿色勾标记
- 自动滚动到下一张卡片
- 顶部汇总更新:`人工验证:3/8 已验证`

点击 `✗ 有问题,需查看`:
- 该卡片标记为橙色,右上角显示问号图标
- 自动展开完整对话(因为标了有问题,一定要看对话才能确定怎么错的)
- 自动滚动到下一张卡片
- 顶部汇总更新:`人工验证:3/8 已验证(2 正确,1 有问题)`

#### 键盘快捷键(重要)

医生连续验证 8 个就诊时,用鼠标点会很慢。加键盘操作:

- `Y` 或 `→`:标记当前卡片为正确,跳到下一张
- `N` 或 `←`:标记当前卡片为有问题,展开对话
- `空格`:展开/收起当前卡片的完整对话
- `↑` / `↓`:在卡片之间移动焦点,不做标记

当前焦点卡片要有明显的视觉标识(比如左侧一条蓝色竖线或整卡描边),让人知道键盘操作作用在哪张卡上。

页面上要有一行小字提示这些快捷键。

这个交互设计让医生可以:看摘要 → 按 Y → 看下一张摘要 → 按 Y,一路验证下去,遇到可疑的按 N 停下细看。8 个就诊 2 分钟内验完。

#### 就诊之间的边界检查区

**这是判断切分对不对的核心工具。** 在相邻两次就诊的卡片之间,插入:

```
───────── 边界检查:就诊#1 与 就诊#2 之间 ─────────

就诊 #1 结尾:
  [12:50] 医生:那就先吃一周看看
  [13:02] 患者:好的谢谢医生
  [13:15] 医生:不客气,有问题再来

中间间隙 (13:20 - 14:35,共 1分15秒):
  ⏸ 静默 38 秒
  💬 非就诊对话 37 秒:"小王下午谁值班"

就诊 #2 开头:
  [14:35] 医生:坐吧,哪里不舒服?
  [14:44] 患者:最近咳嗽一直好不了

─────────────────────────────────────────────────
```

中间间隙部分要把 encounter 之间的所有 idle / non_encounter_talk 段汇总显示,让人知道这段时间发生了什么。

人看这个区域就能判断:上次就诊真的结束了吗、下次就诊真的是新患者吗、这一刀切在正确位置了吗。

### 5. 完整时间轴视图(折叠,调试用)

## 一个具体的展示原则

所有时间一律用 `MM:SS` 或 `HH:MM:SS` 格式,不要用裸秒数。人读"2292 秒"要在脑子里换算,读"38:12"是直接的。

置信度用中文标注含义,不要只给数字:
- ≥ 0.85:高
- 0.75 - 0.85:中
- < 0.75:低,标记需复核

## 验收标准

核心验收标准:**一个医生或助手打开页面,能在 2 分钟内验证完 8 次就诊的切分质量。**

关键是"3 秒一个就诊"的验证节奏——看摘要卡就能判断,不需要读完整对话。

具体检查项:

- 能选择一条长录音,看到可读的时长和员工名
- 能用默认 prompt 跑出切分结果
- 处理过程有进度显示(切分第几块、摘要第几个)
- 结果通过契约校验(完整覆盖时间轴、连续不重叠),不通过时明确报错
- 顶部汇总一眼看出"识别出几次就诊"
- **就诊摘要卡是默认视图**:每次就诊显示患者、主诉、处置、开场句、结束句
- 摘要卡默认不展开完整对话,点击才展开
- 点 `✓ 切分正确` 后自动跳到下一张卡,标记状态可见
- 点 `✗ 有问题` 后自动展开对话
- 相邻就诊之间有边界检查区,显示切口前后各 5 轮对话和中间间隙
- 顶部有验证进度(`5/8 已验证,4 正确 1 有问题`)
- 键盘快捷键可用(Y/N/空格/方向键)
- 所有时间显示为 MM:SS 格式,不是裸秒数
- 能修改 prompt 重新跑,对比效果

## 不需要完美的地方

- UI 不需要好看,能用就行
- 错误处理基本覆盖即可,不需要全面
- 超长文本的分块合并逻辑先做最简版本,后续迭代

# 两遍切分策略 — Codex 任务书

日期：2026-08-13
交付对象：Codex
文件：`internal/splitdemo/service.go`（主）、`internal/splitdemo/model.go`、`internal/splitdemo/static/index.html`

## 问题

现在的切分是单遍分块：把转写按 12000 字符切块，每块独立调一次 LLM，AI 只能看到那一块内的内容。

录音 1802（169 分钟）被切成了 19 块，每块约 10 分钟。第一个患者是一次连续的 27 分钟就诊（328-1968 秒），横跨至少 2-3 个块边界。AI 在每块内看到片段，对每块都独立判断，所以把这一次就诊切成了 4 段。这不是 prompt 的问题，是架构问题：**单块 AI 缺少全局上下文，无法识别跨块的连续就诊。**

## 解决方案：三步流水线

用三步替代原来的单次调用：

```
第一步：全局扫描 → 候选边界列表（秒数 + 信号类型）
第二步：逐一判定 → 每个候选点是 true/false
第三步：规则合并 → 把过短片段合并
```

每步职责单一，互不干扰。

---

## 第一步：全局候选扫描

### 目标

扫描**全文**，只找可能是就诊结束的位置，不判断真伪。

### 输入格式

全文转写，**精简版**：只保留时间戳和文本，去掉 speaker 标记，每行格式：

```
[MM:SS] 那你就先这样，不舒服再来。
[MM:SS] 拜拜。
[MM:SS] 拜拜，谢谢医生。
```

用 `[start_time]` 单时间戳（不用 `[start-end]`），节省 token。

如果精简版仍然超过模型上下文（qwen-max 支持 32k token，169 分钟约 2063 行精简后约 25 万字符，超出了），则每 100 分钟为一段扫描，段之间重叠 5 分钟。这一步不需要 AI 理解上下文，只是检索关键词，所以分段扫描结果质量不受影响。

### 第一步的 System Prompt

```
你是医疗录音边界检测助手。你的唯一任务是从转写文本中找出所有可能是"就诊结束"的位置，不做判断，只做发现。

## 要找的信号

强信号（必须报告）：
- 告别语：拜拜、再见、谢谢医生、慢走、辛苦了
- 公立医院开单指路：去二楼抽血、去药房拿药、拿着单子、到收费处、做完CT回来找我（这个是中途不算）、不舒服再来
- 公立医院交接科室：转到骨科、挂专家号、开住院证
- 私立/消费医疗交接：让客服跟你详细说、带你去前台、找小王办手续
- 叫号/点名：下一个、下一位

中等信号（也要报告）：
- 相邻两句时间戳间隔超过 30 秒（你必须计算每对相邻行的时间差）

## 输出格式

只输出 JSON 数组，不要任何解释文字：

[
  {"at_seconds": 615, "signal_type": "farewell", "signal_text": "拜拜"},
  {"at_seconds": 1968, "signal_type": "farewell", "signal_text": "谢谢医生"},
  {"at_seconds": 2100, "signal_type": "silence_gap", "signal_text": "间隔 62 秒"}
]

signal_type 的值：farewell / handoff / call_next / silence_gap
at_seconds 精确到秒。
```

### 第一步的 User Prompt

```
录音总时长：{{duration_seconds}} 秒

以下是转写文本（每行格式：[开始时间] 内容）：

{{transcript}}

请找出所有可能是就诊结束的位置，输出 JSON 数组。
```

### 第一步的输出数据结构

```go
type CandidateBoundary struct {
    AtSeconds  int    `json:"at_seconds"`
    SignalType string `json:"signal_type"`  // farewell / handoff / call_next / silence_gap
    SignalText string `json:"signal_text"`
}
```

---

## 第二步：逐一判定候选

### 目标

对每个候选点，取前后各 3 分钟（6 分钟窗口），判断这里是不是真正的就诊边界。

### 每次调用的输入

从完整 utterance 列表中按时间范围切出前后各 180 秒。窗口不够时（比如候选在最开头），取能取到的最大范围。

### 第二步的 System Prompt

```
你是医疗录音边界判定助手。你会看到一段 6 分钟左右的录音片段，其中某个时间点被标记为疑似就诊边界。你的任务是判断这里是不是真正的就诊结束。

## 是就诊结束（返回 true）

- 边界后出现了新患者描述自己的症状，医生重新做基础问诊（"多久了"、"什么时候开始的"、"以前看过吗"）
- 边界处有明确的告别语，后面是叫号或新患者

## 不是就诊结束（返回 false）

- 同一患者话题转换（从症状聊到费用、复查安排、用药方法）
- 患者中途离开做检查，但医生明确说了要回来
- 静默后同一对话继续
- 医生举例提到另一个患者，但那个人没有出现在对话里

## 不要依赖说话人标记

转写里说话人标记（speaker_0 等）可能全是同一个，不可信。靠内容判断：提问、下医嘱、解释病理的是医生；描述症状、回答提问的是患者。

## 输出格式

只输出 JSON，不要任何解释：

{"is_boundary": true, "confidence": 0.91, "reason": "32:47 处互道拜拜，32:54 医生开始询问新患者"}
```

### 第二步的 User Prompt

```
疑似边界在 {{at_seconds}} 秒（{{at_time}}），触发信号：{{signal_text}}

以下是边界前后各约 3 分钟的对话：

{{window_transcript}}

这里是不是真正的就诊结束？
```

### 第二步的输出数据结构

```go
type BoundaryJudgment struct {
    AtSeconds  int     `json:"at_seconds"`
    IsBoundary bool    `json:"is_boundary"`
    Confidence float64 `json:"confidence"`
    Reason     string  `json:"reason"`
    SignalType string  `json:"signal_type"`
    SignalText string  `json:"signal_text"`
}
```

---

## 第三步：规则合并

不调 LLM，用代码处理：

1. 把第二步判定为 true 的边界，按时间排序
2. 相邻两个边界的间隔 < 60 秒时，删除置信度较低的那个
3. 用确认的边界列表，把完整 utterance 切分成 encounter 片段
4. 对任何时长 < 60 秒的 encounter，与相邻较短的那段合并，标记 `needs_review: true`

## 如何整合到现有代码

### 新函数

在 `service.go` 里新增：

```go
// 第一步：全文扫描候选边界
func (s *Service) scanCandidateBoundaries(ctx context.Context, model string, utterances []Utterance, totalSeconds int) ([]CandidateBoundary, error)

// 第二步：判定单个候选
func (s *Service) judgeCandidate(ctx context.Context, model string, candidate CandidateBoundary, utterances []Utterance) (BoundaryJudgment, error)

// 第三步：规则合并，返回最终 segment 列表
func buildSegmentsFromJudgments(judgments []BoundaryJudgment, utterances []Utterance, totalSeconds int) []SplitSegment
```

### 修改 splitRecordingWithInput

现有函数里有一个分块循环（大约 420-478 行）。改造成：

1. 如果 utterances 非空（有结构化转写），走新的三步流水线
2. 如果只有纯文本（`TranscriptText`），保留现有的单遍分块逻辑作为 fallback

这样不破坏现有功能，只是对有结构化转写的录音走新路径。

### SplitRequest 加一个字段

```go
type SplitRequest struct {
    // ... 现有字段
    UseTwoPass *bool `json:"use_two_pass,omitempty"` // nil = 自动判断（有 utterances 就用两遍）
}
```

### SplitProgress 新增阶段

```go
// 阶段字符串
"scanning"   // 第一步，全局扫描
"judging"    // 第二步，逐一判定（进度：judged_count/total_candidates）
"merging"    // 第三步，规则合并
"summary"    // 已有的摘要生成阶段
```

`SplitProgress` 结构加字段：

```go
TotalCandidates  int
JudgedCandidates int
```

第一步：扫描边界信号...

进度条分四段：第一步 0-20%，第二步 20-70%（按 judged/total 比例），第三步 70-80%，摘要 80-100%。

## 关于第一步的长度限制

qwen-max 上下文约 32k token，精简版转写（只留时间戳和文本）每行约 30 字符，2063 行约 6 万字符，约 2-3 万 token，**在范围内，不需要分段**。

但要在 `scanCandidateBoundaries` 里做防守：如果精简版超过 2.5 万字符，按 120 分钟一段、重叠 5 分钟的方式分段扫描，结果合并后去重（相同秒数 ±5 秒的候选只保留一个）。

## 保留现有逻辑作为 fallback

以下情况仍走旧的单遍分块逻辑：
- 录音没有 `transcription_segments`（只有纯文本）
- `SplitRequest.UseTwoPass` 明确设置为 false
- 是合成用例（utterances 时间戳全来自拼接，两遍法对合成数据同样有效，但初期可以先只在真实录音上测）

## 验收标准

1. 录音 1802 用两遍法重跑，第一步输出候选边界列表（至少包含 32:47 处的拜拜）
2. 第二步对每个候选输出 is_boundary + confidence + reason
3. 最终就诊数量接近真实值（14 段左右），第一个患者（328-1968 秒）被识别为 1 段，不再切碎成 4 段
4. 前端进度显示四个阶段
5. 合成用例（造用例页面）仍然正常工作（走旧逻辑或两遍法均可）
6. 只有纯文本的录音（如 120、117）走旧逻辑，不报错

# 数据库迁移治理与发布门禁方案

更新时间：2026-10-06

## 一、当前断档的结论与修复

迁移编号 `20261006_004` 到 `20261006_009` 不代表迁移丢失。当前目录中没有这些版本文件，Git 历史也没有对应文件；这是日期内编号没有连续产生，而不是已经发布的迁移被删除。

当前真正的问题有两个：

1. 校验器错误地要求同一天的序号连续，导致合法的 `001、002、003、010、011` 被判定为断档。
2. 工作区曾出现两个 `20261006_001`，一个是评分等级回填，一个是临床提示词恢复。迁移版本必须唯一，提示词迁移已改名为 `20261006_012_restore_emr_generation_prompt_clinical.sql`。

修复原则：

- 已发布或已执行的迁移不改内容、不改版本号。
- 不补空迁移掩盖断档。
- 版本只要求格式正确、全局唯一、按字典序递增；同一天不要求连续。
- 已执行迁移仍由 checksum 保护，文件被修改时 API 必须拒绝启动。

## 二、从今天起的迁移分层

每次数据库变更必须明确属于以下一种：

| 类型 | 负责内容 | 示例 |
|---|---|---|
| Schema | 表、列、索引、约束、视图 | 新增 `grade` 列 |
| Backfill | 已有数据的可重复回填 | 为已有评分补等级 |
| Seed | 规则、模板、权限、默认配置 | 初始化正式规则 |
| Compatibility | 临时兼容旧版本 | 过渡字段、旧数据兼容 |

同一个迁移可以包含同一类的多个 SQL，但不能把长期兼容逻辑、不可控的大批量回填和表结构变更混在一起。兼容迁移必须有退出版本和删除计划。

## 三、表结构变更统一采用 Expand / Backfill / Contract

1. **Expand**：先增加新列、表或索引，保持旧代码可运行。
2. **Deploy**：发布同时兼容新旧结构的 API/Worker。
3. **Backfill**：单独执行可重试、可观测的回填，记录批次、耗时、影响行数和失败原因。
4. **Switch**：代码切换到新字段，验证读写和关键业务数据。
5. **Contract**：确认没有旧版本实例和旧流量后，才删除旧列、旧表或兼容逻辑。

禁止在一个发布中直接“改列类型 + 删除旧列 + 切换代码”。

## 四、发布前门禁

发布顺序固定为：

1. 生成数据库备份或确认可恢复点。
2. 在目标环境执行迁移预检：文件格式、重复版本、代码 checksum、数据库账本未知版本。
3. 执行 `--migrate-only`，迁移全部成功后再启动 API。
4. 验证关键表、关键列、关键数据和回填行数。
5. 发布 API，再发布 Worker，最后做健康检查。
6. 失败时优先回滚应用版本；涉及破坏性变更时不得自动回滚数据库，按迁移的回滚/修复方案处理。

普通 API 启动只校验，不自动写数据库。迁移执行必须由开发中心或发布脚本显式触发。

提交前至少执行：

```bash
./scripts/check_migrations.sh
```

涉及 Go 迁移加载逻辑时执行：

```bash
go test ./internal/store -run TestLoadEmbeddedSchemaMigrations -count=1
```

## 五、以后如何处理同一张表反复打补丁

历史迁移永远保留，新变化继续新增迁移；不要回改旧文件，也不要把多个历史文件改名重排。

当迁移历史过长时：

- 生产和已有环境继续按完整历史账本升级；
- 新建数据库可以使用经过审计的 baseline；
- baseline 只替代“新库重放历史”，不能覆盖生产账本，也不能删除生产已有迁移；
- baseline 必须记录截止版本、schema checksum 和生成时间。

## 六、必须记录的迁移信息

每个迁移提交必须同时写清：

- 版本和用途；
- 变更类型（Schema/Backfill/Seed/Compatibility）；
- 是否可重复执行；
- 预计影响行数和耗时；
- 前置条件；
- 验证 SQL 或检查项；
- 是否允许回滚，以及回滚方式；
- 兼容逻辑的退出版本。

这套规则解决的是“迁移文件存在但没有进入发布链路、编号冲突、结构和回填互相阻塞、应用已发布但数据库未就绪”四类风险。

## 七、迁移文件必须进入发布产物

本地工作区出现的 SQL 文件不等于发布内容。发布前必须检查：

```bash
git status --short -- internal/store/migrations
```

如果出现 `?? internal/store/migrations/...sql`，必须先判断它是：

- 本次功能需要的迁移：加入提交并纳入评审；
- 已废弃的临时文件：删除；
- 尚未决定的实验文件：不得进入发布构建。

禁止带着未跟踪迁移发布，也禁止只提交 Go 代码而遗漏对应 SQL。构建必须从干净提交检出开始，并在构建产物中核对迁移文件清单。

当前工作区已发现多份未跟踪迁移，包含 `20261006_011` 和刚改名的 `20261006_012`；它们在完成审查前不能视为已具备生产发布条件。

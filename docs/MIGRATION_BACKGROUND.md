# 迁移历史背景

> 本文档记录 lingce-api 项目的诞生背景、旧系统的问题分析、以及本次迁移要实现的目标。

## 一、项目背景

灵策医疗运营系统（原项目名 lince-medical-ops）是一套面向医疗机构的 SaaS 运营管理平台，核心功能包括：

- **录音分析**：对医生/咨询师的接诊录音进行 AI 转写、清洗、多维度分析（SEGUE 评分、科室路由、EMR 草稿生成）
- **智能工牌管理**：工牌设备全生命周期管理（验收、检测、分配、回收、异常处理）
- **内容中心**：基于录音素材和热点话题的 AI 内容生成（选题、文章、图文笔记、视频脚本）
- **客户中心**：统一客户档案、多渠道身份、标签分组、互动跟进
- **组织架构**：多租户、机构、科室、员工、医生、患者的层级管理
- **权限管理**：运营端和机构端两套独立的 RBAC 体系

系统服务三个前端：
- operations-web（运营管理后台）
- institution-web（机构管理后台）
- consultant-app（咨询师/医生移动端，Expo 构建）

## 二、旧系统现状

### 2.1 技术栈

旧后端服务 `operations-api` 基于：
- Python 3.9 + FastAPI 0.109
- SQLAlchemy 2.0 + Alembic（ORM + 迁移）
- PostgreSQL 16 + pgvector
- Celery + Redis（异步任务）
- APScheduler（定时调度）
- Docker + Docker Compose（部署）

### 2.3 核心问题

#### 问题一：代码膨胀失控

多个核心文件的行数较大，维护成本高：

| 文件 | 行数 | 说明 |
|------|------|------|
| config.py | 4,380 | 系统配置（含旧任务系统） |
| medical_recordings.py | 3,959 | 医疗录音 API |
| promotion.py | 3,637 | 推广中心（暂不迁移） |
| xiaohongshu.py | 3,212 | 小红书集成（暂不迁移） |
| badge_control.py | 3,045 | 工牌设备管理 |
| task_generator.py | 2,247 | 任务生成引擎（旧链路） |
| doctor_analysis_service.py | 1,856 | 医生分析服务 |
| recording_service.py | 1,699 | 录音服务 |

500 个 Python 文件、总计约 148,000 行代码分散在缺乏清晰边界的目录中，改动一处容易引发连锁问题。

#### 问题二：大量废弃代码

经过功能审计，确认以下模块已废弃或未实际使用：

| 模块 | 状态 |
|------|------|
| MVP-1 遗留（rules/variables） | 已废弃 |
| 会员中心 | 未实际使用 |
| 需求挖掘 | 未实际使用 |
| 产品推荐/销售 | 未实际使用 |
| 小红书集成 | 低频试验性 |
| 微信公众号 | 条件加载，部分使用 |
| 知识库（pgvector） | 条件加载 |
| HIS 数据同步 | 默认关闭 |
| 聚合客服 | 不确定 |
| 工作计划 | 未实际使用 |
| 旧任务系统（tasks 表） | 新旧链路交织，旧链路废弃 |

这些废弃模块的代码和数据表仍然存在于代码库中，增加了理解和维护成本。

#### 问题三：新旧链路交织

以任务系统为例，存在两套并行的实现：
- **旧链路**：基于 `tasks` 表，由 `task_generator.py`（98,519 行）驱动，包含任务规则、模板、调度器等完整体系
- **新链路**：基于 `recording_tasks` 表，由 recording-worker 驱动，专注于录音分析后的跟进任务

两套系统共存于同一代码库，共享部分模型和服务，导致开发和调试时需要不断区分"这段代码走的是哪条链路"。

#### 问题四：Python + Docker 部署痛苦

`requirements.txt` 包含 60+ 依赖包，其中多个有 C 扩展或系统级依赖（playwright、pgvector、pdfplumber、Pillow 等）。具体表现：

- Docker 构建频繁因依赖冲突失败
- 镜像体积大（基于 python:3.9-slim + 系统字体包）
- Web 和 Worker 共用同一镜像，无法独立扩展
- 每次部署需要完整的 `pip install`，耗时长
- 生产环境通过 SSH + rsync + docker-compose up 部署，非幂等

#### 问题五：数据库失控

150 张表中，大量是历史迭代遗留：
- 废弃功能的表未清理
- 128 个迁移文件，部分是一次性数据修复脚本
- 表命名不统一（有的带前缀，有的不带）
- 部分表有数据但对应功能已下线

### 2.4 已完成的 Go 服务拆分

在启动本项目之前，已经将三个最重、最痛的模块用 Go 独立实现：

| 服务 | 仓库 | 替代内容 | 状态 |
|------|------|---------|------|
| llm-gateway | /Users/yiliiang/Documents/llm-gateway | Python 中散落的 DashScope 直调 → 统一网关 | 生产就绪 |
| badge-middleware | /Users/yiliiang/Documents/badge-middleware | Python 中的工牌厂商回调/设备查询 → 统一中间件 | 生产就绪 |
| recording-worker | /Users/yiliiang/Documents/recording-worker | Python worker_main.py 中的录音分析流水线 → 独立 Worker | Phase 3 完成 |

这三个服务的共同特点：
- 单二进制部署（systemd 服务）
- 极少依赖（llm-gateway 仅 4 个直接依赖）
- 共享同一个 PostgreSQL 数据库
- 通过 HTTP 内部通信

它们的成功验证了 Go 重写的可行性和收益。

## 三、迁移目标

### 3.1 核心目标

1. **甩掉历史包袱**：不再背负废弃代码和无用数据表，代码库只包含实际使用的功能
2. **干净的代码结构**：每个模块有清晰的边界（handler → service → store），单文件不超过 500 行
3. **轻量部署**：单二进制 + systemd，与现有三个 Go 服务保持一致的运维模式
4. **前后端分离**：API 路径和响应格式保持兼容，前端零改动切换
5. **可扩展性**：通过提高服务器配置即可扩展，Go 的并发模型天然支持高吞吐

### 3.2 不做的事

- **不做微服务拆分**：单服务器部署场景下，一个二进制内部按 package 分模块即可
- **不重新设计数据库**：复用现有 PostgreSQL 表结构，仅建模需要的 ~60 张表
- **不改 API 契约**：保持 `/api/v1/*` 路径和 JSON 响应格式，前端不需要改动
- **不做渐进式迁移**：冻结新功能开发，完整重写后一次性切换

### 3.3 安全改进

迁移过程中顺带修复旧系统的已知安全问题：

| 问题 | 旧实现 | 新实现 |
|------|--------|--------|
| 密码哈希 | SHA256（无盐） | bcrypt |
| 验证码存储 | 进程内存 | 数据库或 Redis |
| JWT 库 | python-jose | golang-jwt |

## 五、迁移策略

### 5.1 总体策略

**冻结 → 重写 → 切换 → 清理**

1. 冻结 operations-api 的新功能开发
2. 在独立仓库 lingce-api 中用 Go 重写所有保留功能
3. 前端联调验证通过后，nginx 一次性切换到 lingce-api
4. 下线 Python 服务，清理废弃数据表

### 5.2 数据库策略

- 同一个 PostgreSQL 实例，同一个数据库
- Go 的 store 层只建模需要的 ~60 张表
- 表结构保持不变（字段名、类型一致），零数据迁移风险
- 可做小幅改进：补缺失索引、统一命名风格
- Python 下线后，择机 DROP 废弃表

### 5.3 API 兼容策略

- 保持 `/api/v1/*` 路径不变
- 保持 JSON 响应结构不变
- 统一错误响应格式：`{"code": "ERROR_CODE", "message": "描述", "details": {}}`
- 统一分页格式：`{"items": [], "total": 0, "page": 1, "page_size": 20}`
- 前端零改动

### 5.4 部署策略

- 单二进制 + systemd 服务（与 llm-gateway、badge-middleware、recording-worker 一致）
- 端口 :18080
- 健康检查：`GET /healthz`
- 配置：环境变量 + .env 文件

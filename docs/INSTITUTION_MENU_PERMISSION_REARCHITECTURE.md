# 机构端租户菜单权限控制全链路重构总纲

本文档是机构端租户菜单权限控制体系的一次性重构总纲。

本文档回答的不是“某张表怎么改”或“某个接口怎么修”，而是以下更高层的问题：

1. 运营平台如何控制套餐的菜单可见范围
2. 机构端管理员如何控制角色的菜单可见范围
3. 员工最终实际能看到什么菜单
4. 前端菜单显示、路由守卫、后端接口权限、分析/worker 角色判断如何基于同一套事实
5. 当前体系为什么失控
6. 一次性彻底重构后，系统应当长成什么样
7. 数据库、后端、前端、worker 各自承担什么职责

## 1. 为什么必须重构

当前机构端菜单权限控制不是一个统一系统，而是多个阶段性方案叠加后的混合体。

问题已经不是“代码有点乱”，而是：

1. 权限语义没有被单点定义
2. 运行时结果无法稳定推导
3. 前端、后端、worker 依赖的权限事实不一致
4. 数据表层已经真实分叉
5. 系统正在靠兼容分支和默认放开逻辑维持运转

继续在现有结构上修补，只会让问题越来越难以收口。

## 2. 当前问题的本质

当前问题不是单一数据库问题，也不是单一前端问题，而是全链路权限模型失真。

整个链路涉及五层：

1. 套餐/功能包层
2. 角色定义与角色菜单授权层
3. 员工当前角色事实层
4. 前端菜单显示与路由守卫层
5. 后端接口权限判断层

现在这五层没有被同一个模型统一约束。

## 3. 现状问题详述

## 3.1 套餐/功能包层的问题

### 3.1.1 目标语义本应是什么

套餐/功能包层本应只表达：

1. 某租户理论上最多能看到哪些菜单
2. 某租户理论上最多能用哪些功能

也就是：

1. 套餐只控制上限
2. 套餐不直接决定员工个人是否能看到某个菜单

### 3.1.2 当前实际问题

当前系统中，套餐/功能包链路和角色授权链路存在混合与越权行为：

1. 租户功能组和菜单白名单是一套链路
2. 角色菜单授权是另一套链路
3. 某些代码会尝试把功能包变更同步为角色菜单授权
4. 前端有时把“租户允许菜单”直接当成“员工可见菜单”

这导致套餐层从“租户菜单上限”滑向了“实际菜单权限的一部分真相”，职责越界。

### 3.1.3 造成的后果

1. 套餐降配后，角色授权可能未被回收
2. 套餐解绑后，系统可能 fail-open
3. 某些角色即使没有被明确授权，也可能因为套餐白名单而看到菜单
4. 运营平台以为自己在改套餐，实际上间接污染了角色授权层

## 3.2 角色定义与角色菜单授权层的问题

### 3.2.1 正确职责本应是什么

角色层本应只回答：

1. 某租户有哪些角色
2. 某个角色被授予哪些菜单

它不应该回答：

1. 某租户是否有这个菜单能力
2. 某员工当前属于什么角色

### 3.2.2 当前实际问题

当前开发库和代码已经证明：

1. 角色定义与角色菜单授权不在同一体系里
2. `institution_roles` 与 `inst_role_menus` 混搭
3. `institution_menus` 尚未真正落地，菜单字典仍主要依赖 `inst_menus`
4. 角色菜单授权真实运行面仍在 `inst_role_menus`

也就是说：

1. 角色定义层和授权层没有共享同一套统一数据模型
2. 表前缀、字段语义、ID/code 体系都没统一

### 3.2.3 造成的后果

1. 角色保存成功不代表角色菜单授权链路可推导
2. 菜单字典变更可能不会自然反映到角色授权上
3. 角色定义可以迁到新表，菜单授权却还挂在旧表
4. 后续任何重构都会遇到“角色定义在新体系，授权在旧体系”的双轨问题

## 3.3 员工当前角色事实层的问题

### 3.3.1 正确职责本应是什么

员工当前角色事实层本应只回答一件事：

1. 某个员工当前是什么角色

### 3.3.2 当前实际问题

开发库已确认：

1. `institution_employee_roles` 与 `inst_employee_roles` 同时存在
2. 两边数据不一致
3. `inst_employee_roles` 存在一员工多角色
4. 还存在无法映射到角色定义层的角色编码

这说明员工角色事实层不是单一真源，而是已经发生分叉。

### 3.3.3 造成的后果

1. 登录态展示的角色可能和 worker 判断角色不同
2. 录音分析路由可能和后台权限展示不一致
3. 改员工角色后，不同链路看到的结果可能不同步
4. 部门默认角色和手工设置角色可能叠加出多角色事实

## 3.4 前端菜单显示与路由守卫层的问题

### 3.4.1 正确职责本应是什么

前端应当只负责：

1. 基于后端给出的权限事实渲染菜单
2. 做体验层路由阻断
3. 不自行发明权限语义

### 3.4.2 当前实际问题

当前 institution 前端存在典型的权限语义外溢：

1. 前端自己计算菜单 code
2. 前端基于本地 manifest 推导哪些页面属于哪些菜单
3. 前端在某些情况下把“空角色菜单”解释成“继承租户所有菜单”
4. 快捷入口、侧边栏、路由守卫并不总是用同一套规则

### 3.4.3 造成的后果

1. 页面可见性和快捷入口可见性不一致
2. 侧边栏能看到，不代表接口真的允许
3. 接口返回成功，不代表路由守卫允许
4. 新增菜单时，前端可能因为本地规则没更新而失真

## 3.5 后端接口权限层的问题

### 3.5.1 正确职责本应是什么

后端必须是权限真相的最终裁决者。

后端应负责：

1. 计算当前员工的有效菜单
2. 对敏感接口做权限判断
3. 提供前端可消费的权限结果

### 3.5.2 当前实际问题

当前很多逻辑仍停留在：

1. 认证通过即可调用
2. 只靠前端菜单隐藏控制访问
3. 权限更多表现为“页面显示控制”，不是“服务端强约束”

### 3.5.3 造成的后果

1. 知道接口路径的人可能绕过前端限制
2. 系统无法宣称自己有统一的菜单权限控制
3. 审计与合规层面无法证明权限边界

## 4. 当前系统为什么会演变成这样

这是一个阶段性妥协逐步堆叠的结果。

可以概括为：

1. 先有旧 `inst_*` 体系
2. 后来引入 `institution_*` 体系，希望做规范化
3. 又引入租户功能包链路，希望实现套餐控制
4. 为了兼容 worker、录音、badge、sandbox 等业务链路，部分地方保留旧表
5. 迁移没有一次收口，而是长期停在半迁移状态

所以当前系统最大的问题不是“有旧表”，而是：

1. 多套模型长期共存
2. 没有最终裁决层
3. 没有明确 fail-closed 原则

## 5. 本次重构要解决的真正问题

本次重构必须一次性解决的是：

1. 权限语义统一
2. 数据模型统一
3. 运行时计算统一
4. 前后端判定统一
5. worker 与业务链路角色事实统一
6. 菜单新增、角色变更、套餐变更、租户初始化的行为统一

这六件事缺任何一件，都不能算真正完成重构。

## 6. 重构后的全链路目标模型

## 6.1 总体原则

重构后的系统采用三层权限模型：

1. 套餐上限层
2. 角色授权层
3. 员工角色事实层

它们的关系必须严格固定：

1. 套餐决定租户可用菜单上限
2. 角色决定在这个上限之内，某角色被授予哪些菜单
3. 员工通过当前角色继承角色菜单
4. 最终结果由交集计算得出

## 6.2 套餐上限层

职责：

1. 由运营平台配置
2. 表达租户最多可以使用哪些菜单

来源：

1. `tenant_feature_groups`
2. `tenant_feature_group_items`
3. `tenant_feature_assignments`
4. `tenant_feature_overrides`

语义约束：

1. 只控制租户菜单上限
2. 不直接给角色授菜单
3. 不直接给员工授菜单

## 6.3 角色授权层

职责：

1. 由机构端管理员配置
2. 表达某角色在租户可用菜单范围内，被授予哪些菜单

来源：

1. `institution_roles`
2. `institution_role_menus`
3. `institution_menus`

语义约束：

1. 角色空授权就是无菜单
2. 不允许空授权自动继承全量套餐菜单

## 6.4 员工角色事实层

职责：

1. 表达员工当前属于哪个角色

来源：

1. `institution_employee_roles`

语义约束：

1. 一员工只有一个当前角色
2. 当前角色使用 `role_code`

## 6.5 最终计算公式

最终有效菜单必须固定为：

`effective_menu_codes = tenant_allowed_menu_codes ∩ role_granted_menu_codes ∩ active_menu_codes`

其中：

1. `tenant_allowed_menu_codes`：租户套餐上限
2. `role_granted_menu_codes`：角色授权菜单
3. `active_menu_codes`：当前启用菜单字典

这条公式必须成为整个系统唯一的运行时权限规则。

## 7. 重构后的职责边界

## 7.1 运营平台职责

运营平台只负责：

1. 维护功能包
2. 维护套餐与功能包绑定
3. 给租户分配功能包
4. 配置租户菜单 override

运营平台不负责：

1. 给具体角色授菜单
2. 推断某个员工是否能看到某菜单

## 7.2 机构端管理员职责

机构端管理员只负责：

1. 创建和维护角色
2. 给角色分配菜单
3. 给员工分配角色
4. 给部门配置默认角色

机构端管理员不负责：

1. 改租户套餐上限
2. 绕过套餐控制看到更高权限菜单

## 7.3 前端职责

前端只负责：

1. 菜单展示
2. 路由体验守卫
3. 权限配置界面交互

前端不负责：

1. 作为权限真相来源
2. 通过本地规则发明菜单归属语义

## 7.4 后端职责

后端必须负责：

1. 统一计算有效菜单
2. 给前端返回真实权限结果
3. 给敏感接口做权限判断
4. 给 worker / analysis / badge / sandbox 提供统一角色事实

## 7.5 Worker / 分析链路职责

worker 与分析链路只负责：

1. 消费统一员工角色事实
2. 按角色驱动业务路由

它们不应自己维护另一套角色真相。

## 8. Fail-Closed 原则

本次重构必须明确采用 fail-closed。

意味着：

1. 没有功能包分配，不给菜单
2. 没有角色授权，不给菜单
3. 没有有效菜单字典，不给菜单
4. 角色无法映射，不给权限
5. 菜单无法映射，不给权限

不能再出现：

1. 空配置=全权限
2. 配置缺失=默认放开
3. 路由守卫因为缺数据而让用户进入页面

## 9. 这次重构的核心解决方案

## 9.1 统一命名

机构端权限域全部统一为 `institution_*`。

这样可以直接把系统中的“权限域”与“套餐域”区分为：

1. `institution_*`
2. `tenant_feature_*`

## 9.2 统一真源

最终只允许以下真源存在：

1. `institution_employee_roles`
2. `institution_roles`
3. `institution_menus`
4. `institution_role_menus`
5. `institution_department_roles`
6. `tenant_feature_*`

## 9.3 统一业务键

本次重构优先使用业务键：

1. 角色使用 `role_code`
2. 菜单使用 `menu_code`

而不是继续混用：

1. `role_id`
2. `menu_id`
3. `path -> code`
4. 本地 hardcode 规则

原因：

1. 角色和菜单需要跨服务、跨环境、跨迁移稳定存在
2. code 比 id 更适合作为业务事实层键

## 9.4 统一运行时计算

系统必须提供统一的后端权限计算函数，负责：

1. 计算某员工当前角色
2. 计算某员工所属租户套餐上限
3. 计算某角色菜单授权
4. 计算最终有效菜单

前端与接口校验都必须消费这个统一结果。

## 10. 本次重构不做的事

为了保证重构边界清晰，本次不顺手改变以下业务语义：

1. 不重新设计组织管理产品逻辑
2. 不引入多角色员工长期并存模型
3. 不扩展租户级自定义菜单
4. 不把菜单权限扩展成按钮级权限体系

本次只解决菜单权限控制的一致性和可维护性问题。

## 11. 关键场景下的预期行为

## 11.1 新建租户

预期：

1. 系统创建默认 `admin` 角色
2. 创建默认管理员员工
3. 默认管理员写入 `institution_employee_roles`
4. 默认管理员菜单来自 `institution_menus.is_default_for_admin = true`
5. 但最终仍要受租户套餐上限约束

## 11.2 新增菜单

预期：

1. 菜单只在 `institution_menus` 中注册一次
2. 若未加入功能包，则租户不可见
3. 若已加入功能包但未授给角色，则员工不可见
4. 前端只消费后端菜单字典，不再自行猜测

## 11.3 新增角色

预期：

1. 角色定义先创建
2. 若未授菜单，则角色默认无菜单
3. 不再出现空角色自动继承租户全菜单

## 11.4 员工改角色

预期：

1. 只改 `institution_employee_roles`
2. 修改后，前端菜单、后端权限、worker 角色分域同时统一生效

## 11.5 套餐降配

预期：

1. 租户菜单上限立即缩小
2. 角色授权记录不必删除
3. 最终有效菜单自动通过交集缩小

## 11.6 套餐解绑

预期：

1. 若没有显式全功能策略，则租户有效菜单为空
2. 系统 fail-closed

## 12. 如何判断重构成功

只有同时满足以下条件，才算真正成功：

1. 数据层只剩单一真源
2. 前端侧边栏、快捷入口、路由守卫结果一致
3. 后端敏感接口权限结果与前端一致
4. worker / analysis / badge / sandbox 读取同一套角色事实
5. 新增租户、新增菜单、改角色、改套餐、降配五类动作都能稳定推导结果
6. 不需要任何 legacy fallback 或 fail-open 逻辑

# API单体服务统一访问模型与租户收口方案

日期：2026-08-07

## 1. 目标

在不拆微服务的前提下，把 lingce-api 的访问控制收成一条统一链路：

`认证 -> 用户类型 -> 租户范围 -> 权限 -> handler -> service/store`

核心不是增加更多 if，而是把散落在 handler 里的身份判断、租户判断、权限判断，统一上收。

## 2. 问题现状

- 路由、handler、service 三层都在做访问判断。
- 同一种租户逻辑在多个模块里重复实现。
- `claims.TenantID`、`auth.UserTypeAdmin`、`tenancy.ResolveScope()` 分散出现。
- 新功能容易继续复制旧写法，导致规则越来越散。

## 3. 统一模型

### 3.1 路由声明

路由只声明策略，不写业务判断。

推荐字段：

- `AuthMode`
- `AllowedUserTypes`
- `TenantMode`
- `Permission`

### 3.2 TenantMode 约定

- `none`：不做租户解析
- `scope`：解析租户范围并注入上下文
- `required`：必须落到单租户

### 3.3 上下文职责

认证中间件负责放入 JWT claims。

租户中间件负责放入 scope。

handler 只消费上下文，不再自己推导“该不该允许”。

### 3.4 service/store 职责

- service/store 显式接收 `tenantID` 或 `Scope`
- 跨租户查询必须显式传入 `TenantIDs`
- 不允许依赖全局态隐式推导租户

## 4. 实施顺序

1. 给路由模型补 `TenantMode`。
2. 让路由注册器统一处理 tenant scope。
3. 先迁移 `dashboard`、`support`、`recording` 里的高频租户路由。
4. 再收敛 `content`、`customer`、`organization`、`employee` 等模块。
5. 最后清理 handler 内残留的租户判断。

## 5. 迁移原则

- 保持现有路径不变。
- 先兼容旧写法，再逐步切到新写法。
- 单体内收口，不引入微服务拆分。
- 每次只动一条访问规则链，不混着重构业务。

## 6. 验收标准

- 新路由默认能表达租户模式。
- handler 中新增的租户判断显著减少。
- `tenant scope` 的计算只保留少数统一入口。
- `go test ./...` 继续通过。

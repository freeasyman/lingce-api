同一 `eventId` 的多次回调，不只是时间上重复，载荷本身也不稳定。

### 1. `fileUrl` 不稳定

表现有两类：
- 同一事件反复返回不同签名的 CDN URL
- 同一事件部分推送里 `fileUrl` 直接为空

- `iot_cloud_25401534`

  - 对应多组不同签名地址

  - 存在 `fileUrl` 为空的推送

这说明厂家侧对同一事件不是在重复发送同一稳定载荷，而是在重复发送内容不完全一致的载荷。

### 2. `stopTime` 缺失

典型事件：
- `iot_cloud_25706758`
  - 有 `20` 次推送缺失 `stopTime`
- `iot_cloud_25754754`

同一 `eventId` 一部分推送有结束时间，另一部分没有，说明事件数据在不同推送阶段不完整。

## 七、厂家侧问题归纳

从 `SSYX51036358` 这台设备当天的表现看，厂家侧至少存在以下问题：

1. 同一 `eventId` 缺少有效幂等控制，导致重复推送次数异常高。
2. 同一事件在多个小时内持续重复发送，说明重试/补推任务没有正常终止。
3. 同一事件不同次推送的字段内容不一致，说明上游事件对象在发送阶段不稳定。
4. 部分推送缺少 `fileUrl`、`stopTime`、`seconds`，说明厂家会发送不完整事件。
5. 同一设备可同时并行重推多条历史事件，说明问题不是单点故障，而是设备或上游任务队列层面的系统性行为。

## 八、建议厂家排查方向

1. 检查 `AUDIO_INFORM` 的投递幂等逻辑，确认同一 `eventId` 在何种条件下会被再次发送。
2. 检查投递确认机制，确认是否因为回执状态未更新，导致任务持续重放。
3. 检查 `SSYX51036358` 所属设备在 `2026-06-20` 的事件发送队列和补偿任务日志。
4. 检查为什么同一 `eventId` 会出现：
   - URL 变化
   - `fileUrl` 为空
   - `stopTime` 缺失
   - `seconds` 缺失或为 0
5. 检查是否存在“先发送半成品事件，再发送完整事件，但旧任务未停止”的逻辑。
6. 检查 `2026-06-18`、`2026-06-19` 形成的旧事件为何在 `2026-06-20` 被重新长时间推送。

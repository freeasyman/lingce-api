# 开发计划

> 本文档定义 lingce-api 的分阶段开发计划、里程碑、依赖关系和验收标准。

## 总览

| 阶段 | 内容 | 预估工时 | 里程碑 |
|------|------|---------|--------|
| Phase 1 | 基础设施 + auth + organization | 2.5 周 | 可登录、可查看组织数据 |
| Phase 2 | rbac + sysconfig | 2.5 周 | 权限体系就绪、配置管理就绪 |
| Phase 3 | recording + badge | 4 周 | 核心业务模块就绪 |
| Phase 4 | content + customer | 3 周 | 业务模块完整 |
| Phase 5 | support + 集成测试 | 1.5 周 | 全部 API 就绪 |
| Phase 6 | 前端联调 + 切换上线 | 1 周 | 生产环境切换 |
| **合计** | | **~14.5 周** | |

> 注：工时按单人全职估算。两人并行可压缩到 8-9 周（Phase 3/4 可并行）。

---

## Phase 1：基础设施 + auth + organization（2.5 周）

### 目标
搭建项目骨架，实现认证和组织架构模块。完成后可以登录系统、查看租户/机构/员工等基础数据。

### 1.1 项目骨架（3 天）

- [ ] HTTP 服务器（net/http + 路由）
- [ ] 配置加载（环境变量 + .env）
- [ ] PostgreSQL 连接池（pgx/v5）
- [ ] 中间件框架（日志、Recovery、RequestID、CORS）
- [ ] 统一响应格式（成功/错误/分页）
- [ ] 健康检查端点 `GET /healthz`
- [ ] Makefile（build、run、test、lint）
- [ ] .gitignore、.env.example

### 1.2 auth 模块（4 天）

| 端点 | 优先级 | 复杂度 |
|------|--------|--------|
| `POST /api/v1/auth/login` | P0 | 中 |
| `POST /api/v1/auth/login/institution` | P0 | 中 |
| `POST /api/v1/auth/login/employee` | P0 | 中 |
| `POST /api/v1/auth/login/mobile` | P0 | 中 |
| `GET /api/v1/auth/me` | P0 | 低 |
| `GET /api/v1/auth/captcha` | P0 | 中 |
| `POST /api/v1/auth/change-password` | P1 | 低 |
| `POST /api/v1/auth/mobile/sms/send` | P1 | 中（阿里云 SMS） |
| `POST /api/v1/auth/mobile/sms/login` | P1 | 中 |

关键实现：
- JWT 生成/验证（golang-jwt）
- 密码哈希（bcrypt，兼容读取旧 SHA256）
- 图形验证码生成
- 会话版本管理（多端隔离）
- 租户有效期验证
- 阿里云 SMS 集成

### 1.3 organization 模块（5 天）

**员工管理（7 端点）**：
- 列表（含部门、角色、医学专科）、详情、创建、更新、删除
- 医助绑定查询/更新

**部门管理（11 端点）**：
- organization.py 的 3 个 + departments.py 的 8 个
- 含 HIS 同步、业绩统计

**机构管理（6 端点）**：
- 统计、列表、详情、创建、更新、删除

**医生管理（11 端点）**：
- 列表、详情、创建、更新、删除
- HIS 同步、业绩统计、员工映射

**患者管理（7 端点）**：
- 列表、详情、创建、更新、删除
- HIS 同步、360 度视图

**其他（1 端点）**：
- 医学专科目录

### 验收标准
- [ ] 三端（运营/机构/移动）均可登录并获取用户信息
- [ ] 组织架构 CRUD 全部通过 API 测试
- [ ] 与现有 PostgreSQL 数据库兼容（读取现有数据正常）

## Phase 2：rbac + sysconfig（2.5 周）

### 目标
权限体系和系统配置就绪。完成后可以管理角色权限、租户配置、订阅等。

### 2.1 rbac 模块（8 天）

**运营端 RBAC（23 端点）**：
- 角色 CRUD（5）
- 权限管理（3）
- 菜单管理（7）
- 管理员管理（6）
- 角色菜单关联（4）

**机构端 RBAC（21 端点）**：
- 角色 CRUD（5）
- 菜单管理（5）
- 权限管理（3）
- 员工角色（3，单角色模式）
- 部门角色（3）
- 上下级关系（2）

关键实现：
- Casbin 集成（Go 原生库，比 Python 版更成熟）
- 两套独立的 RBAC 体系（ops_casbin_rule / inst_casbin_rule）
- 超级管理员特权逻辑
- RBAC 中间件（替代 Python 的 @require_role 装饰器）

### 2.2 sysconfig 模块（4 天）

| 子模块 | 端点数 | 说明 |
|--------|--------|------|
| 标准变量 | 5 | CRUD |
| 数据映射 | 8 | CRUD + 批量 + AI 建议 |
| 租户管理 | 6 | CRUD（含初始化订阅、部门、菜单） |
| 订阅管理 | 7 | 计划 CRUD + 订阅操作 + 事件历史 |
| 租户功能控制 | 9 | 功能分组 + 覆盖规则 + 有效策略 |

关键实现：
- 租户创建时的级联初始化（订阅、部门、角色、菜单）
- 订阅状态机（active → grace → expired → paused）
- 功能策略合并逻辑（分组 + 覆盖）

### 验收标准
- [ ] 运营端可管理角色、菜单、管理员
- [ ] 机构端可管理角色、员工角色分配
- [ ] 租户创建/订阅/功能控制全流程通过
- [ ] RBAC 中间件正确拦截无权限请求

## Phase 3：recording + badge（4 周）

### 目标
核心业务模块就绪。这是代码量最大的阶段。

### 3.1 recording 模块（2.5 周）

**咨询师录音（27 端点）**：
- 列表、详情、上传、统计（6 种维度）
- 转写/分析/清洗触发（调用 recording-worker）
- 分析结果查询、反馈
- 跟进确认、话术生成、运营计划
- 批量操作

**医疗录音（19 端点）**：
- 列表、质检看板、医生能力排行/详情
- 沟通分析、周会/周总结、团队趋势
- 最佳实践库、跟进任务确认
- 机构规则配置、分析设置

**录音任务（13 端点）**：
- 统计、日报、我的任务、全部任务
- 分配、完成、取消
- 员工协作关系管理

**录音看板（4 端点）**：
- 经营日报、运营诊断、目标更新、漏斗详情

**分析看板（4 端点）**：
- 员工诊断、团队能力、早会素材、个人成长

**录音提示词（10 端点）**：
- 提示词 CRUD + 租户配置 CRUD + 测试

关键实现：
- 与 recording-worker 的 HTTP 集成（POST /v1/jobs 触发任务）
- 与 llm-gateway 的集成（话术生成、运营计划等需要 LLM 调用）
- 复杂的统计查询（多维度聚合、同比环比、漏斗分析）
- 多角色数据过滤（医生/咨询师/医助看到不同数据）

### 3.2 badge 模块（1.5 周）

**设备生命周期管理（33 端点）**：
- 验收（验证、导入、厂商核验）
- 检测（单台、批量、实时状态、录音测试）
- 分配（租户、员工）
- 回收（员工、租户）
- 工单（提交、审核、执行、列表）
- 设备台账（列表、生命周期日志）
- 厂商管理（列表、配置更新）
- 厂家设备池（同步、差异、回滚、创建草稿、标记、异常工单）
- 仪表板

**智能工牌（13 端点）**：
- 租户设备（列表、概览、历史）
- 录音控制（设备列表、启动、停止、日志）
- 厂商回调（开发者、音频）
- 待处理事件
- 我的工牌（状态、启动、停止）

关键实现：
- 与 badge-middleware 的 HTTP 集成（设备查询、录音控制）
- 设备状态机（草稿 → 待验收 → 待分配 → 已分配 → 已回收 → 报废）
- 工单审批流程
- 厂家设备池同步与差异对比

### 验收标准
- [ ] 录音列表、详情、统计看板数据与旧系统一致
- [ ] 触发转写/分析后 recording-worker 正常处理
- [ ] 工牌设备全生命周期流程通过
- [ ] 录音控制（启动/停止）通过 badge-middleware 正常工作

## Phase 4：content + customer（3 周）

### 目标
内容中心和客户中心就绪。

### 4.1 content 模块（2 周）

**选题管理（12 端点）**：
- 热点话题、选题 CRUD、AI 生成
- "我有想法"四步流程（初始化 → 解析文件 → 生成 → 保存）

**内容管理（12 端点）**：
- 列表、详情、AI 生成（文章/图文/视频脚本）
- CRUD、图片生成（异步/同步/保存）
- 发布/取消发布

**会话洞察（4 端点）**：
- 统计、高频问题、选题挖掘、保存

**发布任务（8 端点）**：
- 工作台、列表、详情、创建（单个/批量）
- 状态更新、取消、重试、删除

**GEO 优化（4 端点）**：
- 分析、按 ID 分析、深度优化、策略注入

**素材池（11 端点）**：
- 列表、统计、聚类、灵感、生成草稿
- 驳回、详情、状态更新
- 荣誉榜、我的统计/采纳

**提示词模板（22 端点）**：
- 通用提示词（13）：CRUD + 版本管理 + 发布/回滚 + 测试
- 内容提示词（9）：CRUD + 克隆 + 测试 + 初始化

关键实现：
- 与 llm-gateway 的深度集成（选题生成、内容生成、GEO 优化）
- 异步图片生成任务管理
- 提示词版本管理和发布/回滚机制
- 内容发布工作流

### 4.2 customer 模块（1 周）

**客户管理（17 端点）**：
- 列表、统计、详情、热度历史
- 创建、更新、标记成交
- 渠道身份、互动记录、跟进记录
- 会员信息、重复检测/合并
- 咨询记录、病案记录

**标签管理（6 端点）**：
- CRUD + 客户列表 + 批量打标

**分组管理（12 端点）**：
- CRUD + 客户列表 + 智能计算
- 成员增删 + 规则预览/验证/字段/操作符

关键实现：
- 智能分组规则引擎（条件组合 → SQL 查询）
- 客户去重与合并逻辑
- 多渠道身份管理

### 验收标准
- [ ] AI 选题生成和内容生成流程通过
- [ ] 素材池数据与旧系统一致
- [ ] 客户列表、标签、分组功能正常
- [ ] 智能分组规则计算结果正确

## 风险与应对

| 风险 | 影响 | 应对措施 |
|------|------|---------|
| 旧 API 响应格式不一致 | 前端兼容问题 | 逐个端点对比旧系统响应，确保格式一致 |
| 复杂统计查询性能 | 看板页面慢 | 提前做 SQL 性能测试，必要时加索引 |
| LLM 集成链路复杂 | 内容生成功能异常 | 复用 llm-gateway 已验证的接口 |
| Casbin 行为差异 | 权限判断不一致 | 用相同的测试用例验证 Go 和 Python 版本 |
| 迁移周期过长 | 业务需求积压 | 严格按优先级推进，P0 端点优先 |
